# 姉妹サイト共通仕様

鯨屋（くじらや）が運営する4つのサイトで共通して守る決まりを、ここ1か所にまとめる。

**この文書が唯一の正本。** 各サイトのリポジトリにコピーを置かず、ここを読むこと。
仕様を変えたいときは、この文書を直してから各リポジトリに反映する。逆はしない。

URL: https://github.com/VirgoB77/ogataten-nippo/blob/main/docs/kyotsu-shiyo.md

---

## 1. なぜ共通仕様が要るのか

4つのサイトは、扱う制度も読者も別だが、**同じ土地の上で起きたことを別の角度から見ている**。

```
農地転用・環境影響評価            開店の2〜4年前
都市計画決定・地区計画            1〜3年前
開発許可・盛土規制法              1〜2年前
公有財産の売却（跡地）            数年前
工事完了公告（都計法36条3項）     半年〜1年前
大規模小売店舗立地法の届出        8か月前   ← 大型店日報
　　開店・稼働
町丁目ごとの犯罪統計              現在      ← 犯罪統計マップ
　　↓（数年〜十数年）
競売・公売                                  ← 競売統計
```

同じ住所を同じキーで表せれば、この線が引ける。
「この土地は3年前に市有地として売られ、2年前に開発許可が下り、去年工事完了公告が出て、
今年大型店の届出が出た」——これを出せるのは、キーを揃えたときだけ。

だから **住所の正規化と出力スキーマだけは、4サイトで一言一句そろえる。**
それ以外（サイトの作り、HTMLの書き方、パイプラインの組み方）は各サイトの自由。

---

### どの節が効くかは、サイトによって違う

この文書の節は2種類ある。**新しいサイトを立てるとき、どちらに当たるかを書き出す。**

| | 節 | いつ効くか |
|---|---|---|
| **相手への振る舞い** | 3.4 取得の作法／3.5 出典／7 運営者情報／9 技術方針 | **データの性質にかかわらず、全サイトで効く** |
| **データの性質** | 3.1 個人情報／3.2 小さい母数／4 `addr.py`／6 `index.json` | データが住所や当事者を持つときだけ効く |

**「うちは別系統だから共通仕様は関係ない」と読むと、取得の作法まで落ちる。**
robots を見る・間隔を空ける・429 や 503 で止まる・名乗る——これは
**相手のサーバーの話**であって、こちらのデータが何かとは関係がない。

一部だけ効く節もある。5サイト目（住宅系補助金の自治体横断）は
データに当事者がいないので 3.1 は効かないが、**自治体の補助金ページには
問い合わせ先に担当者名が載ることがある。**
課の名前と電話番号は出す、個人名は出さない、だけは守る。

同じ作法・同じ屋号で作るが、**住所の串には刺さらない。**
姉妹サイトではあるが、家族ではない。

### 街頭窃盗統計という名前について

警察庁が「街頭犯罪」と呼んでいる分類の、窃盗の部分そのもの。
扱う7手口は、ひったくり・車上ねらい・自動車盗・オートバイ盗・自転車盗・
部品ねらい・自動販売機ねらい。実データで確認ずみ（罪名は窃盗のみ、手口は7つだけ）。

**侵入盗（空き巣）は街頭犯罪ではないので、最初から入っていない。**
データが欠けているのではなく、そういうデータ。名前がこれを先に説明する。

出どころが警察のデータなので、名前も警察の言葉にそろえる。
「屋外窃盗」は造語なので使わない。「盗難」は被害者側の言葉で、
警察の統計は「窃盗」「認知件数」なので使わない。

## 3. 守ること（ハードルール）

破ったら公開しない。迷ったら出さない方を選ぶ。

### 3.1 個人情報

**原則：個人が特定できる組み合わせを、恒久的に固定しない。**

一次情報の側が公開していても、こちらは残す。行政の公告は数か月で消えるが、
こちらのサイトは消えない。「消えない」ことが、そのまま責任になる。

| 出すもの | 個人 | 法人 |
|---|---|---|
| 氏名・名称 | **出さない**（`個人` と表記） | 出す |
| 所在地 | **町丁目まで**に丸める | 地番まで出す |
| 面積・用途・日付・金額 | 出す | 出す |

- 法人かどうかが**確かめられないとき**は、個人として扱う。推測で法人にしない。
- **名前がそもそも公表されていない場合は、上の2つとは別の扱いにする。**
  伏せるべき名前が存在しないので、所在地を丸める理由もない。

  | 一次情報の側は | 名前 | 所在地 | `party_kind` |
  |---|---|---|---|
  | 法人名を載せている | 出す | 地番まで | `corp` |
  | 個人名を載せている（法人と確かめられない場合を含む） | `個人` | **町丁目まで** | `individual` |
  | **そもそも名前を載せていない** | 空 | **地番まで** | `undisclosed` |

  3行目は、公有地の売却で落札者の列がない表、競売・公売の物件など。
  こちらが名前を持っていないので「個人と地番の組み合わせ」を作りようがない。
  ただし**地番を出してよいのは、その所在地が一次情報の側で公表されているときだけ。**
  別のソースから補ったり、推測で地番を足したりしない。

- **`undisclosed` を名乗れるのは、名前の欄が無いことを確かめたときだけ。**

  「名前が無い」には2つある。取り違えると、**こちらの解析の穴が、そのまま
  地番の公開になる。** 名前が空になった理由を、必ずどちらかに決める。

  | | 名前が空な理由 | `party_kind` | 所在地 |
  |---|---|---|---|
  | 相手が載せていない | 一次情報に欄が無い（**確認ずみ**） | `undisclosed` | 地番まで |
  | こちらが読めていない | 欄はあるが読み落としている | `individual` | **町丁目まで** |

  確かめ方は、**名前の欄があるかどうかを出どころごとに1回調べて、その結果を
  記録に残す**こと。調べていない出どころは `individual` から始める。
  `undisclosed` は、調べたあとで初めて名乗れる。
  「法人か確かめられないときは個人として扱う」と同じで、**わからない側は安全な側に倒す。**

  実際に踏んだ例：近畿財務局の結果表で、契約相手方の列を読み落としていた。
  名前が空になったので `undisclosed` に見え、**個人121件の地番が出ていた。**
  欄はあった。こちらが読んでいなかっただけだった。
- **画面に出す表示と、`index.json` に入れる値は分ける。**
  - 画面は `個人` と書く。空欄だと「取れなかった」のか「個人だから伏せた」のかが
    読者に分からない。伏せたことは伏せたと書く。
  - `index.json` は**空文字**。機械が読むデータに `個人` という文字列を入れると、
    全国の別人が同じ名前として扱われ、横断ハブで混ざる。
  - 伏せたことは `party_kind` で機械に伝える（5節・6節）。
- 地番と氏名の両方を落とす必要はない。**片方でよい。** 両方落とすと値打ちが消える。
- 人が住んでいる可能性があるものは、**個票として扱わない**
  （競売・公売の入札中物件、居住用途の建物、住居系用途地域）。
  個票とは、住所や物件が特定できる形で1件ずつ残すもの。

  **判定の仕方**（開発系が実装して分かったこと。2026-09-18）：

  - 拾う言葉は「居宅」だけでは足りない。**共同住宅・マンション・アパート・
    長屋・寄宿舎・寮・社宅・戸建**、区分所有らしい部屋番号、住居系用途地域
  - **行ではなく、表の単位で落とす場面がある。** 見出しに `専有` `区分所有`
    `建物` があれば「住戸が混ざる表」と見て、住まいでないと言い切れない行も
    落とす。ある市の結果表は「地積 / 専有面積(㎡)」という**1列に土地と
    マンションの一室を混ぜていた**。行だけ見ても分からない
  - **判定できないものは、落とす側に倒す**（3.1 の `undisclosed` と同じ考え）
  - ただし落としすぎない。「◯番街区」は住居表示の街区であって部屋番号ではない。
    ここまで落とすと**土地が1件も残らなくなる**。**落としすぎていないかを測り、
    テストで固定する**
  - **行は消さず、落とした理由を残す。** 集計には数えるので、
    「個票にしない」という印を立てるだけにする

  **復号や様式変更の前に、この判定を先に入れる。** あとから入れると、
  一度は出てしまう。開発系は文字コードを直す前に間に合わせた（同日）。

  **集計に数えるのは構わない。** 恒久的に固定してはいけないのは「住所」であって
  「件数」ではない。「西宮市で今月 戸建て12件が入札に出た」には、誰の家かを
  示す情報がない。むしろ件数は景気の指標として値打ちがある。

  ただし集計にするときは：
  - 3.2 の小母数のルールがそのまま効く（1〜2件は `1-2` とまとめる）
  - 「入札中」と「売却済み」を同じ升に混ぜない。`kind` を分ける
  - 数えるのは**その月に新しく出た件数**（フロー）。「いま入札中の件数」（ストック）に
    すると、同じ物件を翌月また数えてしまう
  - 一覧は上書きされるので、取得のたびにスナップショットを残す。
    残さないと差分が取れず、フローが数えられない

### 3.2 小さい母数を出さない

件数1件は統計ではなく事故。小さな自治体や町丁目では、1件が個人の特定につながる。

- 集計の升（市区町村 × 種別 × 月など）の件数が **1〜2件のときは `1-2` とまとめ**、実数を出さない。
- 率（人口千人あたりなど）は、**人口500人未満**または**件数が1件か2件**のとき計算しない。
  値を `null` にして、伏せたことがわかるフラグを立てる。
  **0件のときは率も `0` を出す。** 率を伏せるのは「率 × 人口」で件数が戻るからで、
  0件は件数そのものを `0` と出しているので戻るものが無い。ここを「2件以下」と
  書いていたため、0件の升が率の地図で「率を出していない」灰色に落ち、
  次の節の「いちばん薄い階級の色」にならなかった（街頭窃盗統計が実物で見つけた）。
- 粒度の下限は **市区町村**（街頭窃盗統計のみ町丁目まで）。
  町丁目より細かく（学区・地番）は下りない。期間は月単位以上。

### 伏せた升は、引き算で戻せることがある

1〜2件を `1-2` と伏せても、**同じものを2つの粗さで出していると、
引き算で正確な値が分かってしまう。**

```
  尼崎市 × ひったくり × 2020年 の合計       15 件（出している）
  その市の町丁目の升                      2 ＋ 4 ＋ 1-2 ＋ 6 ＋ 1 …
                                               ↑ 伏せたのはこの1つだけ

  15 −（2＋4＋6＋1＋…）＝ 2      ← 伏せた升の正確な値が出る
```

伏せた意味が消える。1件なのか2件なのかまで分かってしまう。
3.2 が守ろうとしたのは、まさにそこ。

- **伏せた升が、そのまとまりの中でちょうど1つになったら、もう1つ伏せる。**
  まとまりとは、同じ親の升を共有する子の升の集まり
  （「市区町村 × 手口 × 年」に属する町丁目の升、など）。
  2つめに伏せるのは、残りのうち**いちばん件数が小さい升**。
  失う情報がいちばん少ない。
- **逆向きにも効く。** 親の升を伏せたのに子を全部出していたら、足し算で
  親が分かる。親を伏せたなら、子も同じまとまりで2つ以上伏せる。
- いちばん簡単なのは、**両方の粗さを出さないこと。**
  迷ったら細かいほうだけ出す。粗いほうは読者が足せばよい。

### 合計の升と、内訳の升を、両方出さない

上の「両方の粗さを出さない」を、親子のある種別に当てはめたもの。
競売統計が実物で見つけた（2026-09-16）。

「公告」とその内訳の「公告-新規」を両方の升で出すと、2つのことが同時に起きる。

1. **読者が足すと二重に数える。** 新規は公告の内数なので、
   升を全部足した数が、本当の件数より多くなる
2. **引き算で伏せた升が戻る。** 公告6 − 公告-新規5 = 1 で、
   出していないはずの再公告が1件だと分かる

どちらも直し方は同じ。

- **合計（親）の升は出さない。内訳（子）の升だけを出す。**
  合計が要る読者は、子を足せばよい
- **内訳は全部出す。1つでも欠けさせない。**
  欠けると、それが「伏せた」のか「0件」のかが読者に分からない
- **0件の内訳も `0` と書く。** 伏せた升（`count: null`）と見た目で分ける
  （次の節と同じこと）

競売統計の `index.json` の実物（大阪市西区・2026年9月）：

```json
{"kind": "競売/公告-新規",   "count": null, "count_label": "1-2"}
{"kind": "競売/公告-再公告", "count": 0,    "count_label": "0"}
```

「競売/公告」という合計の升は出していない。この形にすると、
升を全部足した数が本当の件数に合い（伏せ字のぶんは1〜2の幅）、
引き算で戻せる升も無くなる。

種別が互いに排他なら（大型店日報の新設・廃止・承継・変更のように）、
そもそも親子が無いので考えなくてよい。親子があるのは、
「全体」と「そのうち○○」を両方出したくなったときだけ。

### 伏せた升と、本当に0件の升は、見た目で分ける

地図でどちらも同じ灰色にすると、読者は「ここでは起きていない」と読む。
伏せたのは「起きていない」ではなく「言わない」。逆の意味に読まれる。

| | 見せ方 |
|---|---|
| 0 件 | いちばん薄い階級の色 |
| 伏せた升 | 階級とは別の見た目（斜線など）＋ 凡例に「1〜2件」 |

`index.json` でも同じ。`count` が `null`（伏せた）と `0`（本当に0件）を
必ず書き分ける。片方に寄せない。

### 数字を書かなくても、目で読める形は数字を出している

伏せ字は数字の欄だけに掛けても足りない。横棒の幅・地図の色・階級の境・
並び順・位置は、読者が目で読める数字そのもの。特に2つが危ない。

- **最大値で正規化しない。** 横棒の幅を「その値 ÷ その表の最大値」で出すと、
  最大値はどこかの升の実数なので、幅に掛けるだけで伏せた升が戻る。
  分母は升の実数ではなく固定の目盛りにし、伏せた升は棒を出さない
  （本当の0件と同じ見た目になる。数字のほうで「1-2」と「0」を書き分ける）。
- **階級の境を、伏せる範囲の中に通さない。** 1〜2件を伏せるなら階級の下端は
  3から始める。境が2にあると1件と2件が別の色に落ち、画面が「1-2」と書いた
  真横で、色と凡例が1か2かを答える。

率にも効く。全体の平均を細かく出すと、率 × 人口 で全体の合計（＝升の親）が戻る。
伏せた子が k 個あるなら、丸めの幅が k 件ぶん以上になるところまで桁を落とす。
桁を落としきって0になるなら、値を出さない。

凡例（単年）。階級の境の入れ方：

    直す前    0 ／ 1 ／ 2〜3 ／ 4〜7 ／ 8〜        ← 「1」が階級名として出ていた
    直したあと 0 ／ 3〜4 ／ 5〜7 ／ 8〜11 ／ 12〜   ＋ 斜線で「1〜2件」

横棒（値は架空。下の節の理由で、実物は書かない）：

    直す前    <td class="v num">1-2件</td><td class="barcell"><i style="width:N%"></i></td>
              幅は「その値 ÷ その表の最大値」。最大値は同じ表に出ているので、
              掛け算1つで伏せた升の実数が戻る
    直したあと <td class="v num">1-2件</td><td class="barcell"></td>

数字の欄だけを見ていたときは、街頭窃盗統計で横棒3,216本と色の階級2組が
実数を答えていた（2026-09-16）。

### 「引き算で戻る升 0」だけでは足りない。余裕も出す

戻る升を数えて0になっても、それは**いまのデータでぎりぎり成り立っている
だけ**かもしれない。区画の数が減る、件数が増えて伏せる升が減る、年が1つ増える、
どれでも同じ作りのまま戻るようになる。

だから「0件」という結果だけでなく、**どれだけ余裕があるか**も毎回出す。

まとまりごとに、伏せた升の数 `k` と、そのうち2件だった升の数 `m` を見る。
親の合計から引けば伏せた升の和が出るので、**`m` は確定すると思ってよい。**
守っているのは和ではなく「**どの `m` 個が2件か**」の組合せのほうで、
その数が `C(k, m)` 通りある。

    余裕 = min(m, k − m)

`m` が 0 か `k` に張り付くほど組合せが減り、張り付けば升が特定できる。
だから両端からの距離の小さいほうを見る。**`k` が1なら、和が分かった時点で確定する。**

**この文書に実測の値は書かない**（9節「実測値を説明文に書かない」）。
測った結果は各サイトの決定ログに置く。街頭窃盗統計が実測した（2026-09-17）。

分かったのは、**同じ作りのまま区画の少ない市に広げると、特定できるまとまりが
出る**ということ。「戻る升0」は、区画の多い市だから成り立っていた。

年や市を足す手順に、この測定を組み込む。足してから測るのではなく、
**足す前に測って、余裕が足りなければ層の作りを変える。**

### 食い違いは、守りではなく徴候

同じ升を拘束する経路が2つ以上あって、互いに矛盾することがある。
このとき「**解が0個だから戻らない**」と読んではいけない。

攻撃する側は、**全部の経路を連立させる必要がない。**
矛盾に気づいたら、信頼できる1本を選べばよい。
矛盾は、その1本が使えることを否定しない。

守っているのは矛盾ではなく、**その経路にある未公開の項のほう**である。
（伏せた升の和の幅より大きい、時刻の読めない行の数など）
**どの項が守っているのかを名指しできないなら、守れているか分かっていない。**

同じ日に、街頭窃盗統計が両方向で踏んだ（2026-09-17）。

- 朝：解が1通りに決まったので「戻る」と報告した
  → 制約のほうが矛盾していて、その1通りは真値ではなかった
- 夕：解が0個になったので「戻らない」と報告した
  → 経路を1本外せば解は存在した

**どちらも「複数の経路が食い違っている」という一つの事実の、別の顔。**
食い違いを見つけたら、守りが増えたのではなく、**どこかの数え方が違うという
徴候**として扱う。

### 伏せ方を説明する文書に、実物の値を書かない

この共通仕様も公開している。伏せ方の例に実物の升を使うと、
**説明そのものが伏せ字を破る。**

この文書が実際に踏んだ（2026-09-17、街頭窃盗統計が見つけた）。
上の横棒の例に、町丁目の名前と、実物の幅と、その表の実物の最大値を並べて書いた。
3つそろうと掛け算1つで伏せたはずの実数が出る。それを public なリポジトリに置いていた。

- 例に使う値は**架空のもの**にする
- 仕組みの説明に実物の形が要るときは、**場所の名前を出さない**
- 「直す前／直したあと」を並べるときは、**直す前の側に実物を書かない**
  （直す前こそが、伏せられていない側だから）
- 割合・件数の総数（「横棒3,216本」など）はよい。1つの升を指さない

サイトの側の報告書（`data/parse-unknown.md` など）も同じ。公開するものは全部。

### ほとんどが伏せ字になる層は、出し方を考える

ある手口の升の大半が実数で出せないなら、その層は地図としてほぼ空になる。
空の地図は「この街では起きていない」と読まれる。
件数の少ない手口は、**期間を長くまとめる**か、**粒度を市区町村に上げる**か、
**種別をまとめる**（次の節）か、**その層は出さない**かのどれかにする。
伏せ字だらけの地図は出さない。

判定は「伏せ字の割合」ではなく **「実数が出せた升の割合」** で見る。
街頭窃盗統計のひったくりは、伏せ字は 12.7% しかない。残りの 86.6% は
本当に0件で、実数が出せた升は 0.7% しかなかった。「伏せ字が多い層」で
機械判定すると、7手口すべてがすり抜ける（2026-09-16、実測）。

### 件数の少ない種別は、まとめて1つの層にする

上の4つめ。期間を長くまとめても粒度を上げても足りず、かといって落とすと
読者が困る種別は、**近い種別どうしをまとめて1つの層にする。** 層が減るぶん
1つあたりの件数が増え、実数で出せる升が増える。
層を減らしながら読める量が増えるのは、この選び方だけ。

- まとめるのは、読者が同じ文脈で読む種別だけ。意味の遠いものを足すと、
  数は増えても読めない数字になる
- **まとめたら、細かいほうは出さない。** 束ねた層と、その中の種別ごとの升を
  両方出すと引き算で戻る（「合計の升と、内訳の升を、両方出さない」と同じこと）
- まとめても伏せ字だらけのままの種別は、粒度を上げるか、その層は出さない
- 種別ごとに層を選んでよい。全部を同じ粒度にそろえる必要はない

街頭窃盗統計の実物（兵庫県・8年・849町丁目。実数を出せた区画の割合）：

    まとめる前   車上ねらい 47.1% ／ 部品ねらい 27.6%
                 オートバイ盗 21.2% ／ 自動車盗 2.9%
    まとめたあと 「車・バイク」の1層で 69.7%

    ひったくり 0.7% と 自動販売機ねらい 6.7% は、まとめても足りないので
    市区町村に上げた（町丁目では出さない）

ひったくりは8年＝県警が配布している全期間で、「期間を長くまとめる」は
最初から使えなかった。3つでは足りない場面が実物にある。

### 粗さが混ざるファイルは、升ごとの手当てでは直らない。置き場所で分ける

3.2 の決まりは升1つ1つに掛かる（親を出さない・兄弟をそろえる・1〜2件は伏せる）。
**それだけでは足りない場面がある。**

競売統計の集計ファイルが、**同じ数を5つの粗さで数えていた**
（裁判所／庁×月／庁×年／府県×月／府県×月×種別）。
升1つ1つは 3.2 を守っていたのに、**粗いほうを伏せても細かいほうを足せば戻った。**
言い換えの経路を1つずつ塞ごうとしたが塞ぎきれない。
かといって粗さを1つに減らすと、このファイルの用途
（どの粗さで出すかを後で選べるように並べておく）が無くなる。

**守れていないのはファイル全体のほうで、升ごとの手当てでは直らない。**
だから置き場所で分ける。

    data/agg/     社内用。粗さが混ざっている。**公開しない**
    data/public/  **ここだけが公開用。** 1つの粗さだけを選んで写す

守らせ方は3つ。どれか1つでは足りない。

- 社内用のファイルに「公開しない」の欄を必ず入れる（文言は1か所から配る）
- 走らせた記録（`data/*.md`）は先頭に1行
- テストが見張る（社内用は全部その欄を持つ／公開用は持たない／
  公開用に見覚えのないファイルが増えていない）

**「何を伏せるか」ではなく「どれを公開するか」に問いを変える。**
許可リストのほうが、除外リストより強い（9節）。

### 中途半端に伏せるくらいなら、伏せない

競売統計が、伏せた升の**2行下に同じ数を実数で書いていた**
（`合計.◯◯まで進んだ回 = null` の下に、同じ数を指す別の欄）。

守れていないうえに、**「伏せてある」という誤った安心を作る。**
読む人も、次に直す人も、そこは守られていると思って通り過ぎる。
**伏せ忘れより悪い。** 伏せ忘れは検査が見つけるが、こちらは見つけない。

伏せきれないなら、伏せる振りをやめて、**出さない側に寄せる。**
上の節の「置き場所で分ける」のほうが強い。

### 3.3 評価しない

事実と、事実から機械的に出る数字だけを出す。

- 点数・順位・格付け・「安全」「危険」「おすすめ」「ワースト」は出さない。
- 地図の色分けを **分位（quantile）で切らない。** 分位は順位そのもの。
  必ず**固定の絶対値**で階級を切る。
- 誤読されやすい数字には、必ずその場に注記を添える
  （例：認知件数は通報されたものだけ／夜間人口を分母にしているので商業地は大きく出る）。

### 3.4 取得の作法

**断られたら、そこで打ち切る。回り込まない。**

- `robots.txt` が拒否していたら取りに行かない。人の手か、別の正規ルートに回す。
- 同時接続は **1本**。リクエスト間隔は **5秒以上**。
- `429` / `503` / 待機列が返ったら、**押し込まずにその回は中止**して次回に回す。リトライで突破しない。
- User-Agent に連絡先を入れる：

  ```
  kujiraya archive bot (+<サイトのaboutページURL>; <連絡フォームURL>)
  ```

  サイトがまだ公開されていないうちは、**404 になる URL を入れない。**
  確認できない名乗りは、名乗らないより不審に見える。
  about ページができるまでは、屋号・サイト名・連絡フォームの URL だけにする：

  ```
  kujiraya archive bot (keibai-data; https://forms.gle/xxxxx)
  ```

  URL は設定の1か所にだけ書き、公開したら about ページの URL に差し替える。

- **頻度は「中身の変わり方」と「相手が誰か」の両方で決める。**
  - 公報・告示など、発行されたら中身が変わらないもの → **月2回**
  - 縦覧一覧など、日々書き換わるもの → 毎日
  - 「掲載期間が3か月」なら、必要なのは「3か月以内に1回」であって毎日ではない。
  - **過去分の取り込み（積み直し）は例外。** 1日の上限（大型店日報の兵庫県公報は80号）・
    5秒・同時1本を守れば毎日でよい。追いついたら（未読が新着だけになったら）月2回に戻す。
    戻すのは人の手ではなくコードで（大型店日報は `koho_pdf.py` が未読20号以下になったら
    自動的に1日・15日だけにする。手で押したときは日に関係なく取りに行く）

  ただしこれは**自治体のサーバーに対する決まり**。
  姉妹サイトが GitHub に置いた生データを読むときは、**毎日でよい**。
  相手が違うし（GitHub は大量アクセスを前提にした置き場）、
  上流が毎日更新しているので、月2回にすると新着がそのぶん遅れるだけになる。
  「公報だから月2回」ではなく「兵庫県のサーバーだから月2回」と考える。

- **同じ一次情報を、2つのサイトが別々に取りに行かない。取得は1系統にする。**
  すでに姉妹サイトが取っているものは、そのサイトが公開している生データを読む。
  相手のサーバーへのアクセスが2倍になるのは、単純に失礼。

  | 一次情報 | 取っているサイト | 読み方 |
  |---|---|---|
  | 兵庫県公報（全文・2007年〜。号外を含む） | 大型店日報 | `https://raw.githubusercontent.com/VirgoB77/ogataten-nippo/main/data/koho/full/<日付>-<号>.txt.gz`（gzip。号外は `<日付>-g<n>.txt.gz`：「号外」が g1、「第2号外」が g2。号の一覧は同じリポジトリの `data/koho/issues.json`） |

  共有する側は、**抜き出したあとの形ではなく全文を残す。**
  抜粋だけ残すと、あとから別の告示が要るようになったときに全部取り直しになる。
  大型店日報が実際にこれをやってしまい、737号を取り直すことになった。

  新しく共有できるものができたら、この表に足す。

- `robots.txt` はクローラへのお願いであって、**正規の提供ルートを塞ぐものではない。**
  有償頒布（定期購読）、データ提供の申し出、情報公開請求、国立国会図書館 WARP など、
  正面から取れる道がないか先に調べる。購読できるなら、こちらはクローラではなく購読者になる。

- 人の手に回す工程を作るときは、**機械に催促させる**。人は必ず忘れる。
  - 人に渡すのは「該当する号のURLだけ」。全件を人に見せない。
  - 毎回のレポートに不足分を出し続ける（例：`2026年3月：第12号・第15号が未取得`）。
  - 掲載期限が近いものを警告する（例：`第12号はあと21日で閲覧できなくなります`）。
  - 取り込み済みは台帳に記録し、二度と催促しない。

### 3.5 出典

- **全レコードに `source_url` と `fetched_on` を必ず付ける。** 例外なし。
- 取得先ごとに利用規約を個別に読み、出典表記の指定を `sources.json` に記録する。
- 公報の告示・公告は、著作権法13条により著作物にならない。いちばん安全な一次情報。
- 「政府標準利用規約2.0」は CC BY 4.0 と互換。出典表記をすれば使える。

### 終わった・消えたを記録する

一次情報は消える。役所の縦覧は数か月で消え、補助金の受付は予算が尽きると
締め切られ、公告は年度で書き換わる。**こちらのサイトは消えない。**
だから「まだ生きているか」は、こちらが記録しなければ誰にも言えなくなる。

3つの欄を持つ。使わない欄は `null`。

    closed_on        公表された終了日（公表されているなら。なければ null）
    last_seen_open   まだ続いていると確認できた最後の日
    closed_detected  終わったと分かった日

**`closed_detected` に公表日を入れない。** 1つの欄に2つの意味が混ざり、
あとから見て「終わった日」なのか「気づいた日」なのか分からなくなる。
`as_of` と `fetched_on` で一度踏んだのと同じ形。
公表された終了日は**あとで変わる**（延長・前倒し）ので、別の欄に持たないと
変更を追えない。

#### 終了は点ではなく、区間

毎日見ていなければ、`closed_detected` は「最後に見た日」でしかない。
月1回なら、実際に終わったのは最大1か月前。

    last_seen_open   2026-08-20   この日はまだ続いていた
    closed_detected  2026-09-17   この日に終わったと分かった
    → 終わったのは 8/20 〜 9/17 のあいだ

**終了日が公表されるものでも、区間を捨てない。** 捨てると「予定どおり
終わったか」を確かめる手立てが無くなる。開札日が延期されることは実際にある。

#### 区間の幅は、こちらの弱点の数字でもある

幅は巡回の間隔で決まる。読む人は粒度を知る権利があるので、**出す**
（`fetched_on` を必須にしているのと同じ理屈）。

そのうえで、**幅が広がっていたら巡回が止まっている**と先に分かる。
毎日回していれば幅は1日のはず。3か月に広がっていたら、その数字が教えてくれる。
3.2 の「余裕も出す」と同じ形。**数字を出しておくと、細ったときに気づける。**

#### 根拠のページは、あとで消える

「どのページのどの文言か」を残すのは正しい。ただし**根拠として指している
ページが、次の年度に書き換わる。** URL と文言だけでは1年後に確かめられない。

**検知した時点のページの写しを取る**（9節「生データを全部残す」）。
文言はそこから引く。府のページが更新されて以前の記述を示せなくなったことが
実際にあった。**写しを取っていた分だけが残っている。**

#### 削除される場合のほうが危ない

「令和◯年度の受付は終了しました」と1行残す役所と、**ページごと消える**役所がある。
後者では、**写しが唯一の記録になる。** そして写しは「消える前」に取れていないと
意味がない。**巡回の頻度が、そのまま記録の完全性になる。**

頻度は上げるより下げるほうが安全なので、**最初から短い間隔で始める。**
月1で始めて後から毎日にしても、その間に消えた分は取り戻せない。

## 4. `common/addr.py`

住所を4サイトで突き合わせるための正規化。**Python標準ライブラリのみ**で書く。
ファイル1本で完結させ、各リポジトリにコピーして使う（submodule も pip も使わない）。
先頭に「正本は ogataten-nippo/docs/kyotsu-shiyo.md」とコメントを書く。

### 関数

```python
def normalize(pref: str, city: str, addr: str) -> dict:
    """住所を正規化して、突き合わせ用のキーを返す。"""
```

戻り値：

| キー | 例 | 説明 |
|---|---|---|
| `pref` | `"大阪府"` | 都道府県名 |
| `city` | `"大阪市北区"` | 市区町村名 |
| `city_code` | `"27127"` | 全国地方公共団体コード5桁。総務省の一覧を `ref_jis.py` が `data/ref/jis-codes.json` に取る（90日に1回）。記憶で書かない |
| `town` | `"梅田1"` | 町丁目。**丁目を含む** |
| `addr` | `"大阪市北区梅田1-1-1"` | 整形後の表示用住所 |
| `addr_key` | `"27127\|梅田1-1-1"` | 番地までの突き合わせキー |
| `addr_key_town` | `"27127\|梅田1"` | 町丁目までの突き合わせキー |

### 引数の `addr` と、戻り値の `addr` は別のもの

同じ名前だが、入りと出では指すものが違う。

- **引数の `addr`** は「市区町村より後ろ」を想定する。ただし役所の表は
  「所在地」の1列に都道府県名や市区町村名ごと入れていることがある。
  **先頭に付いていたら落とす**（`city` と重複させないため）。
  政令市の区も見る。`city` が `"堺市西区"` なら、`"西区"` だけの先頭一致も落とす
- **戻り値の `addr`** は**表示用で、市区町村名を含む**（`"大阪市北区梅田1-1-1"`）。
  落とした市区町村名を `city` から足し直した形。そのまま画面に出せる

実装はそうなっていたが、**この文書に書いていなかった**（2026-09-18 に開発系が
「4節の `addr` に市区町村名を含むのか」と聞いてきて分かった）。

### `town` の決め方

**「最初のハイフンより前」では決まらない。** 文字列だけでは原理的に区別できない
ケースがあるので、2段階にする。

```
梅田1-1-1       の最初の 1  = 丁目        → town は 梅田1
上ケ原2番町3-5   の 3        = 番地の始まり → town は 上ケ原2番町
```

どちらも「町名のあとの数字」で、見た目では区別がつかない。

**① 正規化で自分がハイフンにした場所があれば、その手前まで（確実）**

`丁目` `番地` `番` `号` をハイフンに置き換えたとき、**どこを置き換えたかは自分が
知っている**。最初に置き換えた場所の手前が `town`。

```
梅田一丁目1番1号 → 梅田1-1-1     「丁目」を置き換えた → town は 梅田1
潮江1丁目3番1号  → 潮江1-3-1     同上                → town は 潮江1
```

日本の住所のほとんどはこれで決まる。入力にもとからあったハイフンと
取り違えないこと。**置き換えた位置を覚えておく**のがこつ。

**② 1つも置き換えなかったときは、町丁目の一覧で最長一致**

`上ケ原二番町3-5` は「番」の直後が「町」なので、1つも置き換えが起きない。
この形は文字列だけでは決められないので、**市区町村コードごとの町丁目の一覧**を
引いて、いちばん長く一致する町名を採る。

一覧は `data/` に同梱する（`city_code` の一覧と同じ扱い）。
出どころは国土交通省の位置参照情報（大字・町丁目レベル）などを調べて決める。
大阪府・兵庫県だけなら1万件ほどで、数百KBに収まる。

**③ ①でも②でも決まらないときは、`addr_key_town` を空にして記録する**

推測で埋めない。空文字にして `data/parse-unknown.md` に出す（9節）。
黙って間違えた町丁目でつなぐと、**別の場所の記録が混ざる**。
空なら「つながらなかった」と分かるだけで済む。

**丁目は必ず含める。** 「梅田」でまとめてはいけない。

- 犯罪統計マップは丁目ごとに数える。警察のオープンデータも国勢調査の人口も丁目単位。
  「梅田」でまとめると、件数も人口も3つの丁目が混ざって意味をなさない
- 大阪市北区梅田は1〜3丁目あり、駅の北と南ほど違う場所になる
- そもそも「町丁目」という言葉が「丁目まで」を指す

### 正規化のルール

1. 全角英数 → 半角
2. 漢数字 → 算用数字（`一丁目` → `1丁目`）
3. `丁目` `番地` `番` `号` → ハイフン。
   ただし **直後が数字か、文字列の終わりのときだけ。**
   素朴に全部を置き換えると町名が壊れる：

   ```
   上ケ原2番町3-5  →  上ケ原2-町3-5   ← 「番町」の番まで置き換えてしまう
   上ケ原2番町3-5  →  上ケ原2番町3-5   ← 直後が「町」なので置き換えない（正しい）
   梅田1丁目1番1号  →  梅田1-1-1
   ```
4. `大字` `字` を除去
5. 空白を除去
6. 建物名・部屋番号は `addr` には残し、`addr_key` からは除く

### なぜキーが2本あるか

出せる精度がサイトによって違う。

- 犯罪統計マップは町丁目までしか持たない
- 公有地売却・競売の跡地は、買主が個人なら町丁目までに丸める（3.1）
- 大型店日報・開発許可は番地まで持つ

精度の違うもの同士は `addr_key_town` で突き合わせる。
**両方のキーを必ず出す**こと。片方しか作れない場合は、もう片方を空文字にする。

### テスト

`tests/` に単体テストを置き、**ワークフローの最初のステップで走らせる**。
落ちたらそこで止まり、取りに行かない。最低限これは通すこと：

期待値は**必ず具体的に書く。** 「キーが両方出ること」のような書き方だと、
食い違いが見つからない。

```
normalize("大阪府", "大阪市北区", "梅田一丁目１番１号")
  addr           "大阪市北区梅田1-1-1"
  town           "梅田1"
  addr_key       "27127|梅田1-1-1"
  addr_key_town  "27127|梅田1"          ← 丁目を含む

normalize("兵庫県", "尼崎市", "潮江1丁目3番1号")
  addr_key       "28202|潮江1-3-1"
  addr_key_town  "28202|潮江1"

normalize("兵庫県", "西宮市", "大字上ケ原　二番町3-5")
  addr_key       "28204|上ケ原2番町3-5"   ← 「番町」の番を置き換えない
  addr_key_town  "28204|上ケ原2番町"      ← ②の町丁目一覧で決まる
                                          一覧が無いうちは空文字にして記録する（③）
```

1件目・2件目は①で決まる。3件目は②が要る。
**一覧をまだ持っていない間は、3件目の `addr_key_town` は空文字が正しい。**
「上ケ原2番町3」のように途中で切ったものを入れてはいけない。

**出力する値は必ずここを通す。** 通さない経路を作らない。

  個人と取り違えない。

| 実物 | 正体 | どうする |
|---|---|---|
| `未定` `（未定）` `未定３者` `物品販売業を営む店舗` `―` | 名前ではない文言 | **そのまま出す。**「個人」に変えない |
| `大阪市北区角田町３番25号` | **列がずれて住所が入った** | 個人として扱う（安全側）。`parse-unknown.md` に出す |
| `三井住友ファイナンス` `大和ハウスリアルティ` | 法人名が**途中で切れた** | 個人として扱う（安全側）。ただし**置き換えや削除はしない** |

3行目は見分けがつく。**同じデータの中の別の名前の、先頭部分になっていたら、
それは切れた法人名であって人名ではない**（`三井住友ファイナンス` は
`三井住友ファイナンス＆リース株式会社` の頭）。
人名は、ほかの名前の頭にはならない。

これを見落として履歴から `三井住友ファイナンス` を消すと、
`＆リース株式会社` だけが残る。消す作業をするときは必ず先に調べること。

**テストで守る。** `privacy.py` を迂回した出力が1件でもあれば落ちる検査を書く
（例：出力JSON全体を走査して、個人名らしき値・伏せるべき率が残っていないか確認する）。
壊れたら、データを取りに行く前に止まる。

## 6. `index.json`

各サイトがサイトルートに出す、横断用のインデックス。
将来の横断ハブがこれを読んで、住所ごとの年表ページを作る。

### 住所ごとの年表に乗らないサイトは、`index.json` を出さない

`index.json` は **同じ住所を鍵にしてサイトを横断する**ための仕組み。
鍵が住所でないサイトは、この年表に乗らない。

| 鍵 | サイト | 横断ハブ |
|---|---|---|
| **住所** | 大型店日報・開発系・競売統計・街頭窃盗統計・民泊 | 乗る |
| **制度** | 住宅系補助金の自治体横断 | **乗らない** |
| **日付** | 補助金の予算消化率 | **乗らない** |

補助金の制度は、**土地ではなく人と世帯に紐づく。**
「この住所で何があったか」という問いに答えない。

**空の `index.json` を置かない。** 置くと、読む側が
「**まだ作っていない**」のか「**そもそも乗らない**」のかを見分けられない。
出さないほうが正直で、読む側も迷わない。
**出さない理由を README に1行書く**（何も言わずに無いのと、決めて無いのは違う）。


```jsonc
{
  "site": "ogataten-nippo",
  "site_name": "大型店日報",
  "generated_at": "2026-09-14",
  "records": [
    {
      "id":         "ogataten:osaka-pref:2026-09-01:0001",
      "title":      "イオンモール○○ 新設届出",
      "kind":       "大店立地法/新設",
      "date":       "2026-09-01",
      "pref":       "大阪府",
      "city":       "大阪市北区",
      "city_code":  "27127",
      "addr":       "大阪市北区梅田1-1-1",
      "addr_key":      "27127|梅田1-1-1",
      "addr_key_town": "27127|梅田1",
      "party":      "イオンモール株式会社",
      "party_kind": "corp",
      "url":        "https://ogataten-nippo.com/s/xxxx.html",
      "source_url": "https://...",
      "fetched_on": "2026-09-01"
    }
  ],
  "counts_by_city": [
    {
      "city_code":   "27127",
      "city":        "大阪市北区",
      "kind":        "大店立地法/新設",
      "period":      "2026-09",
      "count":       12,
      "count_label": "12"
    },
    {
      "city_code":   "28204",
      "city":        "明石市",
      "kind":        "大店立地法/新設",
      "period":      "2026-09",
      "count":       null,
      "count_label": "1-2"
    }
  ]
}
```

### 決まり

- `id` は `<site>:<source>:<date>:<連番>` の形。サイトをまたいで衝突しないこと。
  連番は日をまたいで安定しないので、届出ごとの安定した鍵（大型店日報は `key`）を
  連番の代わりに使ってよい。同じ届出は毎日同じ `id` になること。
- `kind` は `<制度>/<種別>` の形（`大店立地法/新設`、`開発許可/29条`、`公有地売却/落札`、`犯罪統計/侵入盗`）。
- `party` は**法人名のみ**。個人は**空文字**（`個人` という文字列を入れない）。
  `privacy.py` の `party_for_index()` を通した値を入れる。画面表示用の
  `redact_name()`（個人を `個人` と書くほう）と混ぜないこと。理由は 3.1。
- `party_kind` は `"corp"` / `"individual"` / `"undisclosed"` / `"none"` のいずれか。
  `party` が空のとき、その理由を機械が区別できるようにするために要る。

  | 値 | `party` が空な理由 | `addr` の粒度 |
  |---|---|---|
  | `corp` | （空でない） | 地番まで |
  | `individual` | 個人なので伏せた | 町丁目まで |
  | `undisclosed` | 一次情報の側が名前を載せていない | 地番まで |
  | `none` | そもそも当事者を持たない制度 | 地番まで |

  横断ハブで「法人が買った跡地」を絞るとき、`undisclosed` を `individual` に混ぜると
  取りこぼし、`none` に混ぜると意味が壊れる。4 つを分けること。
- `url` は**絶対URL**。相対パスにしない。
- `source_url` と `fetched_on` は必須。空にしない。
- 値がないキーは省略せず、空文字か `null` を入れる。キーの有無で分岐させない。
- 個票を出さないサイト（競売統計）は `records` を空にして、`counts_by_city` だけを出す。
- 個票を全部出しているサイト（大型店日報）では、升の伏せは守りにならない。読む側が
  `records` を数え直せば実数が分かるからだ。それでも升の形と伏せ方は同じにそろえる
  （横断ハブが4サイトを同じ道具で読めるように）。守りとして効くのは個票を出さないサイト。
- 升の期間は、伏せ字だらけにならない粗さにする（3.2）。大型店日報は市区町村×種別×**年**。
  月にすると 3,713 升のうち 95% が `1-2` になった。月と年の両方は出さない（引き算で戻る）。

### `counts_by_city` の升

`counts_by_city` は 3.2 でいう「升」そのもの。1 要素 = 1 つの升。

- 升は **`city_code` × `kind` × `period`** で決まる。この 3 つは必須。
  この 3 本がないと、集計だけを出すサイトは「何を」「いつの」数えたのかを
  言う場所がなくなる。`records` を空にする以上、ここに書くしかない。
- `kind` は `records` と同じ `<制度>/<種別>` の形。段階で分けるなら
  `競売/公告`・`競売/売却`・`競売/不売` のように種別を段階にする。
  段階を 1 つの升に混ぜない。
- `period` は `"2026-09"`（月）か `"2024-2025"`（年の範囲）。全期間なら `"all"`。
  期間を書かない升は作らない。
- `count` と `count_label` は必ず両方入れる。3.2 の小母数はここで効く。

  | 実数 | `count` | `count_label` |
  |---|---|---|
  | 3 以上 | その数（`12`） | 同じ数の文字列（`"12"`） |
  | 1 か 2 | `null` | `"1-2"` |
  | 0 | `0` | `"0"` |

  人に見せるのは `count_label` のほう。数のまま出さないために 2 本ある。
  `count_label` だけにすると足し算ができず、`count` だけにすると
  伏せたことが `0` と見分けられなくなる。

- 升を伏せたとき `count` は `null` になる。**なぜ伏せたかで `count_label` を分ける。**

  | 伏せ方 | `count` | `count_label` | 読み方 |
  |---|---|---|---|
  | 1 か 2 | `null` | `"1-2"` | 値は 1 か 2 |
  | まとめて伏せた | `null` | `"非公開"` | **値は 1 以上。3 以上かもしれない** |

  2行目は補完的伏せ（3.2）を使ったまとまりの升。そのまとまりでは、
  1〜2件の升と、それを守るために足した3件以上の升を、**同じ札にそろえる。**
  札を分けると「どれが3件以上か」が読者に分かり、1〜2件かもしれない升の数
  （＝隠れる場所）が減るため。

  **機械は `count_label` で読み分ける。** `null` を一律に「1 か 2」と読むと取り違える。

  まとまりは、同じ市区町村・同じ種別・同じ期間でくくった升の集まり。
  その中に補完的に伏せた升が1つでもあれば、そのまとまりの伏せた升は全部 `"非公開"`。
  1つも無ければ全部 `"1-2"` のままでよい。地図の見た目も同じで、
  まとまりの中で伏せた升は全部同じ見た目にする。

- **伏せた理由を、公開する側に書かない。** 「1〜2件だから」「補完だから」の別は
  金庫側にだけ残す（3.5 の出典と同じ扱い）。`index.json` に理由の欄を足すと、
  上でそろえた意味が消える。

- **`"非公開"` は「少ない」という意味ではない、と画面に書く。**
  札をそろえると、読者は「非公開」を「1〜2件のこと」と読みかねない。
  実際には3件以上のこともある。凡例か注記で、はっきりそう書く。

  街頭窃盗統計が両方の案を測って決めた（2026-09-17）。
  849区画を N 区画ずつの塊に切って「小さい市」に見立て、補完的伏せが
  発動したまとまりを数えた。「隠れる場所」は、読者から見て
  「1〜2件かもしれない」升の数（中央値）。

  | 市の区画数 | 発動したまとまり | 隠れる場所（札を分ける） | 隠れる場所（そろえる） |
  |---:|---:|---:|---:|
  | 5 | 99 | 1 | 2 |
  | 10 | 57 | 1 | 2 |
  | 20 | 30 | 1 | 3 |
  | 40 | 8 | 2 | 3.5 |
  | 80 | 1 | 1 | 2 |

  **札を分けても升そのものは特定できない**（補完的伏せが効いているので、
  どのまとまりでも0件だった）。だが隠れる場所は半分以下になる。
  見た目の違いが、それ自体が数字になる。

  そろえる代償は、1〜2件の升が `"1-2"` と書けなくなること。
  実測で 1〜118升（市の大きさによる。区画の多い市では0）。
- 率を出す升は `rate_per_1k` を足す。3.2 で伏せたときは値を `null` にして
  `rate_suppressed: true` を立てる。分母（人口など）も `population` として書く。
- 個票も出すサイトは、`records` 側に `period` を足してよい
  （犯罪統計マップの「町丁目 × 手口 × 期間」の行など）。
  **その種別を個票の粒度で出しているなら、`counts_by_city` には出さない。**
  親と子の両方を出すことになり、引き算で伏せた子が戻る（3.2）。
  `counts_by_city` に出すのは、個票の粒度では伏せ字だらけになるので
  市区町村でしか出さないと決めた種別だけ。同じ数を2か所に書かないのは
  もちろんだが、危ないのは重複ではなく粗さの違う両方出しのほう。

## 7. 運営者情報と連絡先

4サイトで同じ文面を使う。

```
運営者　鯨屋（くじらや）
　　　　大阪府・兵庫県で行政が公開する一次情報を、消える前に記録しています。
連絡先　<訂正・削除の依頼フォームURL>（7日以内にご返信します）
```

- **氏名は載せない。屋号のみ。** 広告収入だけのサイトは通信販売ではないため、
  特定商取引法の表示義務はかからない。有料サービス・物販・有料会員を始めた時点で
  表示義務が発生するので、そのときに改める。
- 所在地（都道府県）も載せない。地域は「何を扱っているか」の側で示す。
- 連絡先は**メールアドレスの直書きではなくフォーム**を優先する。
  1本のフォームを4サイトで共用し、「対象サイト」のプルダウンで振り分ける。
- **4サイトで統一する。** 1つだけ氏名を出すと、隠しているように見えて逆効果。
- **氏名はリポジトリにも書かない。一度もコミットしない。** 個人のメールアドレスも同じ
  （**コミットの作者欄も含む**）。GitHub の Settings → Emails で「Keep my email addresses
  private」と「Block command line pushes that expose my email」を先に入れる。手元の git は
  `user.email` を `<ID>+<名前>@users.noreply.github.com` にする。
  **git の履歴はあとから消せない。** ファイルから消しても履歴から読める。
  名前は足すのは簡単で引くのは不可能だが、git ではなおさら消せない。
  だから公開用は履歴ゼロで新しく作る（9節）。

### 個人のアドレスが無いことの、確かめ方

**見る場所が2つある。同じ `grep` では両方見えない。**

```bash
# ① ファイルの中身（全履歴）
git grep -hoIE '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}' $(git rev-list --all) \
  | sort | uniq -c | sort -rn

# ② コミットの枠（作者欄・コミッタ欄）
git log --all --format='%ae%n%ce' | sort | uniq -c | sort -rn
```

**①だけ見ると「無い」、②だけ見ると「ある」。両方要る。**
競売統計で実際に起きた（2026-09-17）。運営者が確かめて
「作者は全部 noreply、ファイルの中は役所の窓口だけ」と判断したが、
**ファイルの中身は正しく、作者欄を見落としていた。**
`git grep` はコミットの枠を見ないので、片方だけ見ると「無い」と読める。

**`--all` を落とさない。** 現在の枝しか見なくなる。
**件数を出す（`uniq -c`）。** 「有無」だけだと、1件を見落としたときに気づけない。

#### 浅いクローンで確かめない

`git clone --depth 1` した置き場でこの検査を走らせると、**「無い」と嘘が出る。**
持っていない履歴は数えられない。

こちらが実際に踏んだ（同日）。浅いクローンで競売統計と開発系を測って
「どちらも0件」と報告したが、`--depth=5000` で取り直したら
23件と4件が出た。**検査そのものは正しく、置き場が浅かった。**

走らせる前に、次を見る。

```bash
git rev-list --all --count          # コミット数
test -f .git/shallow && echo 浅い    # 何も出なければ全履歴
```

**9節の「鳴らせていない見張り」と同じ話。**
道具が正しくても、当て方で黙る。

### 氏名の代わりに信用を作るもの

氏名を出さない分、こちらを厚くする。統計サイトでは実際こちらの方が効く。

1. 返信が来る窓口（7日以内と書いたら本当に返す）
2. 全レコードの出典URLと取得日
3. 訂正履歴のページ（いつ・何を・なぜ直したか）
4. データと生成コードがそのまま公開されていること

### 役所や図書館に手紙を出すとき

1対1のやりとりは、サイトに載せるのとは別。検索エンジンにも載らない。
**お願いする側が名乗らないのはバランスが悪い**ので、氏名を入れてよい。

ただし**書き方に決まりがある。**

- 下書きは `docs/letters/<相手>.md` に置く。**署名欄に氏名は書かない。**

  ```
  鯨屋（くじらや）
  ※ 送信時に運営者名を1行足す（このファイルには書かない）
  ご返信 info@ogataten-nippo.com
  サイト https://ogataten-nippo.com/about.html
  ```

- 送信のときに、**人が手で氏名を入れる。**
  フォームに「氏名」の入力欄があれば、そこに書くだけでよい。
  その場合、本文の署名は屋号のままにする（フォームの欄はリポジトリに残らない）。
- 相手のサーバーを機械で読まない相談でも、**robots.txt は必ずホスト名まで書く。**
  「どこの robots.txt か」を書かないと、相手が「うちは拒否していない」と混乱する。
- **名乗り（User-Agent）は実物をそのまま書く。** 書いたものと実物が違うのがいちばんまずい。
  書く前に必ずコードを見て確かめる。
- **確かめずに書かない。** 「唯一」「〜だけ」は、自分の調査報告と矛盾しないか見直す。
- 送ったら、ファイルの1行目を
  `YYYY-MM-DD にフォームから送信しました。` に書き換える。
  返事が来たら**同じファイルに追記**する。やりとりが1か所に残る。
- **受付番号・整理番号のたぐいは書かない。** 送信日と方法だけ書く。
  相手の窓口で状況を照会できる番号は、public になるリポジトリに残す種類のものではない。
  控えは送信完了画面のPDFなどで手元に持つ。

### 手紙で「しない」と書いたことは、あとで守る

行政は**こちらの説明を前提にデータを出す。** 黙って前提を変えるのが、
いちばんやってはいけないこと。だから、書く前に将来を狭めすぎないようにし、
書いたあとは見返す場所を決めておく。

**書くときは「現時点で」を付ける。**

```
× データそのものを販売することは考えておりません
○ 現時点で、データそのものの販売は予定しておりません
```

正直さは落ちない。相手も計画が変わることは分かっている。
言い切ると、あとで道を狭める。

**有料の何かを始めるときは、次の2つを必ず見返す。**

1. **運営者情報** — 特定商取引法の表示義務が発生する。氏名・住所・電話番号が要る
2. **`docs/letters/` の手紙** — 行政に「しない」と書いたことがないか確かめる

   破るなら、**先に相手に伝える。黙って始めない。**
   一度「しません」と言った相手に黙って始めるのは、断られるより悪い。

手紙を出したら、`docs/letters/README.md` に
「**この先、有料の何かを始めるときはここを読むこと**」と一行書いておく。
1年後の自分は、手紙のことを覚えていない。

## 8. 各サイトのページに必ず置くもの

- **このサイトについて**：何を、どこから、どの頻度で集めているか
- **免責**：元の届出・公告が変更・取下げされることがあり、実際と異なる場合がある旨
- **数字の読み方**：誤読されやすい数字には、その場に注記
- **出典と利用規約**：取得先ごとの規約と、指定された出典表記
- **訂正・削除の申し出先**：フォームURLと返信のめやす
- **最終更新日と更新頻度**
- **やらないと決めたこと**：扱わない情報と、その理由

## 9. 技術方針（共通）

- Python標準ライブラリのみ。例外を使うときは理由を README に書く
  （現在の例外：`.xls` の `xlrd`、PDFの `poppler-utils`（`pdftotext -layout`）、OCRの `tesseract`）
- GitHub Actions で定期実行、GitHub Pages で静的HTMLを配信
- ワークフローの**最初のステップでテストを走らせる**。落ちたらそこで止まり、取りに行かない
- 生データは全部保存する。**絞り込みは出力の段階だけで行う。**
  取得時点で捨てると、基準を変えたときに取り直しになる
- **HTML の表は `rowspan` / `colspan` を展開してから読む。**
  自治体の一覧表は結合セルだらけで、展開せずに読むと列がずれる。
  ずれ方が「値が空になる」ではなく「隣の列の値が入る」なので、
  面積や金額が黙って別の数字に化ける。気づきにくいので、最初から展開する。
- **知らないものを黙って捨てない。** 解析中に見たことのない見出し・列名・様式に
  出会ったら、値を `extra` に残したうえで `data/parse-unknown.md` に書き出す。
  次の実行で人が見られるようにする。

  **ただし、その記録も `privacy` を通す。** `extra` は「捨てない」ための場所だが、
  知らない列に氏名や地番が入っていることがある。**捨てない仕組みが、
  伏せる仕組みの外にあってはいけない。**
  全部を伏せるのではなく、**列名が当事者を指すときだけ例を出さない**
  （`privacy.is_party_column()` で判定する）。これで「様式が変わったことは残る／
  中身の氏名は残らない」が両立する。

  記録を公開しない置き場に置いていても同じ。**公開しないのは運用の約束で、
  コードで守られてはいない**（5節の「人の判断ではなくコードで守る」）。

  黙って捨てると、様式が変わったことに何年も気づかないまま、
  歯抜けのデータが積み上がる。落ちているものは落ちていると分かる形で残す
- **鍵には「あとから変わらない」と言い切れるものだけを入れる。**

  | 鍵に入れていい | 鍵に入れない |
  |---|---|
  | 出どころ・番号（公報番号・事件番号・物件番号） | 結果・落札金額・応札者数 |
  | 回次 | 面積・用途・価格 |
  | 段階（公告／結果／不調） | 当事者の名前 |
  | 公告日 | 取得日 |

  右の列は訂正で書き換わる。鍵に混ぜると、訂正のたびに同じものが
  新しい鍵で増え、古いほうを消す手がかりが無くなる。
  段階は値ではなく位置なので、鍵に入れてよい。

- **鍵と升は別物。鍵に入れないものを升にしてよい。**
  鍵は「同じものを二重に持たないため」、升は「数え分けるため」。目的が違う。

  結果（落札／不調）は**鍵に入れない**。値なので訂正で変わる。
  でも `counts_by_city` の `kind` には**入れてよい**。
  升は毎回まるごと数え直すので、変わっても困らない。

  | | 単位 | 結果の置き場所 |
  |---|---|---|
  | 記録（`records`） | 1回の入札 | **欄**。`結果: 不調` のように持つ |
  | 升（`counts_by_city`） | 市区町村 × `kind` × 期間 | **`kind`**。`公有地売却/不調` |

  **売れた件数は、レコードの数ではなく欄で数える。**
  結果の記録が82件あっても、61件が不調なら売れたのは21件。
  レコード数で数えると4倍に水増しされる（兵庫県の県有地売払いの実数）。

  段階の言い方は3サイトでそろえる。**予定／公告／結果** の3つ。
  「売出中」ではなく「公告」にする。他のサイトも行政が出した公告を数えているので、
  同じ言葉にしておくと横断ハブで突き合わせられる。
  不調・落札は段階ではなく、結果の欄に入れる。

- **「鍵のぶつかりが0件」は、鍵が正しい証拠にならない。**
  むしろ**壊れた鍵ほどぶつからない。** 値を鍵に混ぜていれば、値が違うだけで
  別の鍵になり、ぶつからずに静かに増える。0件を安心材料にしない。

  確かめ方は3つ。全部やる。

  1. **同じ入力を2回流して、レコード数もIDも変わらないこと。**
  2. **値だけを1つ変えた同じ記録を流して、増えずに上書きされること。**
     これが「値を鍵に混ぜていない」唯一の証拠。1 だけでは通ってしまう。
  3. **鍵から1本ずつ抜いて、ぶつかりが出ること。**
     抜いてもぶつからない項目は、鍵に要らない。細かすぎる鍵も 1 と 2 を通る。

  実際に踏んだ例：兵庫県公報の目録で、公報番号（通し番号・1号1日付）に
  発行日を混ぜていた。Excel のオートフィルで年が1ずつ増えていて、
  13号から偽の号が58個できた。このときもぶつかりは0件だった。

- **鍵の作り方は出どころごとに1つに固定し、途中で変えない。**
  一次情報に番号が無くて所在地などで代用したら、その出どころは以後ずっと
  同じ作り方にする。あとから番号が付いたときに作り方を変えると、
  同じものが2つになる。代用したことは `data/parse-unknown.md` に書き出す。

- リポジトリは private で始め、公開の準備ができてから public に切り替える
  （GitHub Pages を無料で使うには public が必要）

- **そのまま公開できない生データを持つサイトは、リポジトリを2本に分ける。**

  git の履歴は消せない。一度コミットした生データは、その日にリポジトリを
  public にした時点で、過去のぶんも全部公開される。「あとで消す」はできない。
  ファイルを消すコミットを積んでも、履歴から取り出せる。

  | | 置くもの | |
  |---|---|---|
  | 収集用 | 生データ、`inbox/`、人が手で入れた原本 | **ずっと private** |
  | 公開用 | 集計結果、`index.json`、HTML、Pages | public |

  分けるかどうかは、これ1つで決める。
  **その生データを、いまそのまま公開できるか。**

  | 生データ | 公開できるか | |
  |---|---|---|
  | 公報・告示の全文 | できる（著作権法13条2号。県も国会図書館も公開している） | 1本でよい |
  | 警察のオープンデータ | できる（公開が前提のデータ） | 1本でよい |
  | 競売・公売の物件一覧 | **できない**（入札中・住居を含む。3.1） | 分ける |
  | 人が手で保存したページ | 相手の規約しだい。読むまでは「できない」側 | 分ける |

  迷ったら分ける。あとから1本にまとめることはできるが、
  1本にしたものを2本には戻せない。

- **公開する前に、「伏せ方を一度でも直したか」を見る。**

  上の表は**生データ**を見て決めている。それとは別に、**自分が作った出力の
  古い版**が履歴に残っている。伏せ方を直したなら、直す前のゆるい出力が
  そのまま履歴にある。生データが公開してよいものでも、この履歴は別の話。

  街頭窃盗統計が実物で踏んだ（2026-09-17）。元は警察のオープンデータなので
  上の表では「1本でよい」側。ところが伏せ方を直す前の geojson が履歴にあり、
  **伏せたはずの実数 16,208升**がそこから読める。公開する前に気づいた。

  だから、公開用のリポジトリは**そのつど新しく作る**。
  いま private で書いているリポジトリを、あとから public に切り替えない。

  | | |
  |---|---|
  | いま書いているリポジトリ | private のまま。ここが金庫 |
  | 公開用 | **履歴ゼロで新しく作る。** 成果物だけを push する |

  git の履歴を書き換えて public にする、は選ばない。当てにならない。

  - `refs/pull/*` は force-push で消えない
  - fork とキャッシュに残る
  - PR のタイトルと本文は履歴の外に残る

  **公開用の履歴は資産ではない。** 成果物は金庫から作り直せるので、
  公開用は丸ごと捨てて作り直せる状態にしておく。残す価値があるのは
  金庫側の履歴のほう（いつ何を取ったか。3.5）。

  いちばん安いのは、**公開する前に**この形にすること。
  大型店日報は public にしてから気づいたので、名前を変えて private にし、
  公開用を作り直す手順が要った。まだ公開していないサイトは、
  最初からこの形で作れば、その手順ごと要らない。

  **2本にするときの形**（大型店日報の `.github/workflows/shutten-recon.yml` が実物。
  他のサイトも同じ形にする。名前は揃える）

  - 走るのは**公開用の Actions**。public なので Actions の分は無料で、`GITHUB_TOKEN` で
    自分に push できる。収集用は**置き場**。収集用の Actions は止め、workflow は持たせない
    （名前が `-raw` で終わるか `-raw-` を含むリポジトリでは workflow が自分で止まるようにしてある）
  - 公開用の Actions が **deploy key** で収集用を `_raw/` に checkout する。鍵は収集用の
    Settings → Deploy keys（書き込み可）に公開鍵、公開用の Secret **`RAW_DEPLOY_KEY`** に秘密鍵。
    鍵は `ssh-keygen -t ed25519 -N "" -f raw_deploy_key -C <公開用の名前>-actions` で作る
    （**パスフレーズは空**。Actions は対話できない）。Secret には秘密鍵ファイルの全文
    （`-----BEGIN OPENSSH PRIVATE KEY-----` から `END` の行まで）を貼る。
    PAT は期限で黙って止まるので使わない。deploy key は1本のリポジトリにしか効かない。
    公開用の Actions は走る前に、収集用が公開側から見えない（private）ことを確かめ、
    見えたら生データを送らずに止まる
    Secret は**生データを持たない公開用にだけ**入れる（生データを追跡しているリポジトリに
    入れると二重持ちの見張りで止まる。意図どおり）
  - `data/raw` `data/files` `data/ocr` `data/wayback` を `ln -s` で**今までのパスにつなぐ**。
    Python は置き場の違いを知らない。置き場を変えるためにコードを直さない
  - 公開用への commit は**許可リスト**。公開してよいと決めたパスだけを列挙して `git add` する。
    `git add data` のような丸ごとはしない。新しい出力を公開したいときは列挙に1つ足す
    （足し忘れると「載らない」だけで済む。逆は済まない）。commit の直前に、生データ・記録・
    symlink が混ざっていないかを機械で見て、混ざっていたら止まる
  - しまう順番は **収集用 → 公開用**。取り直せないものを先にしまい、そこで失敗したら
    公開用にも送らない。収集用は private なので、公開側の検査を待たずに先に入れてよい
  - ページを作ったあとに**もう一度テストを通してから**公開用に push する。最初のテストは
    昨日の出力に対してなので、それだけだと今日の伏せ忘れが翌朝まで公開される。
    この2回目のテストが止めるのは公開用への push だけ。生データはその前に収集用に入っている
  - 走らせた記録（`data/*.md`・`data/koho/*.md`）は生の値を含みうるので、収集用の
    `data/reports/` に写す。公開用には commit しない（`data/parse-unknown.md` も収集用で見る）。

    **写すかわりに、記録の先頭に1行入れてテストで見張る形でもよい。**

        > **このファイルは公開しない。** 走らせた記録で、伏せる前の値が入りうる。
        > 公開してよいのは `data/public/` の中だけ（正本9節）。

    移す手間が要らず、**ファイル単体を開いた人にも分かる。** 許可リストと
    二重の歯止めになる（競売統計・2026-09-17）。
    公開用と収集用が別々に動いているなら「写す」のほうが確実。
    1本のリポジトリの中で分けているなら「先頭に1行」が向く。**どちらでもよい。**
  - 鍵が無いときに1本の形（`git add data` の丸ごと）で動くのは、**生データを既に追跡している
    移行前のリポジトリだけ**。生データを持たない公開用で鍵が無ければ、取りに行かずに止まる。
    鍵が無いまま走ると、その日の生データが public に載るため
  - 収集用が 2GB を超えそうになったら都道府県ごとに分ける（`-raw-<pref>`）。そのときは
    checkout と Secret と private の確認をもう1組ずつ足し、つなぐ段を収集先ごとのリンクに
    直す。公開 URL と公開用の木は変わらない
  - 一度でも生データを public に commit していたら、そのリポジトリを**名前ごと private に
    して収集用にし**、公開用は履歴ゼロで同じ名前に作り直す。同じ public リポジトリの中で
    履歴を書き換える手（filter-repo・orphan の force-push）は採らない。PR の参照
    （`refs/pull/*`）と PR の題名・本文は force-push でも消えず、そこから旧コミットに届く。
    作り直す順番（サイトが止まる窓と独自ドメインが空く窓を短くし、収集用が public のまま
    生データを受けないため）：
    ⓪ アカウントの Settings → Pages → **Verified domains** で独自ドメインを検証済みにしておく
    （③〜⑧ の間はどのリポジトリもドメインを主張していない。検証していないと他人が自分の
    Pages に付けられる）→ ① 新を**仮の名前**で作り、公開用の木を1コミットで入れる。
    **入れないもの**：`data/raw` `data/files` `data/ocr` `data/wayback`・`data/*.md`・
    `data/koho/*.md`（workflow の見張りが見る一覧と同じ。残すと初回から止まる）・`CNAME`
    （入れると旧と同じドメインを取り合う。⑧ で GitHub が書き戻す）。作り方は「main を
    `git archive` で展開 → 上を消す → 1コミット」。Pages を有効にしてよい（CNAME が無いので
    github.io の仮 URL で配信される。動作確認に使う）→ ② 旧の Actions を止める →
    ③ 旧の Pages を **Unpublish**（独自ドメインを外すだけでは github.io 側が配信を続ける。
    Free なら private 化で落ちるが、それに頼らない）。直後に
    `https://<owner>.github.io/<公開用の名前>/data/raw/<id>/<日付>.html` が 200 でないことを見る →
    ④ 旧を **`<公開用の名前>-raw`** に rename（workflow の checkout・private の確認・名前による
    自己停止が全部この名前を見る）→ ⑤ **すぐ旧を private** にし、旧の main から
    `.github/workflows/` を消す commit を入れる（収集用に workflow を持たせない）→
    ⑥ 収集用（旧）に Deploy key → ⑦ 新を同じ名前に rename → ⑧ 新の Pages に独自ドメインを
    付け（GitHub が `CNAME` を commit する）、それから Secret を入れる →
    ⑨ **`https://<owner>.github.io/<公開用の名前>-raw/data/raw/<id>/<日付>.html`** が 404 で
    あることを見る（`…/<公開用の名前>/` は ⑦ 以降は新のサイトなので確認にならない）。
    Secret を入れるのは収集用が private になった**後**。
    **古い clone は全部 remote を付け替えるか消す。** 同じ名前で作り直したあと、古い clone
    からの push は新しい公開用に届く（新しい枝を push すると、旧履歴ごと public に戻る）

- **生データを公開してよい場合でも、そこから氏名で引ける索引やページを作らない。**
  公報の全文には、法令に基づいて行政が公示した氏名が入っている
  （「土地区画整理組合の理事の氏名等の届出」など）。
  写しをそのまま置くのは、行政の公示を写しているだけなので構わない。
  そこから氏名を抜き出して索引にすると、行政が作っていないものを作ることになる。
  3.1 の「氏名と地番を恒久的に固定しない」はここに効く。
  絞り込みは出力の段階だけ、という上の決まりと同じこと。
  大型店日報の兵庫県公報の写し（`data/koho/full`・`data/koho/text`）は、この決まりのとおり
  公開用に置く（2026-09-16 に運営者が確認。設置者の氏名・住所は県が公示したもので、
  写しから氏名で引ける索引や個票は作らない。姉妹サイトが公開 URL で読む約束でもある）。

- **「変わったか」の見張りは、現在値と比べない。退役した値の一覧と比べる。**
  名前・URL・連絡先を差し替えたら、古いものが残っていないかを見る検査を置く。
  このとき **`config` の現在値と比べる作りにしない。** 手で直した瞬間に
  `old == new` になり、見張りが黙って空振りする。
  退役した値を文字列の一覧に置き、**消さない。** いつ誰が直しても落ちる。

  街頭窃盗統計 `scripts/make_public_tree.py` の `RETIRED` が実装例。
  そこの「古いURLが残っていないか」の見張りが、まさに `old == new` で
  空振りする作りだった。一覧に直した直後、旧名の混入を実際に検出した
  （2026-09-17）。

- **実測値をコメントや説明文に書かない。**
  「この時点で◯◯件」と書いた数は、データが増えれば古くなる。
  そして **検査は数字が「合っているか」を見ない。「あるか」しか見ない。**
  だから古くなっても誰も気づかない。最初から書かず、数えたいなら
  その場で数えるコードを書く。

  街頭窃盗統計で、コメントに残っていた3つの総計が互いに矛盾していた。
  同じ升を拘束する2つの経路が食い違っていて、少なくとも2つは真値でなかった。
  どれがいつの数だったかは、もう分からない（2026-09-17）。

  3.2 の「伏せ方を説明する文書に、実物の値を書かない」とは理由が違う。
  **あちらは漏れる話、こちらは腐る話。** 両方要る。

  **「いま成り立っている値」と「過去に起きたことの記録」は分ける。**
  前者は書かない。データが動けば古くなる。
  後者は書いてよい。起きた時点の話なので古くならない。
  「いま余裕は11」は前者、「2026-09-17 の時点で伏せた升が16,208あった」は後者。
  11節が実測値だらけなのは、全部が後者だから。

- **鳴らせていない見張りは、動くと分かっていない見張り。**
  検査を足したら、**実際に鳴るところまで確かめる。** 条件を人工的に作って、
  落ちるのを見る。「書いたから動くはず」は、確かめていないのと同じ。

  街頭窃盗統計の余裕の見張りが、**余裕 0 になるまで鳴らない作りだった。**
  docstring 自身が「『あと1件で崩れる』状態は素通りする」と書いていたのに、
  誰も読んでいなかった。25%で鳴るよう直し、人工的に細らせて鳴ることを
  確かめた（2026-09-17）。

  同じ日に足した2つの検査は、**足した直後に本物を1件ずつ見つけた**
  （退役名の見張り → 旧名の混入／伏せる判断の手書き検査 → 公報の表の合計）。
  どちらも偶然そうなっただけで、「鳴らして確かめる」を手順として
  書いてはいなかった。

  **鳴ることを確かめたら、直すと黙ることも確かめる。**
  常に鳴る見張りは、鳴らない見張りと同じくらい役に立たない。
  人が「またこれか」と読み飛ばすようになり、本物が来ても止まらない。
  壊した状態で鳴り、直した状態で黙る。**両方を見て、はじめて動くと分かる。**

- **偶然効いている性質は、意図に格上げして検査で留める。**
  守りになっている性質が、設計の意図ではなく**たまたまそうなっている**
  だけのことがある。そのままにすると、**次の変更で黙って消える。**
  気づいたら、意図として文書に書き、検査で留める。

  街頭窃盗統計では、町丁目が8年の合計だけ・市の升が年ごとで、
  そのため**年別には引けない。** 意図して作ったものではなかったが、
  実際に守っていた。気づいた時点で決定ログに書き、粒度がずれていることを
  検査で留めた（2026-09-17）。

- **URL に連動するものを、固定文字列で書かない。** `config` の URL から作る。
  公開先が決まるまでの仮 URL、公開後の本 URL、その差し替え。
  名乗り（User-Agent）・`robots.txt` の `Sitemap:` 行・`sitemap.xml` の中身は
  どれも公開先 URL を含む。別々に書くと、**差し替えのときにどれか1つが残る。**

  街頭窃盗統計は `SITE_URL` から作る形にしたので、公開時の差し替えが
  **1行で済んだ**（名乗りが追従したことを実際に確かめている。2026-09-17）。

  **ただし、config から作っても、人が書き写すところで切れる。**
  大型店日報は名乗りを変数から組み立てていて、コードは正しい。
  それでも国会図書館へ出した手紙に書いた文字列が実物と違っていた
  （訂正を送る予定）。**手紙を書いた側が、実物を出力して確かめなかったため。**
  外に出す文書に名乗りを書くときは、**実物を1回出力して、それを貼る。**
  7節の「手紙で『しない』と書いたことは、あとで守る」と同じ場所で切れる。

- **検査をコマンドで繋ぐとき、パイプを挟まない。** 終了コードが隠れる。
  `検査 | 整形` と書くと `$?` は後ろのコマンドのものになり、
  **検査が落ちても成功に見える。** 繋ぐなら `set -o pipefail` を付けるか、
  一度ファイルに落としてから読む。
  検査そのものが正しくても、**呼び方で黙る。**

- **相手が書き戻したファイルを、作り直しで消さない。**
  Pages に独自ドメインを付けると、GitHub が公開側に `CNAME` を commit する。
  公開用の木を作るスクリプトは `CNAME` を除外している（自分で入れると
  ドメインを取り合う）ので、**作り直した木には無い。**
  そこに `.git` を被せて `git add -A` すると、**CNAME を削除する差分になり、
  push すると独自ドメインが外れる。**

  除外リスト方式は「**作る**」ときは正しい。公開用の木は収集用の写しなので、
  足し忘れより消し忘れのほうが起きやすいから。
  だが「**入れ替える**」ときは、相手が足したものまで消す。
  定期実行は**許可リスト方式**（`git add -A -- <列挙>`）にして、
  手で作り直す経路にだけ注意を書く（街頭窃盗統計・2026-09-17）。

- **前身の置き場を見る。** 9節の作り直し手順は「いま書いているリポジトリ」を
  対象にしている。**その前に使っていた置き場は対象外になっている。**

  サイトは、たいてい別のリポジトリの中から始まる。分けて引っ越したあと、
  前身のほうは「転送ページだけにした」で終わりがちだが、
  **git 履歴には引っ越す前の出力がそのまま残る。**

  大型店日報は `ic-log`（別用途のアプリ）の中で始まり、2026-09-13 に
  `ogataten-nippo` へ移した。前身側は全ページを転送ページに置き換えてあったが、
  **`ic-log` は public で、履歴から伏せる前の3,525枚が読めた。**
  設置者の欄を機械で分類したところ、伏せてあったのは**2枚だけ**だった
  （2026-09-17 に発見し、`ic-log` を private にして塞いだ）。

  確かめること。**いまのリポジトリだけを見ても出てこない。**

  - このサイトは、どこから分かれてきたか
  - その置き場は public か
  - そこに、いまの伏せ方が入る前の出力が残っていないか
  - 転送ページに置き換えてあっても、**履歴からは読める**

  **private 化は force-push と違って実際に効く。** 9節が「当てにならない」と
  言っているのは履歴の書き換えのこと。可視性を落とすのは別の手で、
  fork が無ければ外から読めなくなる（先に fork 数を見る）。

- **workflow が作業用に置くディレクトリは、`.gitignore` と検査の両方に登録する。**
  片方だけだと、もう片方で事故る。

  街頭窃盗統計の月次 workflow が、金庫を `_raw/` に checkout していた。
  `.gitignore` に無いので、手で `git add -A` すれば金庫の中身が公開側に入る。
  検査の除外にも無いので、**検査が金庫まで見て毎回落ちていた**（2026-09-18）。
  金庫の記録に親の合計があるのは正当で、**検査が正しく、当て方が違っていた。**

  **除外リストに1語足すのは応急処置。** 次の作業用ディレクトリで同じことが起きる。
  **検査の範囲は許可リストで決める。** ただし「git が追跡している」だけでは
  足りず、「**公開対象か**」も要る（追跡されていても公開しないものがある）。
  追跡情報が無い場所では除外リストに落ちるが、**どちらで決めたかを毎回印字して、
  落ちたことを黙らない。**

- **検査は、最初の1件で止まらない形にする。** 止まると2件目以降が隠れ、
  同じ穴が2か所にあっても、1か所直すまで2か所目が見えない。

  上の穴を1つ直したあと、**別の検査が同じ穴を持っていた**ことが分かった。
  最初に落ちた1つしか見えていなかった（街頭窃盗統計・2026-09-18）。

- **「どこから来たか」だけでなく「どこへ書いたか」も辿る。**
  前身の置き場を見るとき、来た先だけでは足りない。このリポジトリの出力が
  **外のどこかに書き出されていないか**も見る。

  確かめること：push 先は自分だけか、外への HTTP に書き込み（POST/PUT）が
  無いか、workflow が外部の資格情報を持っていないか、Pages を出していないか。
  開発系が、外への HTTP 全3か所とも GET・Secret 0件・Pages 無しを確かめた
  （2026-09-18）。

## 10. 報告の形（各サイトのチャット共通）

4サイトの進み具合は、共通仕様チャット（大型店日報のチャット）に集約している。
そこへ貼るとき、長い報告のままだと読めない。**報告する側が短い版を用意する。**

各サイトのチャットは、報告のたびに本文の最後にこれを付ける。
**必ずコードブロック（``` で囲む）で出すこと。** 地の文で書くとコピーの範囲を
指でなぞることになり、貼るのが面倒になる。コードブロックならコピーボタンが出る。

````
```
━━━ 共通仕様チャット貼り付け用 ━━━
【やったこと】3行まで
【決まったこと】箇条書き3つまで
【数字】検証した件数・実測値だけ
【判断が要ること】無ければ「なし」
【次にやること】1行
━━━━━━━━━━━━━━━━━━━
```
````

- 10行を超えない。理由や経緯は書かない。
- 本文はこれまで通り詳しく書いてよい。最後にこの枠を足すだけ。
- 「【判断が要ること】なし」と書けるなら、それが一番いい報告。

## 11. この文書の直し方

2. Pull Request を出す
3. マージされたら、各サイトのリポジトリで `common/addr.py` と `common/privacy.py` を更新する

### 見つけたあと、何をするか

公開してしまったものを見つけたとき、**何をどこまでやるか**の線引き。

| 見つけたもの | どうするか |
|---|---|
| **他人の氏名・地番** | **塞ぐ。** 可視性を落とす、公開用を作り直す |
| 運営者自身の連絡先 | 受け入れる。止血（noreply 化）だけする |
| 当事者に結びつかない統計の升 | 受け入れる |

三段目は「**升だから軽い**」ではない。「**当事者に結びつかないから軽い**」。
升でも当事者に結びつくものは重い。

**事後の重さと、事前の基準は別。** この表は「**見つけたあと何をするか**」であって、
「最初からどこまで気をつけるか」ではない。**公開する前なら費用はゼロ**なので、
事前の基準は下げない。

街頭窃盗統計・大型店日報・競売統計の3者が、独立に同じ線に着いた（2026-09-17）。

### 食い違いを見つけたら、直す前に報告する

**この文書は間違っている可能性がある。** 実装していて、

- 節と節で食い違っている
- どちらにも読めて、どちらが正しいか決められない
- 書いてある通りにすると明らかにおかしくなる

に気づいたら、**自分の解釈で先に進まずに報告すること。** 正本のほうを直す。

仕様を書いた側は自分の矛盾に気づけない。実装する側が「両方要ると読んだけれど
合っているか」と聞いてくるのが、いちばん早く正しくなる。これは手戻りではなく、
いちばん安い直し方。
