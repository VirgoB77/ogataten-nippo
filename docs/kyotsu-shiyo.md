# 姉妹サイト共通仕様

鯨屋（くじらや）が運営する4つのサイトで共通して守る決まりを、ここ1か所にまとめる。

**この文書が唯一の正本。** 各サイトのリポジトリにコピーを置かず、ここを読むこと。
仕様を変えたいときは、この文書を直してから各リポジトリに反映する。逆はしない。

URL: https://github.com/VirgoB77/ogataten-nippo/blob/main/docs/kyotsu-shiyo.md

---

## 1. なぜ共通仕様が要るのか

4つのサイトは、扱う制度も読者も別だが、**同じ土地の上で起きたことを別の角度から見ている**。

```
農地転用・環境影響評価            開店の2〜4年前
都市計画決定・地区計画            1〜3年前
開発許可・盛土規制法              1〜2年前
公有財産の売却（跡地）            数年前
工事完了公告（都計法36条3項）     半年〜1年前
大規模小売店舗立地法の届出        8か月前   ← 大型店日報
　　開店・稼働
町丁目ごとの犯罪統計              現在      ← 犯罪統計マップ
　　↓（数年〜十数年）
競売・公売                                  ← 競売統計
```

同じ住所を同じキーで表せれば、この線が引ける。
「この土地は3年前に市有地として売られ、2年前に開発許可が下り、去年工事完了公告が出て、
今年大型店の届出が出た」——これを出せるのは、キーを揃えたときだけ。

だから **住所の正規化と出力スキーマだけは、4サイトで一言一句そろえる。**
それ以外（サイトの作り、HTMLの書き方、パイプラインの組み方）は各サイトの自由。

---

### 迷ったら「時間がたつほど価値が増えるか」で選ぶ

上の線が示しているのは、**4つのサイトが時間の違う断面を見ている**ということ。
だから何を作るか迷ったときは、この一点で選べる。

    **時間がたつほど価値が増えるか。**

役所の縦覧は数か月で消える。補助金のページは年度で書き換わる。
公告は取り下げられる。**誰も取っていなければ、無かったことになる。**

    今日の断面     誰でも今日から集められる。後発が追いつける
    時間の記録     **毎日ためた分は、後から始めた人が作れない**

同じデータでも、切り口によってどちらにもなる。

    「いま貸しに出ている物件の一覧」    → 今日の断面
    「この場所は何年もったか」          → 時間の記録

**時間を含むデータは、断面より件数が少なくても価値が高い。**
前者が千件あって後者が二百件でも、後者のほうが他所に無い。

**少なさが価値なのではない。時間が価値。**
3.2 の「小さい母数を出さない」と食い違わないように、ここを取り違えないこと。
**母数が3件では統計にならないのは、時間を含んでいても同じ。**

3.5 の「終わった・消えたを記録する」と、9節の「落ちた日の収集を捨てない」は、
どちらもこの考えから出ている。**巡回の頻度が、そのまま記録の完全性になる。**

上の「この場所は何年もったか」は、**開店と閉店がつながる前提**で書いている。
つながるとは限らない。始まりの側の届出が手元に無い年の分は、つながらない。
欄の持ち方は 3.5 の「いまつながらなくても、これからつながる形にしておく」。

### 正本に書くか、サイトの設計に書くか

    正本            ほかのサイトも守るもの
    サイトの設計     このサイトだけのもの

線は5節にある。**2サイト目が「同じものが要る」と言った時点で、この文書に上げる。**
その線は `common/` の関数のために書いたが、**掛かるのは関数だけではない。**
決定・語彙・手順・欄の名前・ファイルの置き場も同じ。

2026-09-19、同じものを指す語が4組あった（結果の語）。用途地域は31通りの
書き方で入っていた。どちらも「2サイト目が要ると言った」より前に、
1サイト目が勝手に決めていた。**語も線3に掛ける。**

**サイトの文書は3つに分ける。混ぜない。**

| | 何を書く | 書き方 |
|---|---|---|
| 設計書 | 何のため・どう作るか | **上書きする。**形が変わったら直す |
| 決定ログ | 迷ったとき何を選んだか・なぜ | **追記だけ。**日付つき。消さない |
| 問い合わせ記録 | 正本に送ったことと、その状態 | 状態が変わったら書き直す。**解決も消さない** |

問い合わせ記録の状態は4つ。**「返事待ち」と「材料待ち」を分ける**（7節）。

    解決          正本が直った。こちらも当てた
    保留          正本が「材料待ち」と決めた。止まっているのではない
    生きている    返事待ち。**こちらから催促してよい**
    こちらの宿題   正本は直った。当てるのがこちらに残っている

**大型店日報は、設計書と決定ログを持たない。** ここは正本を置いている場所なので、
別に設計を持つと、次に読む人がどちらが正か迷う。訂正の記録は公開側の
訂正履歴のページに置いてある。**持たないことも、こうして書いておく。**
書かないと「まだ作っていない」のか「そもそも要らない」のかが分からない
（6節「空の `index.json` を置かない」と同じ線）。

### 正本は「最低限これを返す」を決める。実装が足すのは構わない

`split_city()` で、正本が `(city, rest)` の2つ組、実装が4つのキーを持つ dict に
なっていた。どちらかが嘘をついていたわけではない。線はこう引く。

- 実装が**余分なキーを足す**のは構わない。そのサイトが要るなら足してよい
- 足したキーに**2サイト目が依存し始めたら、正本に上げる**（5節の線3）
- **正本が決めた分を返さない／意味を変える**のは食い違い。直すのは実装のほう

今回は「実装が足した」ではなく、**正本のほうが狭すぎた。**
`pref` を返さない形では `city_code_of()` が引けず、**4節の次の段に繋がらない。**
正本を広げた。

なぜ狭かったか。**実装を読まずに、報告の要約だけを見て正本に書いたから**
（2026-09-19、統括）。4節には、逆向きの記録がすでに1つある——
「実装はそうなっていたが、この文書に書いていなかった」（2026-09-18）。

**正本と実装は、どちらの側からもずれる。** 片側だけ見張っても半分しか防げない。

- 新しい関数を正本に**書く**ときは、**先に実装の署名を読む**
- 正本を**直した**ときは、11節の手順3で各サイトの `common/` を当て直す

要約からは署名が作れない。要約は「何をする関数か」しか運ばないが、
署名が決めるのは「**何を捨てるか**」のほう。`pref` はそこで落ちた。

### どの節が効くかは、サイトによって違う

この文書の節は2種類ある。**新しいサイトを立てるとき、どちらに当たるかを書き出す。**

| | 節 | いつ効くか |
|---|---|---|
| **相手への振る舞い** | 3.4 取得の作法／3.5 出典／7 運営者情報／9 技術方針 | **データの性質にかかわらず、全サイトで効く** |
| **データの性質** | 3.1 個人情報／3.2 小さい母数／4 `addr.py`／6 `index.json` | データが住所や当事者を持つときだけ効く |

**「うちは別系統だから共通仕様は関係ない」と読むと、取得の作法まで落ちる。**
robots を見る・間隔を空ける・429 や 503 で止まる・名乗る——これは
**相手のサーバーの話**であって、こちらのデータが何かとは関係がない。

一部だけ効く節もある。5サイト目（住宅系補助金の自治体横断）は
データに当事者がいないので 3.1 は効かないが、**自治体の補助金ページには
問い合わせ先に担当者名が載ることがある。**
課の名前と電話番号は出す、個人名は出さない、だけは守る。

同じ作法・同じ屋号で作るが、**住所の串には刺さらない。**
姉妹サイトではあるが、家族ではない。

**`id` の接頭辞は、この表で衝突しないことを確かめてから決める。**
一度決めたら変えない（9節「鍵にはあとから変わらないものだけを入れる」）。
`site` と同じでも、短い別名でもよい。**衝突しないことだけが要件。**

残る2つの名前とドメインは検討中。ドメインは **`.com` を使う**
（`.jp` は JPRS の WHOIS で登録者名が公開され、公開代行が効かないため）。
WHOIS は必ず**代理公開**にする。氏名も所在地も出さない（7節）。

### 街頭窃盗統計という名前について

警察庁が「街頭犯罪」と呼んでいる分類の、窃盗の部分そのもの。
扱う7手口は、ひったくり・車上ねらい・自動車盗・オートバイ盗・自転車盗・
部品ねらい・自動販売機ねらい。実データで確認ずみ（罪名は窃盗のみ、手口は7つだけ）。

**侵入盗（空き巣）は街頭犯罪ではないので、最初から入っていない。**
データが欠けているのではなく、そういうデータ。名前がこれを先に説明する。

出どころが警察のデータなので、名前も警察の言葉にそろえる。
「屋外窃盗」は造語なので使わない。「盗難」は被害者側の言葉で、
警察の統計は「窃盗」「認知件数」なので使わない。

## 3. 守ること（ハードルール）

破ったら公開しない。迷ったら出さない方を選ぶ。

### 3.1 個人情報

**原則：個人が特定できる組み合わせを、恒久的に固定しない。**

一次情報の側が公開していても、こちらは残す。行政の公告は数か月で消えるが、
こちらのサイトは消えない。「消えない」ことが、そのまま責任になる。

| 出すもの | 個人 | 法人 |
|---|---|---|
| 氏名・名称 | **出さない**（`個人` と表記） | 出す |
| 所在地 | **町丁目まで**に丸める | 地番まで出す |
| 面積・用途・日付・金額 | 出す | 出す |

- 法人かどうかが**確かめられないとき**は、個人として扱う。推測で法人にしない。
- **名前がそもそも公表されていない場合は、上の2つとは別の扱いにする。**
  伏せるべき名前が存在しないので、所在地を丸める理由もない。

  | 一次情報の側は | 名前 | 所在地 | `party_kind` |
  |---|---|---|---|
  | 法人名を載せている | 出す | 地番まで | `corp` |
  | 個人名を載せている（法人と確かめられない場合を含む） | `個人` | **町丁目まで** | `individual` |
  | **そもそも名前を載せていない** | 空 | **地番まで** | `undisclosed` |

  3行目は、公有地の売却で落札者の列がない表、競売・公売の物件など。
  こちらが名前を持っていないので「個人と地番の組み合わせ」を作りようがない。
  ただし**地番を出してよいのは、その所在地が一次情報の側で公表されているときだけ。**
  別のソースから補ったり、推測で地番を足したりしない。

- **`undisclosed` を名乗れるのは、名前の欄が無いことを確かめたときだけ。**

  「名前が無い」には2つある。取り違えると、**こちらの解析の穴が、そのまま
  地番の公開になる。** 名前が空になった理由を、必ずどちらかに決める。

  | | 名前が空な理由 | `party_kind` | 所在地 |
  |---|---|---|---|
  | 相手が載せていない | 一次情報に欄が無い（**確認ずみ**） | `undisclosed` | 地番まで |
  | こちらが読めていない | 欄はあるが読み落としている | `individual` | **町丁目まで** |

  確かめ方は、**名前の欄があるかどうかを出どころごとに1回調べて、その結果を
  記録に残す**こと。調べていない出どころは `individual` から始める。
  `undisclosed` は、調べたあとで初めて名乗れる。
  「法人か確かめられないときは個人として扱う」と同じで、**わからない側は安全な側に倒す。**

  実際に踏んだ例：近畿財務局の結果表で、契約相手方の列を読み落としていた。
  名前が空になったので `undisclosed` に見え、**個人121件の地番が出ていた。**
  欄はあった。こちらが読んでいなかっただけだった。
- **画面に出す表示と、`index.json` に入れる値は分ける。**
  - 画面は `個人` と書く。空欄だと「取れなかった」のか「個人だから伏せた」のかが
    読者に分からない。伏せたことは伏せたと書く。
  - `index.json` は**空文字**。機械が読むデータに `個人` という文字列を入れると、
    全国の別人が同じ名前として扱われ、横断ハブで混ざる。
  - 伏せたことは `party_kind` で機械に伝える（5節・6節）。
- 地番と氏名の両方を落とす必要はない。**片方でよい。** 両方落とすと値打ちが消える。
- 人が住んでいる可能性があるものは、**個票として扱わない**
  （競売・公売の入札中物件、居住用途の建物、住居系用途地域）。
  個票とは、住所や物件が特定できる形で1件ずつ残すもの。

  **判定の仕方**（開発系が実装して分かったこと。2026-09-18）：

  - 拾う言葉は「居宅」だけでは足りない。**共同住宅・マンション・アパート・
    長屋・寄宿舎・寮・社宅・戸建**、区分所有らしい部屋番号、住居系用途地域
  - **行ではなく、表の単位で落とす場面がある。** 見出しに `専有` `区分所有`
    `建物` があれば「住戸が混ざる表」と見て、住まいでないと言い切れない行も
    落とす。ある市の結果表は「地積 / 専有面積(㎡)」という**1列に土地と
    マンションの一室を混ぜていた**。行だけ見ても分からない
  - **判定できないものは、落とす側に倒す**（3.1 の `undisclosed` と同じ考え）
  - ただし落としすぎない。「◯番街区」は住居表示の街区であって部屋番号ではない。
    ここまで落とすと**土地が1件も残らなくなる**。**落としすぎていないかを測り、
    テストで固定する**
  - **行は消さず、落とした理由を残す。** 集計には数えるので、
    「個票にしない」という印を立てるだけにする

  **復号や様式変更の前に、この判定を先に入れる。** あとから入れると、
  一度は出てしまう。開発系は文字コードを直す前に間に合わせた（同日）。

  **集計に数えるのは構わない。** 恒久的に固定してはいけないのは「住所」であって
  「件数」ではない。「西宮市で今月 戸建て12件が入札に出た」には、誰の家かを
  示す情報がない。むしろ件数は景気の指標として値打ちがある。

  ただし集計にするときは：
  - 3.2 の小母数のルールがそのまま効く（1〜2件は `1-2` とまとめる）
  - **段階の違うものを同じ升に混ぜない。** 公告に出た件数と落札された件数は
    別の升にする。`kind` を分ける（語は9節でそろえる）
  - 数えるのは**その月に新しく出た件数**（フロー）。「いま入札中の件数」（ストック）に
    すると、同じ物件を翌月また数えてしまう
  - 一覧は上書きされるので、取得のたびにスナップショットを残す。
    残さないと差分が取れず、フローが数えられない

### 3.2 小さい母数を出さない

件数1件は統計ではなく事故。小さな自治体や町丁目では、1件が個人の特定につながる。

- 集計の升（市区町村 × 種別 × 月など）の件数が **1〜2件のときは `1-2` とまとめ**、実数を出さない。
- 率（人口千人あたりなど）は、**件数が1件か2件**のとき、または**人口500人未満**
  のとき計算しない。値を `null` にして、伏せたことがわかるフラグを立てる。

  **ただし、0件かどうかを先に見る。0件なら、人口がどれだけ小さくても率は `0` を出す。**
  率を伏せるのは「率 × 人口」で件数が戻るからで、0件は件数そのものを `0` と
  出しているので戻るものが無い。**人口の小ささも、同じ理由で効かない**
  （9件÷400人の率に400を掛ければ9件が戻るが、0件には戻る先が無い）。

  件数のほうを「2件以下」と書いていたため、0件の升が率の地図で
  「率を出していない」灰色に落ち、次の節の「いちばん薄い階級の色」に
  ならなかった（街頭窃盗統計が実物で見つけた）。
  **人口の側にも同じ穴が残っていた。** 3サイトの実装が全部
  「人口を先に見て、0件かどうかを見ていなかった」ため、
  `suppress_rate(0, 400)` が `True` を返していた
  （2026-09-19、開発系が自分の実装で見つけた）。
  **条件を2つ並べるときは、どちらを先に見るかも書く。**
- 粒度の下限は **市区町村**（街頭窃盗統計のみ町丁目まで）。
  町丁目より細かく（学区・地番）は下りない。期間は月単位以上。

### 伏せた升は、引き算で戻せることがある

1〜2件を `1-2` と伏せても、**同じものを2つの粗さで出していると、
引き算で正確な値が分かってしまう。**

```
  ある市 × ある種別 × ある年 の合計         15 件（出している）
  その市の町丁目の升                      2 ＋ 4 ＋ 1-2 ＋ 6 ＋ 1 …
                                               ↑ 伏せたのはこの1つだけ

  15 −（2＋4＋6＋1＋…）＝ 2      ← 伏せた升の正確な値が出る
```

伏せた意味が消える。1件なのか2件なのかまで分かってしまう。
3.2 が守ろうとしたのは、まさにそこ。

- **伏せた升が、そのまとまりの中でちょうど1つになったら、もう1つ伏せる。**
  まとまりとは、同じ親の升を共有する子の升の集まり
  （「市区町村 × 手口 × 年」に属する町丁目の升、など）。
  2つめに伏せるのは、残りのうち**いちばん件数が小さい升**。
  失う情報がいちばん少ない。
- **逆向きにも効く。** 親の升を伏せたのに子を全部出していたら、足し算で
  親が分かる。親を伏せたなら、子も同じまとまりで2つ以上伏せる。
- いちばん簡単なのは、**両方の粗さを出さないこと。**
  迷ったら細かいほうだけ出す。粗いほうは読者が足せばよい。

### 合計の升と、内訳の升を、両方出さない

上の「両方の粗さを出さない」を、親子のある種別に当てはめたもの。
競売統計が実物で見つけた（2026-09-16）。

「公告」とその内訳の「公告-新規」を両方の升で出すと、2つのことが同時に起きる。

1. **読者が足すと二重に数える。** 新規は公告の内数なので、
   升を全部足した数が、本当の件数より多くなる
2. **引き算で伏せた升が戻る。** 公告6 − 公告-新規5 = 1 で、
   出していないはずの再公告が1件だと分かる

どちらも直し方は同じ。

- **合計（親）の升は出さない。内訳（子）の升だけを出す。**
  合計が要る読者は、子を足せばよい
- **内訳は全部出す。1つでも欠けさせない。**
  欠けると、それが「伏せた」のか「0件」のかが読者に分からない
- **0件の内訳も `0` と書く。** 伏せた升（`count: null`）と見た目で分ける
  （次の節と同じこと）

競売統計の `index.json` の実物（大阪市西区・2026年9月）：

```json
{"kind": "競売/公告-新規",   "count": null, "count_label": "1-2"}
{"kind": "競売/公告-再公告", "count": 0,    "count_label": "0"}
```

「競売/公告」という合計の升は出していない。この形にすると、
升を全部足した数が本当の件数に合い（伏せ字のぶんは1〜2の幅）、
引き算で戻せる升も無くなる。

種別が互いに排他なら（大型店日報の新設・廃止・承継・変更のように）、
そもそも親子が無いので考えなくてよい。親子があるのは、
「全体」と「そのうち○○」を両方出したくなったときだけ。

### 伏せた升と、本当に0件の升は、見た目で分ける

地図でどちらも同じ灰色にすると、読者は「ここでは起きていない」と読む。
伏せたのは「起きていない」ではなく「言わない」。逆の意味に読まれる。

| | 見せ方 |
|---|---|
| 0 件 | いちばん薄い階級の色 |
| 伏せた升 | 階級とは別の見た目（斜線など）＋ 凡例に「1〜2件」 |

`index.json` でも同じ。`count` が `null`（伏せた）と `0`（本当に0件）を
必ず書き分ける。片方に寄せない。

### 数字を書かなくても、目で読める形は数字を出している

伏せ字は数字の欄だけに掛けても足りない。横棒の幅・地図の色・階級の境・
並び順・位置は、読者が目で読める数字そのもの。特に2つが危ない。

- **最大値で正規化しない。** 横棒の幅を「その値 ÷ その表の最大値」で出すと、
  最大値はどこかの升の実数なので、幅に掛けるだけで伏せた升が戻る。
  分母は升の実数ではなく固定の目盛りにし、伏せた升は棒を出さない
  （本当の0件と同じ見た目になる。数字のほうで「1-2」と「0」を書き分ける）。
- **階級の境を、伏せる範囲の中に通さない。** 1〜2件を伏せるなら階級の下端は
  3から始める。境が2にあると1件と2件が別の色に落ち、画面が「1-2」と書いた
  真横で、色と凡例が1か2かを答える。

率にも効く。全体の平均を細かく出すと、率 × 人口 で全体の合計（＝升の親）が戻る。
伏せた子が k 個あるなら、丸めの幅が k 件ぶん以上になるところまで桁を落とす。
桁を落としきって0になるなら、値を出さない。

凡例（単年）。階級の境の入れ方：

    直す前    0 ／ 1 ／ 2〜3 ／ 4〜7 ／ 8〜        ← 「1」が階級名として出ていた
    直したあと 0 ／ 3〜4 ／ 5〜7 ／ 8〜11 ／ 12〜   ＋ 斜線で「1〜2件」

横棒（値は架空。下の節の理由で、実物は書かない）：

    直す前    <td class="v num">1-2件</td><td class="barcell"><i style="width:N%"></i></td>
              幅は「その値 ÷ その表の最大値」。最大値は同じ表に出ているので、
              掛け算1つで伏せた升の実数が戻る
    直したあと <td class="v num">1-2件</td><td class="barcell"></td>

数字の欄だけを見ていたときは、街頭窃盗統計で横棒3,216本と色の階級2組が
実数を答えていた（2026-09-16）。

### 「引き算で戻る升 0」だけでは足りない。余裕も出す

戻る升を数えて0になっても、それは**いまのデータでぎりぎり成り立っている
だけ**かもしれない。区画の数が減る、件数が増えて伏せる升が減る、年が1つ増える、
どれでも同じ作りのまま戻るようになる。

だから「0件」という結果だけでなく、**どれだけ余裕があるか**も毎回出す。

まとまりごとに、伏せた升の数 `k` と、そのうち2件だった升の数 `m` を見る。
親の合計から引けば伏せた升の和が出るので、**`m` は確定すると思ってよい。**
守っているのは和ではなく「**どの `m` 個が2件か**」の組合せのほうで、
その数が `C(k, m)` 通りある。

    余裕 = min(m, k − m)

`m` が 0 か `k` に張り付くほど組合せが減り、張り付けば升が特定できる。
だから両端からの距離の小さいほうを見る。**`k` が1なら、和が分かった時点で確定する。**

**この文書に実測の値は書かない**（9節「実測値を説明文に書かない」）。
測った結果は各サイトの決定ログに置く。街頭窃盗統計が実測した（2026-09-17）。

分かったのは、**同じ作りのまま区画の少ない市に広げると、特定できるまとまりが
出る**ということ。「戻る升0」は、区画の多い市だから成り立っていた。

年や市を足す手順に、この測定を組み込む。足してから測るのではなく、
**足す前に測って、余裕が足りなければ層の作りを変える。**

### 食い違いは、守りではなく徴候

同じ升を拘束する経路が2つ以上あって、互いに矛盾することがある。
このとき「**解が0個だから戻らない**」と読んではいけない。

攻撃する側は、**全部の経路を連立させる必要がない。**
矛盾に気づいたら、信頼できる1本を選べばよい。
矛盾は、その1本が使えることを否定しない。

守っているのは矛盾ではなく、**その経路にある未公開の項のほう**である。
（伏せた升の和の幅より大きい、時刻の読めない行の数など）
**どの項が守っているのかを名指しできないなら、守れているか分かっていない。**

同じ日に、街頭窃盗統計が両方向で踏んだ（2026-09-17）。

- 朝：解が1通りに決まったので「戻る」と報告した
  → 制約のほうが矛盾していて、その1通りは真値ではなかった
- 夕：解が0個になったので「戻らない」と報告した
  → 経路を1本外せば解は存在した

**どちらも「複数の経路が食い違っている」という一つの事実の、別の顔。**
食い違いを見つけたら、守りが増えたのではなく、**どこかの数え方が違うという
徴候**として扱う。

### 親を出す前に、当てる組合せの数を測る

3.2 は「余裕も出す」と書いているが、**どこからが足りないのかを書いていなかった。**
まとまりの性質がサイトによって違うので、一律のしきい値はまだ決められない
（あるサイトは伏せた升が 20〜100 の桁、別のサイトは **ほとんどが `k=1`**）。

いま決まっているのは1つだけ。

**当てる組合せが1通りしかないまとまりは、親を出さない。例外なし。**

    k = 伏せた升の数
    m = そのうち2件だった升の数（親から引けば確定する）
    当てる組合せ = C(k, m)

`C(k, m) = 1` は「伏せた升がすべて確定する」という意味で、
伏せていないのと同じ。**`k = 1` は常にこれに当たる。**

`k` が小さいまとまりは、そもそも隠れる場所が無い。

    k=1   → 1通り        確定する
    k=2   → 最大 2通り    ほぼ確定する
    k=4   → 最大 6通り
    k=10  → 最大 252通り
    k=20  → 最大 184,756通り

**残りのしきい値は、4サイトの実測が出そろってから決める。**
それまでは各サイトが実測を決定ログに置き、**親を出さない側に倒す。**
出さない判断のほうが、あとから戻せる。

### 伏せ方を説明する文書に、実物の値を書かない

この共通仕様も公開している。伏せ方の例に実物の升を使うと、
**説明そのものが伏せ字を破る。**

この文書が実際に踏んだ（2026-09-17、街頭窃盗統計が見つけた）。
上の横棒の例に、町丁目の名前と、実物の幅と、その表の実物の最大値を並べて書いた。
3つそろうと掛け算1つで伏せたはずの実数が出る。それを public なリポジトリに置いていた。

- 例に使う値は**架空のもの**にする
- 仕組みの説明に実物の形が要るときは、**場所の名前を出さない**
- 「直す前／直したあと」を並べるときは、**直す前の側に実物を書かない**
  （直す前こそが、伏せられていない側だから）
- 割合・件数の総数（「横棒3,216本」など）はよい。1つの升を指さない

サイトの側の報告書（`data/parse-unknown.md` など）も同じ。公開するものは全部。

### ほとんどが伏せ字になる層は、出し方を考える

ある手口の升の大半が実数で出せないなら、その層は地図としてほぼ空になる。
空の地図は「この街では起きていない」と読まれる。
件数の少ない手口は、**期間を長くまとめる**か、**粒度を市区町村に上げる**か、
**種別をまとめる**（次の節）か、**その層は出さない**かのどれかにする。
伏せ字だらけの地図は出さない。

判定は「伏せ字の割合」ではなく **「実数が出せた升の割合」** で見る。
街頭窃盗統計のひったくりは、伏せ字は 12.7% しかない。残りの 86.6% は
本当に0件で、実数が出せた升は 0.7% しかなかった。「伏せ字が多い層」で
機械判定すると、7手口すべてがすり抜ける（2026-09-16、実測）。

逆の端の実物もある。競売統計の `競売/公告-再公告` は、46升すべてが本当に0件で、
伏せ字は **0.0%**。「伏せ字の割合」で機械判定すると、全層のうちで**最良**に見える。
だが実数が出せた升も **0** で、地図としては完全に空だった（2026-09-19、実測）。
伏せ字0%は「よく出せている」ではなく「出すものが無かった」のこともある。
**両端から挟まれるのは、この指標が分子だけを見て分母を見ていないから。**

### 件数の少ない種別は、まとめて1つの層にする

上の4つめ。期間を長くまとめても粒度を上げても足りず、かといって落とすと
読者が困る種別は、**近い種別どうしをまとめて1つの層にする。** 層が減るぶん
1つあたりの件数が増え、実数で出せる升が増える。
層を減らしながら読める量が増えるのは、この選び方だけ。

- まとめるのは、読者が同じ文脈で読む種別だけ。意味の遠いものを足すと、
  数は増えても読めない数字になる
- **まとめたら、細かいほうは出さない。** 束ねた層と、その中の種別ごとの升を
  両方出すと引き算で戻る（「合計の升と、内訳の升を、両方出さない」と同じこと）
- まとめても伏せ字だらけのままの種別は、粒度を上げるか、その層は出さない
- 種別ごとに層を選んでよい。全部を同じ粒度にそろえる必要はない

街頭窃盗統計の実物（兵庫県・8年・849町丁目。実数を出せた区画の割合）：

    まとめる前   車上ねらい 47.1% ／ 部品ねらい 27.6%
                 オートバイ盗 21.2% ／ 自動車盗 2.9%
    まとめたあと 「車・バイク」の1層で 69.7%

    ひったくり 0.7% と 自動販売機ねらい 6.7% は、まとめても足りないので
    市区町村に上げた（町丁目では出さない）

ひったくりは8年＝県警が配布している全期間で、「期間を長くまとめる」は
最初から使えなかった。3つでは足りない場面が実物にある。

### 粗さが混ざるファイルは、升ごとの手当てでは直らない。置き場所で分ける

3.2 の決まりは升1つ1つに掛かる（親を出さない・兄弟をそろえる・1〜2件は伏せる）。
**それだけでは足りない場面がある。**

競売統計の集計ファイルが、**同じ数を5つの粗さで数えていた**
（裁判所／庁×月／庁×年／府県×月／府県×月×種別）。
升1つ1つは 3.2 を守っていたのに、**粗いほうを伏せても細かいほうを足せば戻った。**
言い換えの経路を1つずつ塞ごうとしたが塞ぎきれない。
かといって粗さを1つに減らすと、このファイルの用途
（どの粗さで出すかを後で選べるように並べておく）が無くなる。

**守れていないのはファイル全体のほうで、升ごとの手当てでは直らない。**
だから置き場所で分ける。

    data/agg/     社内用。粗さが混ざっている。**公開しない**
    data/public/  **ここだけが公開用。** 1つの粗さだけを選んで写す

守らせ方は3つ。どれか1つでは足りない。

- 社内用のファイルに「公開しない」の欄を必ず入れる（文言は1か所から配る）
- 走らせた記録（`data/*.md`）は先頭に1行
- テストが見張る（社内用は全部その欄を持つ／公開用は持たない／
  公開用に見覚えのないファイルが増えていない）

**「何を伏せるか」ではなく「どれを公開するか」に問いを変える。**
許可リストのほうが、除外リストより強い（9節）。

### 中途半端に伏せるくらいなら、伏せない

競売統計が、伏せた升の**2行下に同じ数を実数で書いていた**
（`合計.◯◯まで進んだ回 = null` の下に、同じ数を指す別の欄）。

守れていないうえに、**「伏せてある」という誤った安心を作る。**
読む人も、次に直す人も、そこは守られていると思って通り過ぎる。
**伏せ忘れより悪い。** 伏せ忘れは検査が見つけるが、こちらは見つけない。

伏せきれないなら、伏せる振りをやめて、**出さない側に寄せる。**
上の節の「置き場所で分ける」のほうが強い。

### 伏せる基準は覚えられる。伏せる理由は、当て直さないと外れる

2026-09-19、開発系が同じ日に2か所で同じ間違いをした。

| 場所 | 間違い |
|---|---|
| 升の伏せ方 | 伏せる升の2つめに **0件の升**を選んでいた |
| 率の伏せ方 | 0件の率を **人口の小ささ**で伏せていた |

どちらも「**伏せる基準を、伏せる理由から切り離して当てた**」形。
基準（1〜2件／人口500未満）は覚えていて、
理由（引き算で件数が戻るから）を毎回当て直していない。
**0件は、理由のほうで必ず外れる。**

基準は数字なので覚えられる。理由は文なので覚えられない。だから
**基準を書く行の、すぐ隣に理由を書く。** 離して書くと、基準だけが運ばれていく。

同じ日、大型店日報の `suppress_rate()` も同じだった。しかもこちらは、
**docstring に「0件は伏せない」と正しく書いてあり、その3行下のコードが
人口を先に見ていた。** 書いた本人が、書いた直後に外していた。
**docstring が正しいことは、コードが正しいことの証拠にならない。**
証拠になるのは検査だけ（9節「書いた検査が鳴らないのが、いちばんこわい」）。

そして**その検査も、違反のほうを固定していた**——
`suppress_rate(0, 400)` が `True` であることを `eq(..., True)` で
期待値に書いていた。開発系の `tests/` にも、同じ行が同じ形であった。
**基準だけを覚えて書くと、実装と検査が同じ向きにずれる。**
2本あっても、同じ人が同じ日に同じ理由で書いたなら、確かめたことにならない。

### 伏せる理由と、出さない理由は別

ここまでの節は、伏せる話（個人が当たる・引き算で戻る）と、伏せた結果が
読めなくなる話（「ほとんどが伏せ字になる層」「中途半端に伏せるくらいなら、伏せない」）
でできている。理由はもう1つある。
**伏せる必要が無くても、母数が小さいと、出した値が読める数にならない。**

大型店日報が26年分の退店の一覧を作り、開店日までつながったのは3件だった（3.5）。
平均在店年数は出さないと決めた（2026-09-19）。個票を全部出しているので伏せても
守りにならず（6節）、伏せる側の理由は無い。それでも出さない。
3件の平均は、一覧全体について何も言っていない。

    伏せる    個人が当たる。引き算で戻る        → 値を null にして、伏せたと分かる形にする
    出さない  母数が足りず、読める値にならない  → その値を計算して載せない

**2つを混ぜると、伏せ字のフラグが立っていないものは全部出してよい、と読める。**

3.3 の「測る前に、外れたときにどうするかを決めておく」とは軸が違う。あちらは
外れた結果にも値打ちがあると言っている。分けるのは、外れたかどうかではなく、
母数が足りるかどうか。外れていても母数が足りれば出す。当たっていても
母数が足りなければ出さない。

3.5 の「空のまま持っておく欄」とも別。あちらはまだ入っていない事実なので、
入る日が来れば埋まる。こちらは母数から出す計算なので、母数が増えるまで出せない。
1節の「母数が3件では統計にならないのは、時間を含んでいても同じ」は、これを
時間の側から言ったもの。

### 3.3 評価しない

事実と、事実から機械的に出る数字だけを出す。

- 点数・順位・格付け・「安全」「危険」「おすすめ」「ワースト」は出さない。
- 地図の色分けを **分位（quantile）で切らない。** 分位は順位そのもの。
  必ず**固定の絶対値**で階級を切る。
- 誤読されやすい数字には、必ずその場に注記を添える
  （例：認知件数は通報されたものだけ／夜間人口を分母にしているので商業地は大きく出る）。

### 同じデータでも、見出しで性質が変わる

出している値がまったく同じでも、**何と名づけるか**でデータの性質が変わる。

    「設置者と小売業者が別の届出の一覧」   → 公示情報をそのまま並べたもの
    「賃貸物件リスト」                     → 営業に使う名簿

**中身は1バイトも違わないのに、後者は 3.1 と 7節が禁じている側に近づく。**

だから、見出し・タイトル・説明文を書くときは、
**そのデータが何であるかを書く。何に使えるかではなく。**

- 使い道を見出しにすると、**使う人の目的がデータの性質になる**
- 「◯◯に使えます」は、こちらが決めることではない。読む人が決める
- 3.3 の「評価しない」と同じ形。**評価も用途も、こちらは足さない**

**断定にも同じことが言える。** 同じ例で、
「設置者と小売業者が別＝**貸している物件**」と書くのは行き過ぎだった。
デベロッパーと核テナントの関係、同じ企業グループ内で会社が分かれている形も
同じように見える。**「建物を用意した人と店をやる人が別」までが、データが
言っていること。** その先は読む人が判断する（2026-09-18）。

### 誰のために作ったかは書いてよい。何に使えるかは書かない

上の「そのデータが何であるかを書く。何に使えるかではなく」が止めているのは
使い道のほうで、**誰のために作ったかまでは止めていない。**

    「治安のいい町丁目が分かります」               → 直す。評価になっている（3.3）
    「住まいを探している人が、町丁目ごとの
      窃盗の統計を地図で見られるサイトです」       → 直さない。できることを書いている

「見られる」は用途ではなく、できること。「◯◯に使えます」は読む人が決めることだが、
「誰に向けて作ったか」はこちらが決めたことそのもので、読む人の目的を先回りしていない。
1節は「扱う制度も読者も別」と、4つのサイトの読者が違うことを事実として書いている。
サイトの側がそれを名乗っても、データに足したものは無い。

**順番は効く。何であるかを先に、誰のためかを後に。**

    ○ 町丁目ごとの窃盗の統計を地図にしたもの。住まいを探している人が見られる
    × 住まい探しのためのサイト。中身は町丁目ごとの窃盗の統計

同じ2文でも、読む人が最初に受け取るものが「用途」か「データの正体」かで変わる。
2026-09-19 に街頭窃盗統計の公開 README の書き出しをこの順に直した。
読者の名指しは消していない。**消すのではなく、順番。**

  **検査を足すときに、見る範囲も決める。** 見出しを数える検査が `<script>` の
  中の文字列を見出しとして拾い、「画面に出る不具合かもしれない」と報告された。
  不具合ではなかった（2026-09-19）。script の中を見るか、コメントの中を見るかは、
  足すときに決める。鳴ってから除外を1語ずつ足すのは、この節のあとの
  「検査の範囲は許可リストで決める」が応急処置と呼んでいるのと同じ形。

- 3.3 の隣の「同じデータでも、見出しで性質が変わる」は「**何に使えるか**は
  書かない」と言っているが、**誰のために作ったか**を書いてよいかは言って
  いなかった。街頭窃盗統計の公開 README の書き出しが「住まいを探している人が、
  町丁目ごとの窃盗の統計を地図で見られるサイトです」で、規則が説明文にも
  掛かるので直すべきかと聞いてきた
  → 「誰のために作ったかは書いてよい。何に使えるかは書かない」を隣に足した。
  「見られる」は用途ではなく、できること。**消すのではなく、何であるかを先に、
  誰のためかを後にする。** 1節が「扱う制度も読者も別」と書いているのとも
  噛み合う（2026-09-19・街頭窃盗統計）

- 9 は「常に鳴る見張りは、鳴らない見張りと同じくらい役に立たない」と書いて
  いるが、**見る範囲を、検査を足すときに決める**とは書いていなかった。
  見出しを数える検査が `<script>` の中の文字列を拾い、画面に出る不具合かも
  しれないと報告された。不具合ではなかった
  → 新しい節は立てず、その場に「検査を足すときに、見る範囲も決める」を足した。
  誤報の話は9節に既にあるので重ねず、「検査の範囲は許可リストで決める」に
  寄せた（同日・街頭窃盗統計）

### 締切は並べる。急がせない

上の節「同じデータでも、見出しで性質が変わる」の系。

補助金の受付は、予算が尽きると締め切られる（3.5「終わった・消えたを記録する」）。
締切のあるものを並べると、見出しが**読む人を急がせる側に倒れやすい。**

    「受付終了日が今月のもの」    → 公表されている事実を並べたもの
    「今月中に急いで」            → 読む人の行動を急がせるもの

出している一覧は同じ。違うのは名づけだけ。
後者は 3.3 の「評価しない」を越えている。評価語は1つも使っていないので、
3.3 が並べている語（点数・順位・格付け・「安全」「危険」「おすすめ」「ワースト」）
には引っかからない。それでも越えている。
**評価は「こちらが足さない」、煽りは「読む人を動かそうとしない」。** 別の話。

締切が動くことも効く。公表された終了日はあとで変わる（延長・前倒し。3.5）。
延長されたとき、事実を並べた見出しはそのままでよい。
急がせた見出しだけが、残って間違いになる。

- 見出しには、そのデータが何であるかを書く。読む人への呼びかけを入れない
- 残り日数を出すなら、日付から機械で出た数字として出す
  （3.3 の「事実から機械的に出る数字だけを出す」）。
  「あと3日」に「お早めに」を足さない
- 3.4 の「掲載期限が近いものを警告する」は**こちら向けの催促**。
  同じ文面を読む人のページに出すと、煽りになる

（2026-09-19・5サイト目の住宅系補助金の設計で出た）

### 予測を出すサイトは、予測の成績も出す

上の節は「測る前に決める」話。ここは、出すと決めて出したあとの話。

予測・見込み・予兆を出すと、当たったものだけが手元に残る。
外れたものは古くなって落ち、ページの上には当たったものが積む。
誰も嘘を書いていないのに、**当たり続けているように見える。**

- 外れた予測は、当たった予測と**同じ場所に、同じ大きさで**残す。
  別ページに移す・小さく載せる・過去ログに畳むのは、消すのと同じ
- 予測には、出した日と、答え合わせをする日を先に入れる。
  その日が来たら、当たり外れに関係なく結果を書く
- 外れが1つも無い予測の一覧を見たら、まず残し方を疑う

上の節の「外れたときに引っ込める設計にしておく」は、**測る前の企画のほう。**
出す前なら引っ込めてよい。出したあとの予測を引っ込めるのは、別の話。

母数が足りなければ出さないのは、ここでも変わらない。
3.2 の「伏せる理由と、出さない理由は別」が、外れたかどうかと母数が足りるか
どうかは軸が違うと書いている。出すと決めていても、母数のほうで落ちる。

補助金に限らない。予測・見込み・予兆を出すサイト全部に効く。
大型店日報は「営業時間の変更が撤退の予兆になるか」を調べる予定で、
外れた結果も出すと先に決めてある（2026-09-19）。

### 測る前に、外れたときにどうするかを決めておく

「こういう関係があるはずだ」と思って測るとき、**外れた場合にその結果を
出すかどうかを、測る前に決める。**

決めずに測ると、**当たった測定だけが表に出る。** 外れたものは黙って
引き出しに入り、読む人からは「測ったら当たった」ようにしか見えない。
これは 3.3 の「評価しない」と同じ形で、**都合のよい結果だけを出すのは、
評価を足すのと変わらない。**

**外れた結果にも値打ちがある。**

    「営業時間を短縮した店のうち、3年以内に閉店したのは 5% だった」

5% でも、**誰も出していない数字**。予兆にならなかったという発見も、
時間をかけて測った人にしか言えない。

**当たること前提で作ると、引っ込みがつかなくなる。**
外れたときに引っ込める設計にしておくと、外れても損にならない
（2026-09-18・5サイト目の設計をしている側の指摘）。

### 3.4 取得の作法

**断られたら、そこで打ち切る。回り込まない。**

- `robots.txt` が拒否していたら取りに行かない。人の手か、別の正規ルートに回す。
- 同時接続は **1本**。リクエスト間隔は **5秒以上**。
- `429` / `503` / 待機列が返ったら、**押し込まずにその回は中止**して次回に回す。リトライで突破しない。
- User-Agent に連絡先を入れる：

  ```
  kujiraya archive bot (+<サイトのaboutページURL>; <連絡フォームURL>)
  ```

  ※ 名乗りの続きは下。先に、取りに行く側の作りについて2つ。

- **URL を決め打ちしない。一覧ページから辿る。**
  相手のページの作りは変わる。決め打ちした URL は、変わった日に 404 を踏むか、
  もっと悪いと**別のものを取ってくる。** 一覧ページを読んで、そこから辿る。
  辿れなかったら、**取りに行かずにそう報告する。**「たぶんここだろう」で叩かない。

- **届かない相手のことは、報告に実物を持って帰る。**
  取りに行く場所と、コードを書く場所が違うことがある。**書く側から相手に
  届かないなら、報告に入っていないものは永久に分からない。**

  2026-09-19、大型店日報で国交省のデータを取りに行った。1回目の報告は
  「zip のリンクが0本。見つからなかった」だけで、**なぜ0本なのかを調べる
  手がかりが何も無かった。** 報告に足したもの：

      HTTP の状態・Content-Type・バイト数
      **飛ばされた先**（最後の URL が違えばそう書く）
      title ／ href・src・form の数と、form の中身
      href の拡張子の内訳（無いのか、別の形なのか）
      探している語を含む href を、**拡張子を問わず**拾う
      ページの実物そのもの（金庫に置く）

  **1本目で空振りでも、そこで終わりにしない。** 上の階層も見て、何が
  置いてあるかを報告に残す。見つかった時点で止める。
  手で回す相手が1人なら、**1回の実行でなるべく多く持って帰る。**

  「見つからなかった」は、3.5 の「空なら『つながらなかった』と分かるだけで済む」
  とは違う。あちらは**値が無いこと自体が答え**。こちらは**次に何をすればいいかが
  答えで、それが入っていない。**

  サイトがまだ公開されていないうちは、**404 になる URL を入れない。**
  サイトがまだ公開されていないうちは、**404 になる URL を入れない。**
  確認できない名乗りは、名乗らないより不審に見える。
  about ページができるまでは、屋号・サイト名・連絡フォームの URL だけにする：

  ```
  kujiraya archive bot (keibai-toukei; https://forms.gle/xxxxx)
  ```

  URL は設定の1か所にだけ書き、公開したら about ページの URL に差し替える。

- **頻度は「中身の変わり方」と「相手が誰か」の両方で決める。**
  - 公報・告示など、発行されたら中身が変わらないもの → **月2回**
  - 縦覧一覧など、日々書き換わるもの → 毎日
  - 「掲載期間が3か月」なら、必要なのは「3か月以内に1回」であって毎日ではない。
  - **過去分の取り込み（積み直し）は例外。** 1日の上限（大型店日報の兵庫県公報は80号）・
    5秒・同時1本を守れば毎日でよい。追いついたら（未読が新着だけになったら）月2回に戻す。
    戻すのは人の手ではなくコードで（大型店日報は `koho_pdf.py` が未読20号以下になったら
    自動的に1日・15日だけにする。手で押したときは日に関係なく取りに行く）

  ただしこれは**自治体のサーバーに対する決まり**。
  姉妹サイトが GitHub に置いた生データを読むときは、**毎日でよい**。
  相手が違うし（GitHub は大量アクセスを前提にした置き場）、
  上流が毎日更新しているので、月2回にすると新着がそのぶん遅れるだけになる。
  「公報だから月2回」ではなく「兵庫県のサーバーだから月2回」と考える。

- **同じ一次情報を、2つのサイトが別々に取りに行かない。取得は1系統にする。**
  すでに姉妹サイトが取っているものは、そのサイトが公開している生データを読む。
  相手のサーバーへのアクセスが2倍になるのは、単純に失礼。

  | 一次情報 | 取っているサイト | 読み方 |
  |---|---|---|
  | 兵庫県公報（全文・2007年〜。号外を含む） | 大型店日報 | `https://raw.githubusercontent.com/VirgoB77/ogataten-nippo/main/data/koho/full/<日付>-<号>.txt.gz`（gzip。号外は `<日付>-g<n>.txt.gz`：「号外」が g1、「第2号外」が g2。号の一覧は同じリポジトリの `data/koho/issues.json`） |

  共有する側は、**抜き出したあとの形ではなく全文を残す。**
  抜粋だけ残すと、あとから別の告示が要るようになったときに全部取り直しになる。
  大型店日報が実際にこれをやってしまい、737号を取り直すことになった。

  新しく共有できるものができたら、この表に足す。

- `robots.txt` はクローラへのお願いであって、**正規の提供ルートを塞ぐものではない。**
  有償頒布（定期購読）、データ提供の申し出、情報公開請求、国立国会図書館 WARP など、
  正面から取れる道がないか先に調べる。購読できるなら、こちらはクローラではなく購読者になる。

- 人の手に回す工程を作るときは、**機械に催促させる**。人は必ず忘れる。
  - 人に渡すのは「該当する号のURLだけ」。全件を人に見せない。
  - 毎回のレポートに不足分を出し続ける（例：`2026年3月：第12号・第15号が未取得`）。
  - 掲載期限が近いものを警告する（例：`第12号はあと21日で閲覧できなくなります`）。
  - 取り込み済みは台帳に記録し、二度と催促しない。

### 3.5 出典

- **全レコードに `source_url` と `fetched_on` を必ず付ける。** 例外なし。
- 取得先ごとに利用規約を個別に読み、出典表記の指定を `sources.json` に記録する。
- 公報の告示・公告は、著作権法13条により著作物にならない。いちばん安全な一次情報。
- 「政府標準利用規約2.0」は CC BY 4.0 と互換。出典表記をすれば使える。

### 終わった・消えたを記録する

一次情報は消える。役所の縦覧は数か月で消え、補助金の受付は予算が尽きると
締め切られ、公告は年度で書き換わる。**こちらのサイトは消えない。**
だから「まだ生きているか」は、こちらが記録しなければ誰にも言えなくなる。

3つの欄を持つ。使わない欄は `null`。

    closed_on        公表された終了日（公表されているなら。なければ null）
    last_seen_open   まだ続いていると確認できた最後の日
    closed_detected  終わったと分かった日

**`closed_detected` に公表日を入れない。** 1つの欄に2つの意味が混ざり、
あとから見て「終わった日」なのか「気づいた日」なのか分からなくなる。
`as_of` と `fetched_on` で一度踏んだのと同じ形。
公表された終了日は**あとで変わる**（延長・前倒し）ので、別の欄に持たないと
変更を追えない。

#### 消えたものを数えるには、消える前の一覧が要る

終わりを「消えたこと」で知るサイトは、**前回の一覧が無いと何も言えない。**
今回いなくなったものを見つけるには、前回いたことが記録されていないといけない。

そして**消える理由は1つではない。**

    もう出てこない      手続きが止まった・終わった
    次にまた出てくる    今回は決まらず、次の期間に回った

**消えた日には、どちらか決められない。** 再登場するかどうかは時間が決める。
その日に片方へ倒すと、もう片方がそれに化ける。そして
**化けたあとでは、照らし合わせる相手がもう存在しない**（4節）。
伏せ字や語彙の穴は、あとから記録を見れば分かる。これは分からない。

だから順番が決まる。**母集団の保存が先、判断はあと。**

    公告に出た時点の一覧を、まるごと残す
    消えた行は捨てず、消えたと分かった日を付けて残す
    再登場したかどうかは、次の期間の一覧と突き合わせて決める

**鍵に「その回だけのもの」を入れないこと。** 開札日や回次を鍵に混ぜると、
同じものが期間をまたぐたびに別の鍵になり、再登場が追えなくなる。
「鍵にはあとから変わらないものだけを入れる」（9節）が、ここで効く。

#### 終了は点ではなく、区間

毎日見ていなければ、`closed_detected` は「最後に見た日」でしかない。
月1回なら、実際に終わったのは最大1か月前。

    last_seen_open   2026-08-20   この日はまだ続いていた
    closed_detected  2026-09-17   この日に終わったと分かった
    → 終わったのは 8/20 〜 9/17 のあいだ

**終了日が公表されるものでも、区間を捨てない。** 捨てると「予定どおり
終わったか」を確かめる手立てが無くなる。開札日が延期されることは実際にある。

#### 区間の幅は、こちらの弱点の数字でもある

幅は巡回の間隔で決まる。読む人は粒度を知る権利があるので、**出す**
（`fetched_on` を必須にしているのと同じ理屈）。

そのうえで、**幅が広がっていたら巡回が止まっている**と先に分かる。
毎日回していれば幅は1日のはず。3か月に広がっていたら、その数字が教えてくれる。
3.2 の「余裕も出す」と同じ形。**数字を出しておくと、細ったときに気づける。**

#### 根拠のページは、あとで消える

「どのページのどの文言か」を残すのは正しい。ただし**根拠として指している
ページが、次の年度に書き換わる。** URL と文言だけでは1年後に確かめられない。

**検知した時点のページの写しを取る**（9節「生データを全部残す」）。
文言はそこから引く。府のページが更新されて以前の記述を示せなくなったことが
実際にあった。**写しを取っていた分だけが残っている。**

#### 削除される場合のほうが危ない

「令和◯年度の受付は終了しました」と1行残す役所と、**ページごと消える**役所がある。
後者では、**写しが唯一の記録になる。** そして写しは「消える前」に取れていないと
意味がない。**巡回の頻度が、そのまま記録の完全性になる。**

頻度は上げるより下げるほうが安全なので、**最初から短い間隔で始める。**
月1で始めて後から毎日にしても、その間に消えた分は取り戻せない。

### いまつながらなくても、これからつながる形にしておく

上の3つの欄は全部が終わり側で、**始まり側の欄が1つも無い。**
だから1節の「この場所は何年もったか」は、この3つだけでは出ない。
終わった日は分かるが、始まった日がどこにも無い。4つめを足す。

    opened_on        公表された開始日（公表されているなら。なければ null）

過去の分は、あとから取りに行っても埋まらない。大型店日報が 2026-09-19 に
26年分の退店の一覧を作り、開店日までつながったのは3件だった。
始まりの側の届出が手元に無い年の分は、つなぎようがない。

**つながらないのは過去だけ。今日以降に始まりを取れた分は、閉じるときにつながる。**
だから欄は空のまま持っておく。欄ごと消すと、埋まる日が来てから遡って足すことになり、
その間に閉じた分だけ穴があく。埋まらない過去の分は、埋まらないままでよい。

ここで増えるのは「いまは埋められないが、これから埋まる欄」。
どこで切れるかはサイトごとに違うので、README に
「いつより前の分は埋まらないか」を1行書く。

4節の③が `addr_key_town` で同じことをしている。決まらないものは空にして記録し、
推測で埋めない。9節の「決めてから当てるまでの間を、書いておく」も同じ形だが、
あちらは名前と URL、こちらはデータの欄。

6節の「空の `index.json` を置かない」とは別の話。線は、**ファイル全体が空か、
レコードの1欄が空か**で引く。ファイルごと無いと「まだ作っていない」のか
「そもそも乗らない」のかが見分けられない。欄が空なのは、6節の「値がないキーは
省略せず、空文字か `null` を入れる」が最初から言っている側で、7節の「『まだ無い』と
書いた記録は、記録が無いより悪い」にも当たらない。**空の欄は「無い」と言っていない。**

年数が出なくても、一覧そのものの値打ちは1節の通りで変わらない。
年数はそこに足すもので、無いと成り立たないものではない。

## 4. `common/addr.py`

住所を4サイトで突き合わせるための正規化。**Python標準ライブラリのみ**で書く。
ファイル1本で完結させ、各リポジトリにコピーして使う（submodule も pip も使わない）。
先頭に「正本は ogataten-nippo/docs/kyotsu-shiyo.md」とコメントを書く。

### 関数

```python
def normalize(pref: str, city: str, addr: str) -> dict:
    """住所を正規化して、突き合わせ用のキーを返す。"""

def split_city(addr: str, pref: str = "", city: str = "") -> dict:
    """1列に入った住所から、都道府県・市区町村・残りを切り出す。

    pref / city は**ヒント**。切れなかった欄は空文字にする。
    呼ぶ側の市名で黙って埋めない。次の節を見ること。"""
```

`split_city()` の戻り値：

| キー | 例 | 説明 |
|---|---|---|
| `pref` | `"岡山県"` | 都道府県名。決まらなければ空文字 |
| `city` | `"備前市"` | 市区町村名。決まらなければ空文字 |
| `rest` | `"伊部1-2-3"` | 市区町村より後ろ。`normalize()` の引数 `addr` に渡せる形 |
| `city_precision` | — | `city` を**どうやって決めたか**。下の3つを区別する |

**`pref` を捨てない。** 同名の町村があるので、都道府県が決まらないと
`city_code_of()` が引けない。そして1列の住所は「岡山県備前市……」のように
**都道府県まで書いてあることがある。** `(city, rest)` だけ返す形にすると、
せっかく読めた都道府県をその場で捨てて、次の段で引けなくなる。

**ヒントを受ける。** 市が自分のページに自分の市名を書かないことがある
（大阪市の一覧が「矢田五丁目」とだけ書く）。文字列だけでは切れないので、
収集先が分かっているならヒントとして渡す。渡さないと、その行が丸ごと空になる。

**ヒントで埋めたことを、埋めていないことと区別する。** これが `city_precision`。
次の節のとおり、市は自分の市の外の土地も売るので、
**ヒントで補った行は「たぶんその市」でしかない。**
文字列から切れた行と同じ確かさで扱ってはいけない。区別が要るのは3つ：

1. **住所そのものから切れた**——いちばん確か
2. **ヒントで補った**——たぶんその市。突き合わせには使えるが、
   食い違いが出たら住所の側を信じる
3. **決まらなかった**——空文字のまま。埋めない

**`city_precision` の値の名前は、まだこの文書に写していない**
（開発系の実装が持っている。次の報告で写す。2026-09-19）。


戻り値：

| キー | 例 | 説明 |
|---|---|---|
| `pref` | `"大阪府"` | 都道府県名 |
| `city` | `"大阪市北区"` | 市区町村名 |
| `city_code` | `"27127"` | 全国地方公共団体コード5桁。総務省の一覧を `ref_jis.py` が `data/ref/jis-codes.json` に取る（90日に1回）。記憶で書かない |
| `town` | `"梅田1"` | 町丁目。**丁目を含む** |
| `addr` | `"大阪市北区梅田1-1-1"` | 整形後の表示用住所 |
| `addr_key` | `"27127\|梅田1-1-1"` | 番地までの突き合わせキー |
| `addr_key_town` | `"27127\|梅田1"` | 町丁目までの突き合わせキー |

### 引数の `addr` と、戻り値の `addr` は別のもの

同じ名前だが、入りと出では指すものが違う。

- **引数の `addr`** は「市区町村より後ろ」を想定する。ただし役所の表は
  「所在地」の1列に都道府県名や市区町村名ごと入れていることがある。
  **先頭に付いていたら落とす**（`city` と重複させないため）。
  政令市の区も見る。`city` が `"堺市西区"` なら、`"西区"` だけの先頭一致も落とす
- **戻り値の `addr`** は**表示用で、市区町村名を含む**（`"大阪市北区梅田1-1-1"`）。
  落とした市区町村名を `city` から足し直した形。そのまま画面に出せる

実装はそうなっていたが、**この文書に書いていなかった**（2026-09-18 に開発系が
「4節の `addr` に市区町村名を含むのか」と聞いてきて分かった）。

### 収集先の市を、そのまま住所に被せない

「所在地」1列で来る表では、市区町村名が**入っている行と入っていない行が混ざる。**
入っていない行を、**その表を配っている市の名前で埋めてはいけない。**

市は、自分の市の外にある土地も売る。大阪市の一覧に、他県の土地が入っていた
（開発系・2026-09-19、実測）。収集先の市を被せると、その行は
**この世に無い住所**になり、しかも形は正しいので検査を通る。

`split_city()` で1列から市区町村名を切り出し、**切れなかった行は `city` を空のまま**
にする。空のままなら「繋がらなかった」として残るが、間違った市を被せると
別の場所と**まとまってしまい、あとから見分けられない**
（この節の「繋がらなかったことは残るが、まとまってしまったことは残らない」と同じ理由）。

開発系で当てたところ、456件のうち **454件**が切れた。残りの2件は市が本当に
書かれていない行で、空のままにした。**2件を埋めるために、454件を汚さない。**

#### 「被せない」は「食い違いを被せない」

上を字義どおり「呼ぶ側の市は一切使わない」と読むと、行き過ぎる。
役所の表には「**見出しに市、欄に番地**」という**正しい分かれ方**があり、
そこで市を使わないと、読める行まで落ちる。線は3本に分ける。

| 住所の側 | どうする |
|---|---|
| **別の市を名乗っている** | **被せない。止める。** これが食い違い |
| **市を名乗っていない** | 呼ぶ側の市を使ってよい。ただし**使ったと記録する**（`city_precision`） |
| **同じ市を名乗っている** | 落として、呼ぶ側の市を使う。いちばん確か |

真ん中を許す条件は1つ。**その表で食い違いが出ていないことを、測ったとき。**
開発系は実データ106行のうち105行で住所からも同じ市が読め、**食い違い0件**だった。
大型店日報も4,809件で**0件**だった（どちらも 2026-09-19）。

**ただし「測った」は「そのときの一覧では」の意味しかない。**
出どころは、ある日から別の市の土地を載せはじめる。
だから**食い違いの数は、一度数えて終わりにせず、0のままかを検査で見張る。**
0でなくなった日に止まるようにしておく。測っただけでは、次の一覧で破れる。

#### 別の市を名乗っていたら、繋げずに止める

`normalize()` は、住所の先頭に付いた都道府県名・市区町村名を落とす。
**落とせなかったときに、そのまま繋げてはいけない。**

```
normalize("大阪府", "大阪市北区", "兵庫県西宮市甲子園町1-1")
  → "大阪市北区兵庫県西宮市甲子園町1-1" / コードは大阪市北区
```

**形は正しいので検査を通るのに、この世に無い住所。** キーは大阪市北区で作られ、
西宮市の土地が大阪市北区の升に入る。開発系と大型店日報の両方が、
**同じ形で無防備だった**（2026-09-19。どちらも呼ぶ側が住所から市を読んでいたので、
現に踏んではいなかった）。

見るのは**都道府県名**と、**「市」で終わる市名**だけでよい。
町丁目の名前はこの2つと衝突しない（「甲子園町」で終わる市は無い）。
**区・町・村は町丁目と衝突しうるので見ない**——**見落とすほうに倒す。**
守りが誤って止めるより、呼ぶ側の読みで防ぐほうに任せる。

**見張りは、知っている名前しか見つけられない。**
市区町村コードの一覧に載っていない市は、食い違っていても素通りする
（大型店日報の検査は、この理由で「堺市」を最初は見つけられなかった）。

### `town` の決め方

**「最初のハイフンより前」では決まらない。** 文字列だけでは原理的に区別できない
ケースがあるので、2段階にする。

```
梅田1-1-1       の最初の 1  = 丁目        → town は 梅田1
上ケ原2番町3-5   の 3        = 番地の始まり → town は 上ケ原2番町
```

どちらも「町名のあとの数字」で、見た目では区別がつかない。

**① 正規化で自分がハイフンにした場所があれば、その手前まで（確実）**

`丁目` `番地` `番` `号` をハイフンに置き換えたとき、**どこを置き換えたかは自分が
知っている**。最初に置き換えた場所の手前が `town`。

```
梅田一丁目1番1号 → 梅田1-1-1     「丁目」を置き換えた → town は 梅田1
潮江1丁目3番1号  → 潮江1-3-1     同上                → town は 潮江1
```

日本の住所のほとんどはこれで決まる。入力にもとからあったハイフンと
取り違えないこと。**置き換えた位置を覚えておく**のがこつ。

**② 1つも置き換えなかったときは、町丁目の一覧で最長一致**

`上ケ原二番町3-5` は「番」の直後が「町」なので、1つも置き換えが起きない。
この形は文字列だけでは決められないので、**市区町村コードごとの町丁目の一覧**を
引いて、いちばん長く一致する町名を採る。

一覧は `data/` に同梱する（`city_code` の一覧と同じ扱い）。
出どころは国土交通省の位置参照情報（大字・町丁目レベル）などを調べて決める。
大阪府・兵庫県だけなら1万件ほどで、数百KBに収まる。

**③ ①でも②でも決まらないときは、`addr_key_town` を空にして記録する**

推測で埋めない。空文字にして `data/parse-unknown.md` に出す（9節）。
黙って間違えた町丁目でつなぐと、**別の場所の記録が混ざる**。
空なら「つながらなかった」と分かるだけで済む。

**丁目は必ず含める。** 「梅田」でまとめてはいけない。

- 犯罪統計マップは丁目ごとに数える。警察のオープンデータも国勢調査の人口も丁目単位。
  「梅田」でまとめると、件数も人口も3つの丁目が混ざって意味をなさない
- 大阪市北区梅田は1〜3丁目あり、駅の北と南ほど違う場所になる
- そもそも「町丁目」という言葉が「丁目まで」を指す

### 正規化のルール

1. 全角英数 → 半角
2. 漢数字 → 算用数字（`一丁目` → `1丁目`）
3. `丁目` `番地` `番` `号` → ハイフン。
   ただし **直後が数字か、文字列の終わりのときだけ。**
   素朴に全部を置き換えると町名が壊れる：

   ```
   上ケ原2番町3-5  →  上ケ原2-町3-5   ← 「番町」の番まで置き換えてしまう
   上ケ原2番町3-5  →  上ケ原2番町3-5   ← 直後が「町」なので置き換えない（正しい）
   梅田1丁目1番1号  →  梅田1-1-1
   ```
4. `大字` `字` を除去
5. 空白を除去
6. 建物名・部屋番号は `addr` には残し、`addr_key` からは除く

### なぜキーが2本あるか

出せる精度がサイトによって違う。

- 犯罪統計マップは町丁目までしか持たない
- 公有地売却・競売の跡地は、買主が個人なら町丁目までに丸める（3.1）
- 大型店日報・開発許可は番地まで持つ

精度の違うもの同士は `addr_key_town` で突き合わせる。
**両方のキーを必ず出す**こと。片方しか作れない場合は、もう片方を空文字にする。

### 町丁目で繋いだものは「同じ場所」ではなく「近い場所」

精度の違うもの同士は `addr_key_town` で突き合わせる（上の節）。
突き合わせはやめない。だが、突き合わさったものを同じ場所と呼ばない。
`addr_key_town` の一致は **「近い場所」であって「同じ場所」ではない**。

③（①でも②でも決まらないときは空にする）とは別の話。
③は町丁目を取り違えたときに別の場所が混ざる話で、ここは取り違えていない町丁目の話。
正しく埋まった `addr_key_town` どうしでも混ざる。

`town` は町丁目のこともあれば大字のこともある。
駅前なら1つの町丁目にビルが何棟も建ち、店が何十と入る。
同じ単位でも、**中に入るものの数が桁で違う。**

同じ場所と名乗るには、住所以外の鍵をもう1本足す。店名、法人名、届出の番号。
足せないときは繋ぐのをやめるのではなく、**「近い場所」として出す。**
同じ行にまとめない。同じ主体として数えない。
町丁目までしか持たないサイトは、常にこちら側になる。

3.1 で町丁目まで丸めたレコードは、丸めた結果の鍵で繋ぐことになる。
繋いだ先の番地を、その当事者の住所として出さない
（3.1「別のソースから補ったり、推測で地番を足したりしない」）。

繋いだ側は、**どちらの鍵で繋いだかを自分の出力に残す**
（大型店日報の退店一覧は `match` に「番地+店名」「町丁目+店名」と書く）。
`index.json` のレコードには欄を足さない。6節のスキーマは4サイトでそろえる側で、
両方のキーは元から出ている。横断ハブは、どちらで当たったかを自分で言える。

2026-09-19 に大型店日報で測った。

- 廃止の届出を新設の届出に町丁目だけで突き合わせたら55件つながった。
  店名まで一致したのは9件。残り46件は別の店だった
- 同じ日、設置者と小売業者の一覧をまとめる鍵を番地から町丁目に落として作り直したら、
  店の数が76減った。**別の店に吸われたのは16で、残り60は `addr_key_town` が
  空だったために落ちただけ**（③）。減った数をまとめて粒度のせいにしない

**ひとつの数字の動きを、ひとつの原因のせいにしない。** 最初は76を全部
「別の店に吸われた」と読んで、そう書いて出した。分けて数えたら5分の1だった。

大型店日報だけの話ではない。横断ハブは住所を鍵にする（6節）ので、
町丁目までしか持たないサイトを番地を持つサイトと並べるところ全部にかかる。

### 繋がらなかったことは残るが、まとまってしまったことは残らない

上の2つの測定は、どちらも町丁目まで丸めた話だが、**気づけ方が逆になる。**

    突き合わせ    当たらなかった行が、当たらないまま一覧に残る
    まとめ直し    行そのものが消えて、数が減るだけになる

廃止と新設の突き合わせは、繋がらなかった行を捨てない。何で当たったかの欄を
空にして残すので、どれが繋がっていないかをあとから読める。
まとめ直しは違う。別の店に吸われた行も、`addr_key_town` が空で落ちた行も、
出来上がった一覧には出てこない。残るのは減ったあとの数だけ。
上の16と60が分かれたのは、**まとめる前の鍵でもう一度数えたから**であって、
出来上がった一覧を読んだからではない。

出した数が正しいかどうかは、出した数からは読めない。
**だから2つの方法で数えて、突き合わせる。**
まとめる鍵を変えるときは、変える前の鍵でも数えて、差の行き先を
原因ごとに分ける（上の節）。片方だけでは、差があることにも気づかない。

- 当たらなかった行を消さない。何で当たったかの欄を空のまま残す
  （3.1「行は消さず、落とした理由を残す」と同じ形）
- 欄に入れる語は固定し、同じ意味の別の言い方に置き換えない
  （9節「規則を満たしていても、規則の言葉で書く」）。検査は語そのものを見る。
  大型店日報の `test_privacy.py` は `match` に「店名」の2文字が入っているかで、
  店名の一致なしに在店年数を出していないかを見ている

### テスト

`tests/` に単体テストを置き、**ワークフローの最初のステップで走らせる**。
落ちたらそこで止まり、取りに行かない。最低限これは通すこと：

期待値は**必ず具体的に書く。** 「キーが両方出ること」のような書き方だと、
食い違いが見つからない。

```
normalize("大阪府", "大阪市北区", "梅田一丁目１番１号")
  addr           "大阪市北区梅田1-1-1"
  town           "梅田1"
  addr_key       "27127|梅田1-1-1"
  addr_key_town  "27127|梅田1"          ← 丁目を含む

normalize("兵庫県", "尼崎市", "潮江1丁目3番1号")
  addr_key       "28202|潮江1-3-1"
  addr_key_town  "28202|潮江1"

normalize("兵庫県", "西宮市", "大字上ケ原　二番町3-5")
  addr_key       "28204|上ケ原2番町3-5"   ← 「番町」の番を置き換えない
  addr_key_town  "28204|上ケ原2番町"      ← ②の町丁目一覧で決まる
                                          一覧が無いうちは空文字にして記録する（③）
```

1件目・2件目は①で決まる。3件目は②が要る。

「上ケ原2番町3」のように途中で切ったものを入れてはいけない。

### 引数を足したら、渡す側も同じコミットで足す

`redact_name()` に `names` を足したとき、渡していたのは**テストだけ**だった。
本番の経路は、どこも渡していない。**テストだけが渡している引数は、本番では
無いのと同じ。** テストは通り、名札は付かない。

既定値のある引数は、この食い違いを何も鳴らさずに通す。だから
**引数を足すコミットに、渡す側の変更を同じコミットで入れる。**
入れられないなら、その引数はまだ足さない。

**呼ぶ側が1つも無いこともある。** 開発系の `redact_name()` は、画面を作って
いないので本番の呼び出しがゼロで、テストからしか呼ばれていない。
5節は「呼んでいなくても署名は置いてそろえる」と決めているので、それは正しい。
だが**そういう関数は、守っているように見えて何も守っていない。**
次に読む人が「ここを通っているから安全」と思い込む。
**呼ばれていない守りの関数には、呼ばれていないと書く。**
（3.1 の「伏せたことは、伏せたと書く」と同じ形。無いことは、無いと書く。）

これで済むのは、この引数が「気づくため」のものだから。
**もし安全性が引数に依存していたら、渡し忘れはそのまま穴になっていた。**
上の docstring で「names は戻り値を変えない」と先に決めてあるのは、
そのため（開発系・2026-09-19）。

**`residential_reason()` は 2026-09-18 に足した。** 3.1 の「人が住んでいる可能性が
あるものは個票にしない」を、人の判断ではなくコードで守るための層。
開発系が実装し、競売統計が「入札中物件は個票にしない」で同じ判断を持っていたため、
**5節の線3（2サイト目が要ると言ったら上げる）に当たった。**

判定に使う語。**当事者の語と同じで、4サイトぶんを合わせて持つ。**

```

  戸建 テラスハウス 文化住宅 宿舎 住居

  「宿舎」は「公務員宿舎」「独身宿舎」。国有財産・公有財産の売却に出る
  「住居」は用途の欄に「住居」と書かれる形（住居表示のことではない）

  部屋番号は3〜4桁で出る（「…12番13-1406号」「（◯◯◯◯211）」）

**「住宅」は地名や事業名にも出る**（「◯◯住宅第1地区」）。それでも入れる。
**落とす側に倒れるだけ**だから。

**ただし落としすぎない。「◯番街区」は住居表示の街区であって部屋番号ではない。**
ここまで落とすと**土地が1件も残らなくなる**。落としすぎていないかを測り、

**行を消さず、落とした理由を残す。** 集計には数えるので、
「個票にしない」という印を立てるだけにする。

**`masked()` は 2026-09-17 に足した。** それまで count 側を返す関数が無く、
3つのサイトが同じ判断をそれぞれ手で書いていた。たまたま3つとも合っていたので
誰も気づかなかった。**開発系の点検が「3.2 の count 側が無い」と指摘して見つかった。**

判断を1か所に置いたら、すぐ効いた。大型店日報に手書きの判断がもう1か所残っていて、
足した検査が即日それを見つけた（`build_site.py` の公報の表の合計）。

  個人と取り違えない。

### `common/` は、どこまで一致させるか

4節と5節は「各リポジトリにコピーして使う」と書いているが、**実際はかなり
分かれている。** 同じ役目で名前が違うもの（`is_corp` / `is_corporate`）、
片方にしか無いもの、行数が2倍違うもの
（2026-09-18 に開発系が4サイトを測って分かった）。

**全部を一致させるのは、無理だし目指さない。** データの性質が違うサイトに
使わない関数を置くと、**使っていないぶん、ずれに気づけない。**

線は3本。

| | どうするか |
|---|---|
| **この文書に署名があるもの** | **名前・引数・戻り値を一致させる。** 中身も同じにする |
| 同じ役目で名前が違うもの | **この文書の名前に寄せる**（`is_corporate` → `is_corp`） |
| 片方にしか無いもの | 各サイトの自由。ただし **2サイト目が要ると言ったら、この文書に上げる** |

3本目が効く。**2つのサイトが同じものを別々に書いた時点で、それは共通のもの。**
`masked()` がそうだった（3サイトが手で書いていて、たまたま合っていた）。

**呼んでいなくても、署名があるものは置いてそろえる。** 使っていない関数の
ずれは、走らせても気づけない。**次に使い始めた人が、古い版を使う。**

### 署名をそろえる検査は、名前だけでなく引数まで見る

線1は「**名前・引数・戻り値を一致させる**」と書いている。
だが検査が「**その名前の関数があるか**」しか見ていないと、
引数が違っていても通ってしまう。

**「あるか」を見る検査は、「合っているか」を見ていない。**
`masked()` が「使っていないから気づけなかった」のと同じ形
（2026-09-18 に開発系が自分の検査を直して分かった）。

署名の一致を見る検査は、**関数名と引数の並びの両方**を固定する。

### 当事者を指す列名

`is_party_column()` が見る語。**4サイトぶんを合わせて持つ。**

```
氏名 名義 代表者 代表取締役 届出者 申請者 設置者 小売業者 事業者 所有者 世帯主
落札者 落札者名 契約相手方 契約の相手方 買受人 譲受人
```

**語を含んでいても、名前の欄ではないものがある。**
「設置者対応」（設置者がどう応じたか）、「設置者意見」のように、
語のうしろに別の意味の語が来る形。**名前は列名の末尾に来る。**

新しい列名に出会ったサイトは、**2サイト目を待たずにここへ足す。**
当事者の語は**落とすと地番が出る側**なので、足すのは安全側。

### 「個人」に化けてはいけないもの

`is_corp()` が False を返しても、氏名とはかぎらない。次の3つは別に扱う。

| 実物 | 正体 | どうする |
|---|---|---|
| `未定` `未詳` `不明` `なし` `無し` `（未定）` `未定３者` `物品販売業を営む店舗` `―` | 名前ではない文言 | **そのまま出す。**「個人」に変えない |
| `大阪市北区角田町３番25号` | **列がずれて住所が入った** | 個人として扱う（安全側）。`parse-unknown.md` に出す |
| `三井住友ファイナンス` `大和ハウスリアルティ` | 法人名が**途中で切れた** | 個人として扱う（安全側）。ただし**置き換えや削除はしない** |

3行目は見分けがつく。**同じデータの中の別の名前の、先頭部分になっていたら、
それは切れた法人名であって人名ではない**（`三井住友ファイナンス` は
`三井住友ファイナンス＆リース株式会社` の頭）。
人名は、ほかの名前の頭にはならない。

これを見落として履歴から `三井住友ファイナンス` を消すと、
`＆リース株式会社` だけが残る。消す作業をするときは必ず先に調べること。

**テストで守る。** `privacy.py` を迂回した出力が1件でもあれば落ちる検査を書く
（例：出力JSON全体を走査して、個人名らしき値・伏せるべき率が残っていないか確認する）。
壊れたら、データを取りに行く前に止まる。

## 6. `index.json`

各サイトがサイトルートに出す、横断用のインデックス。
将来の横断ハブがこれを読んで、住所ごとの年表ページを作る。

### 住所ごとの年表に乗らないサイトは、`index.json` を出さない

`index.json` は **同じ住所を鍵にしてサイトを横断する**ための仕組み。
鍵が住所でないサイトは、この年表に乗らない。

| 鍵 | サイト | 横断ハブ |
|---|---|---|
| **住所** | 大型店日報・開発系・競売統計・街頭窃盗統計・民泊 | 乗る |
| **制度** | 住宅系補助金の自治体横断 | **乗らない** |
| **日付** | 補助金の予算消化率 | **乗らない** |

補助金の制度は、**土地ではなく人と世帯に紐づく。**
「この住所で何があったか」という問いに答えない。

**空の `index.json` を置かない。** 置くと、読む側が
「**まだ作っていない**」のか「**そもそも乗らない**」のかを見分けられない。
出さないほうが正直で、読む側も迷わない。
**出さない理由を README に1行書く**（何も言わずに無いのと、決めて無いのは違う）。

### 決まり

- `id` は `<サイトの接頭辞>:<source>:<date>:<連番>` の形。
  **接頭辞は `site` と同じでも、短い別名でもよい**（大型店日報は `site` が
  `ogataten-nippo` で接頭辞が `ogataten`）。**サイトをまたいで衝突しないこと**
  だけが要件で、一致は求めない。使う接頭辞は2節の表で確かめてから決め、
  **一度決めたら変えない**（9節「鍵にはあとから変わらないものだけを入れる」）。
  連番は日をまたいで安定しないので、届出ごとの安定した鍵（大型店日報は `key`）を
  連番の代わりに使ってよい。同じ届出は毎日同じ `id` になること。
- `kind` は `<制度>/<種別>` の形（`大店立地法/新設`、`開発許可/29条`、`公有地売却/落札`、`犯罪統計/侵入盗`）。
  **種別には段階も結果も入る。** どちらの語も9節でそろえる。
- `party` は**法人名のみ**。個人は**空文字**（`個人` という文字列を入れない）。
  `privacy.py` の `party_for_index()` を通した値を入れる。画面表示用の
  `redact_name()`（個人を `個人` と書くほう）と混ぜないこと。理由は 3.1。
- `party_kind` は `"corp"` / `"individual"` / `"undisclosed"` / `"none"` のいずれか。
  `party` が空のとき、その理由を機械が区別できるようにするために要る。

  | 値 | `party` が空な理由 | `addr` の粒度 |
  |---|---|---|
  | `corp` | （空でない） | 地番まで |
  | `individual` | 個人なので伏せた | 町丁目まで |
  | `undisclosed` | 一次情報の側が名前を載せていない | 地番まで |
  | `none` | そもそも当事者を持たない制度 | 地番まで |

  横断ハブで「法人が買った跡地」を絞るとき、`undisclosed` を `individual` に混ぜると
  取りこぼし、`none` に混ぜると意味が壊れる。4 つを分けること。
- `url` は**絶対URL**。相対パスにしない。
- `source_url` と `fetched_on` は必須。空にしない。
- 値がないキーは省略せず、空文字か `null` を入れる。キーの有無で分岐させない。
- 個票を出さないサイト（競売統計）は `records` を空にして、`counts_by_city` だけを出す。
- 個票を全部出しているサイト（大型店日報）では、升の伏せは守りにならない。読む側が
  `records` を数え直せば実数が分かるからだ。それでも升の形と伏せ方は同じにそろえる
  （横断ハブが4サイトを同じ道具で読めるように）。守りとして効くのは個票を出さないサイト。
- 升の期間は、伏せ字だらけにならない粗さにする（3.2）。大型店日報は市区町村×種別×**年**。
  月にすると 3,713 升のうち 95% が `1-2` になった。月と年の両方は出さない（引き算で戻る）。

### `counts_by_city` の升

`counts_by_city` は 3.2 でいう「升」そのもの。1 要素 = 1 つの升。

- 升は **`city_code` × `kind` × `period`** で決まる。この 3 つは必須。
  この 3 本がないと、集計だけを出すサイトは「何を」「いつの」数えたのかを
  言う場所がなくなる。`records` を空にする以上、ここに書くしかない。
- `kind` は `records` と同じ `<制度>/<種別>` の形。**種別には段階も結果も入る。**
  段階で分けるなら `競売/公告`、結果で分けるなら `競売/落札`・`競売/不調`。
  **段階と結果を 1 つの升に混ぜない**（数えている対象が違う）。
  種別の中をさらに分けるときは `-` でつなぐ（`競売/公告-新規`・`競売/公告-再公告`）。
  語は9節でそろえる。ここに `売却`・`不売` と書いていたのは誤り（2026-09-19 に直した）。
- `period` は `"2026-09"`（月）か `"2024-2025"`（年の範囲）。全期間なら `"all"`。
  期間を書かない升は作らない。
- `count` と `count_label` は必ず両方入れる。3.2 の小母数はここで効く。

  | 実数 | `count` | `count_label` |
  |---|---|---|
  | 3 以上 | その数（`12`） | 同じ数の文字列（`"12"`） |
  | 1 か 2 | `null` | `"1-2"` |
  | 0 | `0` | `"0"` |

  人に見せるのは `count_label` のほう。数のまま出さないために 2 本ある。
  `count_label` だけにすると足し算ができず、`count` だけにすると
  伏せたことが `0` と見分けられなくなる。

- 升を伏せたとき `count` は `null` になる。**なぜ伏せたかで `count_label` を分ける。**

  | 伏せ方 | `count` | `count_label` | 読み方 |
  |---|---|---|---|
  | 1 か 2 | `null` | `"1-2"` | 値は 1 か 2 |
  | まとめて伏せた | `null` | `"非公開"` | **値は 1 以上。3 以上かもしれない** |

  2行目は補完的伏せ（3.2）を使ったまとまりの升。そのまとまりでは、
  1〜2件の升と、それを守るために足した3件以上の升を、**同じ札にそろえる。**
  札を分けると「どれが3件以上か」が読者に分かり、1〜2件かもしれない升の数
  （＝隠れる場所）が減るため。

  **機械は `count_label` で読み分ける。** `null` を一律に「1 か 2」と読むと取り違える。

  まとまりは、同じ市区町村・同じ種別・同じ期間でくくった升の集まり。
  その中に補完的に伏せた升が1つでもあれば、そのまとまりの伏せた升は全部 `"非公開"`。
  1つも無ければ全部 `"1-2"` のままでよい。地図の見た目も同じで、
  まとまりの中で伏せた升は全部同じ見た目にする。

- **伏せた理由を、公開する側に書かない。** 「1〜2件だから」「補完だから」の別は
  金庫側にだけ残す（3.5 の出典と同じ扱い）。`index.json` に理由の欄を足すと、
  上でそろえた意味が消える。

- **`"非公開"` は「少ない」という意味ではない、と画面に書く。**
  札をそろえると、読者は「非公開」を「1〜2件のこと」と読みかねない。
  実際には3件以上のこともある。凡例か注記で、はっきりそう書く。

  街頭窃盗統計が両方の案を測って決めた（2026-09-17）。
  849区画を N 区画ずつの塊に切って「小さい市」に見立て、補完的伏せが
  発動したまとまりを数えた。「隠れる場所」は、読者から見て
  「1〜2件かもしれない」升の数（中央値）。

  | 市の区画数 | 発動したまとまり | 隠れる場所（札を分ける） | 隠れる場所（そろえる） |
  |---:|---:|---:|---:|
  | 5 | 99 | 1 | 2 |
  | 10 | 57 | 1 | 2 |
  | 20 | 30 | 1 | 3 |
  | 40 | 8 | 2 | 3.5 |
  | 80 | 1 | 1 | 2 |

  **札を分けても升そのものは特定できない**（補完的伏せが効いているので、
  どのまとまりでも0件だった）。だが隠れる場所は半分以下になる。
  見た目の違いが、それ自体が数字になる。

  そろえる代償は、1〜2件の升が `"1-2"` と書けなくなること。
  実測で 1〜118升（市の大きさによる。区画の多い市では0）。
- 率を出す升は `rate_per_1k` を足す。3.2 で伏せたときは値を `null` にして
  `rate_suppressed: true` を立てる。分母（人口など）も `population` として書く。
- 個票も出すサイトは、`records` 側に `period` を足してよい
  （犯罪統計マップの「町丁目 × 手口 × 期間」の行など）。
  **その種別を個票の粒度で出しているなら、`counts_by_city` には出さない。**
  親と子の両方を出すことになり、引き算で伏せた子が戻る（3.2）。
  `counts_by_city` に出すのは、個票の粒度では伏せ字だらけになるので
  市区町村でしか出さないと決めた種別だけ。同じ数を2か所に書かないのは
  もちろんだが、危ないのは重複ではなく粗さの違う両方出しのほう。

### 数えなかったものを、数えなかった理由で分ける

升に入らなかった行を、黙って落とさない。**なぜ入らなかったかで3つに分ける。**
1つにまとめると、誰が動けばいいのか分からなくなる。**減らせる主体が違う。**

    unresolved  読めなかった。語彙の穴          → **こちらが減らす**
    undecided   読めている。置き場が正本で未定   → こちらでは減らせない
    gone        消えた。待たないと決められない   → 時間が決める

`index.json` に `not_counted` として3つとも数を出す。0でも出す
（上の「値がないキーは省略せず、空文字か `null` を入れる」と同じ）。

**1つの行が2つの箱に入らないこと。** 混ざると、足したときに数が合わなくなる。
重ならないことをテストで固定する。

`gone` は競売統計が見つけたが、**4サイト全部に効く。**
公告に出たあと一覧から消えたものは、**その日には決められない。**
手続きが止まったのかもしれないし、次の期間にまた出てくるのかもしれない。
消えた日に片方へ倒すと、もう片方がそれに化ける。
**化けたあとでは、照らし合わせる相手がもう存在しない**（4節「繋がらなかった
ことは残るが、まとまってしまったことは残らない」）。だから母集団の保存が先。

自分の穴（`unresolved`）と、相手待ち（`undecided`）と、時間待ち（`gone`）を
分けていないと、**本当に催促すべき1件が、催促できない9件に埋もれる**（7節）。

**足したときに数が合うこと。** 升の合計 ＋ `not_counted` の3つ ＝ 見た行の数。
合わなければ、どこかで黙って落としている。

## 7. 運営者情報と連絡先

4サイトで同じ文面を使う。

```
運営者　鯨屋（くじらや）
　　　　大阪府・兵庫県で行政が公開する一次情報を、消える前に記録しています。
連絡先　<訂正・削除の依頼フォームURL>（7日以内にご返信します）
```

- **氏名は載せない。屋号のみ。** 広告収入だけのサイトは通信販売ではないため、
  特定商取引法の表示義務はかからない。有料サービス・物販・有料会員を始めた時点で
  表示義務が発生するので、そのときに改める。
- 所在地（都道府県）も載せない。地域は「何を扱っているか」の側で示す。
- 連絡先は**メールアドレスの直書きではなくフォーム**を優先する。
  1本のフォームを4サイトで共用し、「対象サイト」のプルダウンで振り分ける。
- **4サイトで統一する。** 1つだけ氏名を出すと、隠しているように見えて逆効果。
- **氏名はリポジトリにも書かない。一度もコミットしない。** 個人のメールアドレスも同じ
  （**コミットの作者欄も含む**）。GitHub の Settings → Emails で「Keep my email addresses
  private」と「Block command line pushes that expose my email」を先に入れる。手元の git は
  `user.email` を `<ID>+<名前>@users.noreply.github.com` にする。
  **git の履歴はあとから消せない。** ファイルから消しても履歴から読める。
  名前は足すのは簡単で引くのは不可能だが、git ではなおさら消せない。
  だから公開用は履歴ゼロで新しく作る（9節）。

### 個人のアドレスが無いことの、確かめ方

**見る場所が2つある。同じ `grep` では両方見えない。**

```bash
# ① ファイルの中身（全履歴）
git grep -hoIE '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}' $(git rev-list --all) \
  | sort | uniq -c | sort -rn

# ② コミットの枠（作者欄・コミッタ欄）
git log --all --format='%ae%n%ce' | sort | uniq -c | sort -rn
```

**①だけ見ると「無い」、②だけ見ると「ある」。両方要る。**
競売統計で実際に起きた（2026-09-17）。運営者が確かめて
「作者は全部 noreply、ファイルの中は役所の窓口だけ」と判断したが、
**ファイルの中身は正しく、作者欄を見落としていた。**
`git grep` はコミットの枠を見ないので、片方だけ見ると「無い」と読める。

**`--all` を落とさない。** 現在の枝しか見なくなる。
**件数を出す（`uniq -c`）。** 「有無」だけだと、1件を見落としたときに気づけない。

#### 浅いクローンで確かめない

`git clone --depth 1` した置き場でこの検査を走らせると、**「無い」と嘘が出る。**
持っていない履歴は数えられない。

こちらが実際に踏んだ（同日）。浅いクローンで競売統計と開発系を測って
「どちらも0件」と報告したが、`--depth=5000` で取り直したら
23件と4件が出た。**検査そのものは正しく、置き場が浅かった。**

走らせる前に、次を見る。

```bash
git rev-list --all --count          # コミット数
test -f .git/shallow && echo 浅い    # 何も出なければ全履歴
```

**9節の「鳴らせていない見張り」と同じ話。**
道具が正しくても、当て方で黙る。

#### 「無い」と書くときは、どこを見て無いのかも書く

浅いクローンと同じ形が、**枝の上でも起きる。** 3日遅れた枝で数えれば、
本流にあるものは見えない。数え方は正しく、見ている範囲が狭い。

開発系が実際に踏んだ（2026-09-19）。枝の中では `data/raw` の 09-17・09-18 が
無く、そのまま「無い」と報告した。**`main` には4回とも成功した実物があった。**
枝分かれの位置が違っていれば、こちらの削除が本物を巻き込んでいた。

**「無い」は、範囲を書かないと意味を持たない。**

    枝の上で無い        いま見ている枝に無い。本流にはあるかもしれない
    全履歴で無い        このリポジトリに一度も無い
    main で無い         公開されている側に無い

数える前に、見ている範囲を出す。上の2行（`git rev-list --all --count` と
`test -f .git/shallow`）に、**枝の名前と `main` との差**を足す。

```bash
git rev-parse --abbrev-ref HEAD      # いまいる枝
git log --oneline HEAD..origin/main | wc -l   # 本流に何本遅れているか
```

**同じ形を4回踏んだ**（浅いクローンで2回、枝で1回、公開用の木で1回）。
道具ではなく、当て方のほうが毎回ちがう。

### 氏名の代わりに信用を作るもの

氏名を出さない分、こちらを厚くする。統計サイトでは実際こちらの方が効く。

1. 返信が来る窓口（7日以内と書いたら本当に返す）
2. 全レコードの出典URLと取得日
3. 訂正履歴のページ（いつ・何を・なぜ直したか）
4. データと生成コードがそのまま公開されていること

### 役所や図書館に手紙を出すとき

1対1のやりとりは、サイトに載せるのとは別。検索エンジンにも載らない。
**お願いする側が名乗らないのはバランスが悪い**ので、氏名を入れてよい。

ただし**書き方に決まりがある。**

- 下書きは `docs/letters/<相手>.md` に置く。**署名欄に氏名は書かない。**

  ```
  鯨屋（くじらや）
  ※ 送信時に運営者名を1行足す（このファイルには書かない）
  ご返信 info@ogataten-nippo.com
  サイト https://ogataten-nippo.com/about.html
  ```

- 送信のときに、**人が手で氏名を入れる。**
  フォームに「氏名」の入力欄があれば、そこに書くだけでよい。
  その場合、本文の署名は屋号のままにする（フォームの欄はリポジトリに残らない）。
- 相手のサーバーを機械で読まない相談でも、**robots.txt は必ずホスト名まで書く。**
  「どこの robots.txt か」を書かないと、相手が「うちは拒否していない」と混乱する。
- **名乗り（User-Agent）は実物をそのまま書く。** 書いたものと実物が違うのがいちばんまずい。
  書く前に必ずコードを見て確かめる。
- **確かめずに書かない。** 「唯一」「〜だけ」は、自分の調査報告と矛盾しないか見直す。
- 送ったら、ファイルの1行目を
  `YYYY-MM-DD にフォームから送信しました。` に書き換える。
  返事が来たら**同じファイルに追記**する。やりとりが1か所に残る。
- **受付番号・整理番号のたぐいは書かない。** 送信日と方法だけ書く。
  相手の窓口で状況を照会できる番号は、public になるリポジトリに残す種類のものではない。
  控えは送信完了画面のPDFなどで手元に持つ。

### 手紙は屋号で数える。サイトで数えない

**自分のサイトが1通も出していなくても、屋号で出した手紙には縛られる。**
相手から見れば、サイトが違っても**同じ1つの説明**。

競売統計が実際に間違えた。`docs/letters/README.md` に

    このサイトはまだ1通も出していない。だから守るべき約束もまだ無い

と書いた。**サイト単位で数えたせいで、屋号単位の約束が見えなかった**
（2026-09-18）。

#### 「まだ無い」と書いた記録は、記録が無いより悪い

空のファイルなら、読んだ人は「調べよう」と思う。
**「約束は無い」と書いてあると、そこで確かめるのをやめる。**
**確認済みに見せてしまう。**

これは手紙にかぎらない。**「無い」と書くときは、どの範囲で数えて
無いのかを一緒に書く。** 範囲を書かない「無い」は、
次に読む人の確認を止める。

### 手紙は各サイトに写す。設定は1か所に寄せる

3.4 は「URL は設定の1か所にだけ書く」と言っている。**手紙は逆。**

    設定    現在値が動く      → **1か所。** 写すと食い違う
    手紙    送ったら動かない  → **各サイトに写す。** 写さないと見落とす

**送った手紙は変わらないので、写しても食い違わない。**
1サイトにだけ置くと、ほかのサイトが「うちは出していない」と読む。

**手紙を出したら、4サイトすべてに同じ写しを置く。**
どのサイトから読んでも、屋号で何を約束したかが見える形にする。

### 収入の形を変える前に、手紙で言ったことと突き合わせる

役所あての手紙に**収入の形を書いていることがある。**
**1通とはかぎらない。** 屋号で名乗っているので、**サイトが違っても
同じ相手への説明**になる。**サイトごとにではなく、屋号で数える。**

2026-09-16 の時点で2通ある。

    大阪府あて          「収入は広告のみで、閲覧・検索は無料です」
    国立国会図書館あて  「現時点で、データそのものの販売は予定しておりません」

**後者のほうが強い。** 前者は収入の**形**の話だが、
後者は**データを売らない**と名指しで書いている。

だから、広告以外の収入が発生する時点で前者と食い違い、
**データそのものを売る**話になった時点で後者と食い違う。
集計（件数・割合・分布）は、どちらにも触れない。

**順番を守る。**

  1. **収入について何と伝えたか、手紙を数える。1通で終わらせない**
  2. その相手全員に何と伝えるかを決める
  3. そのあとで、売る中身を決める

逆にすると、決めたあとで撤回することになる。
「あとで伝える」は 7節の「**破るなら、先に相手に伝える。黙って始めない**」に
触れる（2026-09-18）。

#### 「現時点で」が入っていれば、撤回ではなく更新になる

上の「**書くときは『現時点で』を付ける**」が、ここで効く。

国立国会図書館あてには入っている。だから**方式が変わったときに、
改めて伝えれば済む。** 前に言ったことを取り消すのではなく、
そのとき現時点だったことを更新する形になる。

**入っていなければ、撤回になる。** 大阪府あてには入っていない。

書いた時点では「念のため」に見える2文字が、**方針が動いたときに
「詫びる」と「知らせる」の差になる。**

### 手紙で「しない」と書いたことは、あとで守る

行政は**こちらの説明を前提にデータを出す。** 黙って前提を変えるのが、
いちばんやってはいけないこと。だから、書く前に将来を狭めすぎないようにし、
書いたあとは見返す場所を決めておく。

**書くときは「現時点で」を付ける。**

```
× データそのものを販売することは考えておりません
○ 現時点で、データそのものの販売は予定しておりません
```

正直さは落ちない。相手も計画が変わることは分かっている。
言い切ると、あとで道を狭める。

**有料の何かを始めるときは、次の2つを必ず見返す。**

1. **運営者情報** — 特定商取引法の表示義務が発生する。氏名・住所・電話番号が要る
2. **`docs/letters/` の手紙** — 行政に「しない」と書いたことがないか確かめる

   破るなら、**先に相手に伝える。黙って始めない。**
   一度「しません」と言った相手に黙って始めるのは、断られるより悪い。

手紙を出したら、`docs/letters/README.md` に
「**この先、有料の何かを始めるときはここを読むこと**」と一行書いておく。
1年後の自分は、手紙のことを覚えていない。

## 8. 各サイトのページに必ず置くもの

- **このサイトについて**：何を、どこから、どの頻度で集めているか
- **免責**：元の届出・公告が変更・取下げされることがあり、実際と異なる場合がある旨

## 9. 技術方針（共通）

- Python標準ライブラリのみ。例外を使うときは理由を README に書く
  （現在の例外：`.xls` の `xlrd`、PDFの `poppler-utils`（`pdftotext -layout`）、OCRの `tesseract`）
- GitHub Actions で定期実行、GitHub Pages で静的HTMLを配信
- ワークフローの**最初のステップでテストを走らせる**。落ちたらそこで止まり、取りに行かない
- 生データは全部保存する。**絞り込みは出力の段階だけで行う。**
  取得時点で捨てると、基準を変えたときに取り直しになる
- **HTML の表は `rowspan` / `colspan` を展開してから読む。**
  自治体の一覧表は結合セルだらけで、展開せずに読むと列がずれる。
  ずれ方が「値が空になる」ではなく「隣の列の値が入る」なので、
  面積や金額が黙って別の数字に化ける。気づきにくいので、最初から展開する。
- **知らないものを黙って捨てない。** 解析中に見たことのない見出し・列名・様式に
  出会ったら、値を `extra` に残したうえで `data/parse-unknown.md` に書き出す。
  次の実行で人が見られるようにする。

  **ただし、その記録も `privacy` を通す。** `extra` は「捨てない」ための場所だが、
  知らない列に氏名や地番が入っていることがある。**捨てない仕組みが、
  伏せる仕組みの外にあってはいけない。**
  全部を伏せるのではなく、**列名が当事者を指すときだけ例を出さない**
  （`privacy.is_party_column()` で判定する）。これで「様式が変わったことは残る／
  中身の氏名は残らない」が両立する。

  記録を公開しない置き場に置いていても同じ。**公開しないのは運用の約束で、
  コードで守られてはいない**（5節の「人の判断ではなくコードで守る」）。

  黙って捨てると、様式が変わったことに何年も気づかないまま、
  歯抜けのデータが積み上がる。落ちているものは落ちていると分かる形で残す
- **鍵には「あとから変わらない」と言い切れるものだけを入れる。**

  | 鍵に入れていい | 鍵に入れない |
  |---|---|
  | 出どころ・番号（公報番号・事件番号・物件番号） | 結果・落札金額・応札者数 |
  | 回次 | 面積・用途・価格 |
  | 段階（予定／公告／結果） | 当事者の名前 |
  | 公告日 | 取得日 |

  右の列は訂正で書き換わる。鍵に混ぜると、訂正のたびに同じものが
  新しい鍵で増え、古いほうを消す手がかりが無くなる。
  段階は値ではなく位置なので、鍵に入れてよい。

- **鍵と升は別物。鍵に入れないものを升にしてよい。**
  鍵は「同じものを二重に持たないため」、升は「数え分けるため」。目的が違う。

  結果（落札／不調）は**鍵に入れない**。値なので訂正で変わる。
  でも `counts_by_city` の `kind` には**入れてよい**。
  升は毎回まるごと数え直すので、変わっても困らない。

  | | 単位 | 結果の置き場所 |
  |---|---|---|
  | 記録（`records`） | 1回の入札 | **欄**。`結果: 不調` のように持つ |
  | 升（`counts_by_city`） | 市区町村 × `kind` × 期間 | **`kind`**。`公有地売却/不調` |

  **売れた件数は、レコードの数ではなく欄で数える。**
  結果の記録が82件あっても、61件が不調なら売れたのは21件。
  レコード数で数えると4倍に水増しされる（兵庫県の県有地売払いの実数）。

  段階の言い方は3サイトでそろえる。**予定／公告／結果** の3つ。
  「売出中」ではなく「公告」にする。他のサイトも行政が出した公告を数えているので、
  同じ言葉にしておくと横断ハブで突き合わせられる。
  不調・落札は段階ではなく、結果の欄に入れる。

  **結果の言い方も1組に決める。落札／不調 の2つ。**
  「売却」「不売」「売却済み」とは書かない。法令に近い語にそろえる。
  段階をそろえる理由がそのまま結果にも効く。**そろっていない語のまま足すと、
  横断ハブは同じものを2つの値として数える。**

  2026-09-19 の時点で、この文書の中に同じものを指す語が4組あった
  （`公有地売却/落札` ／ `競売/売却`・`競売/不売` ／ `結果（落札／不調）` ／
  `入札中`・`売却済み`）。**語が決まっていないと、新しい段階や結果を
  どこに足すかも決められない。** 足す前に、語を1組にする。

- **「鍵のぶつかりが0件」は、鍵が正しい証拠にならない。**
  むしろ**壊れた鍵ほどぶつからない。** 値を鍵に混ぜていれば、値が違うだけで
  別の鍵になり、ぶつからずに静かに増える。0件を安心材料にしない。

  確かめ方は3つ。全部やる。

  1. **同じ入力を2回流して、レコード数もIDも変わらないこと。**
  2. **値だけを1つ変えた同じ記録を流して、増えずに上書きされること。**
     これが「値を鍵に混ぜていない」唯一の証拠。1 だけでは通ってしまう。
  3. **鍵から1本ずつ抜いて、ぶつかりが出ること。**
     抜いてもぶつからない項目は、鍵に要らない。細かすぎる鍵も 1 と 2 を通る。

  実際に踏んだ例：兵庫県公報の目録で、公報番号（通し番号・1号1日付）に
  発行日を混ぜていた。Excel のオートフィルで年が1ずつ増えていて、
  13号から偽の号が58個できた。このときもぶつかりは0件だった。

- **鍵の作り方は出どころごとに1つに固定し、途中で変えない。**
  一次情報に番号が無くて所在地などで代用したら、その出どころは以後ずっと
  同じ作り方にする。あとから番号が付いたときに作り方を変えると、
  同じものが2つになる。代用したことは `data/parse-unknown.md` に書き出す。

- リポジトリは private で始め、公開の準備ができてから public に切り替える
  （GitHub Pages を無料で使うには public が必要）

- **そのまま公開できない生データを持つサイトは、リポジトリを2本に分ける。**

  git の履歴は消せない。一度コミットした生データは、その日にリポジトリを
  public にした時点で、過去のぶんも全部公開される。「あとで消す」はできない。
  ファイルを消すコミットを積んでも、履歴から取り出せる。

  | | 置くもの | |
  |---|---|---|
  | 収集用 | 生データ、`inbox/`、人が手で入れた原本 | **ずっと private** |
  | 公開用 | 集計結果、`index.json`、HTML、Pages | public |

  分けるかどうかは、これ1つで決める。
  **その生データを、いまそのまま公開できるか。**

  | 生データ | 公開できるか | |
  |---|---|---|
  | 公報・告示の全文 | できる（著作権法13条2号。県も国会図書館も公開している） | 1本でよい |
  | 警察のオープンデータ | できる（公開が前提のデータ） | 1本でよい |
  | 競売・公売の物件一覧 | **できない**（入札中・住居を含む。3.1） | 分ける |
  | 人が手で保存したページ | 相手の規約しだい。読むまでは「できない」側 | 分ける |

  迷ったら分ける。あとから1本にまとめることはできるが、
  1本にしたものを2本には戻せない。

- **公開する前に、「伏せ方を一度でも直したか」を見る。**

  上の表は**生データ**を見て決めている。それとは別に、**自分が作った出力の
  古い版**が履歴に残っている。伏せ方を直したなら、直す前のゆるい出力が
  そのまま履歴にある。生データが公開してよいものでも、この履歴は別の話。

  街頭窃盗統計が実物で踏んだ（2026-09-17）。元は警察のオープンデータなので
  上の表では「1本でよい」側。ところが伏せ方を直す前の geojson が履歴にあり、
  **伏せたはずの実数 16,208升**がそこから読める。公開する前に気づいた。

  だから、公開用のリポジトリは**そのつど新しく作る**。
  いま private で書いているリポジトリを、あとから public に切り替えない。

  | | |
  |---|---|
  | いま書いているリポジトリ | private のまま。ここが金庫 |
  | 公開用 | **履歴ゼロで新しく作る。** 成果物だけを push する |

  git の履歴を書き換えて public にする、は選ばない。当てにならない。

  - `refs/pull/*` は force-push で消えない
  - fork とキャッシュに残る
  - PR のタイトルと本文は履歴の外に残る

  **公開用の履歴は資産ではない。** 成果物は金庫から作り直せるので、
  公開用は丸ごと捨てて作り直せる状態にしておく。残す価値があるのは
  金庫側の履歴のほう（いつ何を取ったか。3.5）。

  いちばん安いのは、**公開する前に**この形にすること。
  大型店日報は public にしてから気づいたので、名前を変えて private にし、
  公開用を作り直す手順が要った。まだ公開していないサイトは、
  最初からこの形で作れば、その手順ごと要らない。

  **2本にするときの形**（大型店日報の `.github/workflows/shutten-recon.yml` が実物。
  他のサイトも同じ形にする。名前は揃える）

  - 走るのは**公開用の Actions**。public なので Actions の分は無料で、`GITHUB_TOKEN` で
    自分に push できる。収集用は**置き場**。収集用の Actions は止め、workflow は持たせない
    （名前が `-raw` で終わるか `-raw-` を含むリポジトリでは workflow が自分で止まるようにしてある）
  - 公開用の Actions が **deploy key** で収集用を `_raw/` に checkout する。鍵は収集用の
    Settings → Deploy keys（書き込み可）に公開鍵、公開用の Secret **`RAW_DEPLOY_KEY`** に秘密鍵。
    鍵は `ssh-keygen -t ed25519 -N "" -f raw_deploy_key -C <公開用の名前>-actions` で作る
    （**パスフレーズは空**。Actions は対話できない）。Secret には秘密鍵ファイルの全文
    （`-----BEGIN OPENSSH PRIVATE KEY-----` から `END` の行まで）を貼る。
    PAT は期限で黙って止まるので使わない。deploy key は1本のリポジトリにしか効かない。
    公開用の Actions は走る前に、収集用が公開側から見えない（private）ことを確かめ、
    見えたら生データを送らずに止まる
    **鍵は、それを使うサイトのところで作る。** 横断ハブ（共通仕様のチャット）を
    経由させない。秘密鍵は運営者が、作ったところから GitHub の画面へ直接貼る。
    **経由するところが1つ増えるたびに、鍵が残る場所が1つ増える。**
    端末で作れるなら端末で作るのがいちばん少ない。
    Secret は**生データを持たない公開用にだけ**入れる
    Secret は**生データを持たない公開用にだけ**入れる（生データを追跡しているリポジトリに
    入れると二重持ちの見張りで止まる。意図どおり）
  - `data/raw` `data/files` `data/ocr` `data/wayback` を `ln -s` で**今までのパスにつなぐ**。
    Python は置き場の違いを知らない。置き場を変えるためにコードを直さない
  - 公開用への commit は**許可リスト**。公開してよいと決めたパスだけを列挙して `git add` する。
    `git add data` のような丸ごとはしない。新しい出力を公開したいときは列挙に1つ足す
    （足し忘れると「載らない」だけで済む。逆は済まない）。commit の直前に、生データ・記録・
    symlink が混ざっていないかを機械で見て、混ざっていたら止まる
  - しまう順番は **収集用 → 公開用**。取り直せないものを先にしまい、そこで失敗したら
    公開用にも送らない。収集用は private なので、公開側の検査を待たずに先に入れてよい
  - ページを作ったあとに**もう一度テストを通してから**公開用に push する。最初のテストは
    昨日の出力に対してなので、それだけだと今日の伏せ忘れが翌朝まで公開される。
    この2回目のテストが止めるのは公開用への push だけ。生データはその前に収集用に入っている
  - 走らせた記録（`data/*.md`・`data/koho/*.md`）は生の値を含みうるので、収集用の
    `data/reports/` に写す。公開用には commit しない（`data/parse-unknown.md` も収集用で見る）。

    **写すかわりに、記録の先頭に1行入れてテストで見張る形でもよい。**

        > **このファイルは公開しない。** 走らせた記録で、伏せる前の値が入りうる。
        > 公開してよいのは `data/public/` の中だけ（正本9節）。

    移す手間が要らず、**ファイル単体を開いた人にも分かる。** 許可リストと
    二重の歯止めになる（競売統計・2026-09-17）。
    公開用と収集用が別々に動いているなら「写す」のほうが確実。
    1本のリポジトリの中で分けているなら「先頭に1行」が向く。**どちらでもよい。**
  - 鍵が無いときに1本の形（`git add data` の丸ごと）で動くのは、**生データを既に追跡している
    移行前のリポジトリだけ**。生データを持たない公開用で鍵が無ければ、取りに行かずに止まる。
    鍵が無いまま走ると、その日の生データが public に載るため
  - 収集用が 2GB を超えそうになったら都道府県ごとに分ける（`-raw-<pref>`）。そのときは
    checkout と Secret と private の確認をもう1組ずつ足し、つなぐ段を収集先ごとのリンクに
    直す。公開 URL と公開用の木は変わらない
  - 一度でも生データを public に commit していたら、そのリポジトリを**名前ごと private に
    して収集用にし**、公開用は履歴ゼロで同じ名前に作り直す。同じ public リポジトリの中で
    履歴を書き換える手（filter-repo・orphan の force-push）は採らない。PR の参照
    （`refs/pull/*`）と PR の題名・本文は force-push でも消えず、そこから旧コミットに届く。
    作り直す順番（サイトが止まる窓と独自ドメインが空く窓を短くし、収集用が public のまま
    生データを受けないため）：
    ⓪ アカウントの Settings → Pages → **Verified domains** で独自ドメインを検証済みにしておく
    （③〜⑧ の間はどのリポジトリもドメインを主張していない。検証していないと他人が自分の
    Pages に付けられる）→ ① 新を**仮の名前**で作り、公開用の木を1コミットで入れる。
    **入れないもの**：`data/raw` `data/files` `data/ocr` `data/wayback`・`data/*.md`・
    `data/koho/*.md`（workflow の見張りが見る一覧と同じ。残すと初回から止まる）・`CNAME`
    （入れると旧と同じドメインを取り合う。⑧ で GitHub が書き戻す）。作り方は「main を
    `git archive` で展開 → 上を消す → 1コミット」。Pages を有効にしてよい（CNAME が無いので
    github.io の仮 URL で配信される。動作確認に使う）→ ② 旧の Actions を止める →
    ③ 旧の Pages を **Unpublish**（独自ドメインを外すだけでは github.io 側が配信を続ける。
    Free なら private 化で落ちるが、それに頼らない）。直後に
    `https://<owner>.github.io/<公開用の名前>/data/raw/<id>/<日付>.html` が 200 でないことを見る →
    ④ 旧を **`<公開用の名前>-raw`** に rename（workflow の checkout・private の確認・名前による
    自己停止が全部この名前を見る）→ ⑤ **すぐ旧を private** にし、旧の main から
    `.github/workflows/` を消す commit を入れる（収集用に workflow を持たせない）→
    ⑥ 収集用（旧）に Deploy key → ⑦ 新を同じ名前に rename → ⑧ 新の Pages に独自ドメインを
    付け（GitHub が `CNAME` を commit する）、それから Secret を入れる →
    ⑨ **`https://<owner>.github.io/<公開用の名前>-raw/data/raw/<id>/<日付>.html`** が 404 で
    あることを見る（`…/<公開用の名前>/` は ⑦ 以降は新のサイトなので確認にならない）。
    Secret を入れるのは収集用が private になった**後**。
    **古い clone は全部 remote を付け替えるか消す。** 同じ名前で作り直したあと、古い clone
    からの push は新しい公開用に届く（新しい枝を push すると、旧履歴ごと public に戻る）

- **生データを公開してよい場合でも、そこから氏名で引ける索引やページを作らない。**
  公報の全文には、法令に基づいて行政が公示した氏名が入っている
  （「土地区画整理組合の理事の氏名等の届出」など）。
  写しをそのまま置くのは、行政の公示を写しているだけなので構わない。
  そこから氏名を抜き出して索引にすると、行政が作っていないものを作ることになる。
  3.1 の「氏名と地番を恒久的に固定しない」はここに効く。
  絞り込みは出力の段階だけ、という上の決まりと同じこと。
  大型店日報の兵庫県公報の写し（`data/koho/full`・`data/koho/text`）は、この決まりのとおり
  公開用に置く（2026-09-16 に運営者が確認。設置者の氏名・住所は県が公示したもので、
  写しから氏名で引ける索引や個票は作らない。姉妹サイトが公開 URL で読む約束でもある）。

- **「変わったか」の見張りは、現在値と比べない。退役した値の一覧と比べる。**
  名前・URL・連絡先を差し替えたら、古いものが残っていないかを見る検査を置く。
  このとき **`config` の現在値と比べる作りにしない。** 手で直した瞬間に

  空振りする作りだった。一覧に直した直後、旧名の混入を実際に検出した
  （2026-09-17）。

- **消したものの記録は、上書きされるファイルに書かない。**
  こちらが消したもの（ファイル・節・やめた方針）を、毎回作り直される
  ファイルに書くと、次の実行で**消した記録ごと消える。**
  残らないのではなく、消えたことが消える。
  消したものは追記だけのファイルに置く（例 `docs/deleted.md`）。
  日付と、消したもの、消した理由を1行ずつ足す。
  上の退役した値の一覧と同じ形で、足すだけにして消さない。

  置き場を `data/` にしない。`data/*.md` は走らせた記録として収集用に写し、

  走らせた記録ではないので、`docs/` に置く。

  あちらは一次情報が向こうで消える話、こちらはこちらが消した話。
  混ぜると、どちらの記録も読めなくなる。
  7節の「『まだ無い』と書いた記録は、記録が無いより悪い」（1479行）とは対になる。
  あちらは「無い」と書いてしまう話、こちらは書いたものが消える話。

### 控えの名前は、中の値がいつのものかで決める

一覧は上書きされるので、取得のたびにスナップショットを残す（212行）。
残す形も既にある。`data/raw/<id>/<日付>.html`（1787行・1793行）。
**書いていないのは、その日付が何の日付かということ。**
作り直しの手順の中にパスとして出てくるだけなので、決まりとして書く
（「偶然効いている性質は、意図に格上げして検査で留める」1859行）。

名前に入れるのは、中の値がいつのものか。作った日でも通し番号でもない。

日付が中に書かれているものは、その日付を使う。公報の写しが `<日付>-<号>`
なのは発行日で名づけているからで、既にこの形（636行）。
日付が書かれていない一覧は、取得日で名づける。ただし取得日は
「いつのものか」そのものではなく、**それより古くないと言える上限**でしかない。
3.5 の「終了は点ではなく、区間」（679行）と同じで、巡回の間隔だけ幅がある。
名前に畳み込んだ幅は、名前からは読めない。

作った日や通し番号にしない。作り直したり、取り込みが1日遅れたりすると、
中身がいつの一次情報なのか名前から分からなくなる。
番号は並び順しか教えないので、抜けにも気づけない。
6節が `id` の連番を避けたのと同じ理由（1249行）。

1つの名前に2つの日付の意味を混ぜないのは、`closed_on` と `closed_detected` を
別の欄にするのと同じ形（673行）。

### 貼り付け用に書いたものは、リポジトリにも1行残す

上の枠はチャットに出すためのもので、**チャットに出しただけでは記録にならない。**
送った側と受けた側のメモの中にしか無いものは、どちらからも確かめようがない。

競売統計が共通仕様あてに10件の指摘を送った。共通仕様の側は「こちらで見る。
順番に返す」と答えたまま3日止まった。見に行ったが、コミットにも進捗ファイルにも
無かった。**競売側は貼り付け用に書いただけで、リポジトリに残していなかった**
（2026-09-19）。いまは `docs/seihon-toiawase.md` に、送った10件を状態つきで置く。

7節が手紙で同じことをしている。送ったら送信日を書き、返事は同じファイルに
追記して、やりとりが1か所に残る形にする（1460行）。相手が役所か姉妹サイトかが
違うだけなので、置き場も形もそちらに揃える。
1479行の「まだ無い」と書いた記録の、もう一段下にあたる。
あちらは「無い」と書いてしまった話で、こちらはそもそも記録が無い。

- 正本あてに何かを送ったら、送った側が自分のリポジトリに1行足す。
  送った日・件名・送り先。チャットの控えではなく、こちらの記録として置く。
- 受けた側も、見るとだけ答えて終わりにしない。答えた日を同じ一覧に返す。
- 一覧に書くのは件名と状態だけ。升の実数・引き算の式・場所の名前は、
  チャットにもこの一覧にも書かない（1956行）。

#### 「返事待ち」と「材料待ち」を分ける

一覧には状態の欄を持つ。**「返事待ち」と「材料待ち」を同じ欄に入れない。**

材料待ち（4サイトの実測が出そろうまで決められないもの。412行）には、
催促する相手がいない。返事待ちには相手がいる。10件を状態で分けたら、
解決が7、材料が揃うまで保留が1、返事待ちが1、こちらの宿題が1だった
（2026-09-19）。催促する相手がいるのは1件だけ。
**分けないと、その1件が催促できない9件に埋もれる。**

3.5 が `closed_on` と `closed_detected` を分けるのと同じ形（673行）。
1つの欄に2つの意味を混ぜると、あとから見分けられなくなる。

- **実測値をコメントや説明文に書かない。**
  「この時点で◯◯件」と書いた数は、データが増えれば古くなる。
  そして **検査は数字が「合っているか」を見ない。「あるか」しか見ない。**
  だから古くなっても誰も気づかない。最初から書かず、数えたいなら
  その場で数えるコードを書く。

  街頭窃盗統計で、コメントに残っていた3つの総計が互いに矛盾していた。
  同じ升を拘束する2つの経路が食い違っていて、少なくとも2つは真値でなかった。
  どれがいつの数だったかは、もう分からない（2026-09-17）。

  3.2 の「伏せ方を説明する文書に、実物の値を書かない」とは理由が違う。
  **あちらは漏れる話、こちらは腐る話。** 両方要る。

  **「いま成り立っている値」と「過去に起きたことの記録」は分ける。**
  前者は書かない。データが動けば古くなる。
  後者は書いてよい。起きた時点の話なので古くならない。
  「いま余裕は11」は前者、「2026-09-17 の時点で伏せた升が16,208あった」は後者。
  11節が実測値だらけなのは、全部が後者だから。

- **鳴らせていない見張りは、動くと分かっていない見張り。**
  検査を足したら、**実際に鳴るところまで確かめる。** 条件を人工的に作って、
  落ちるのを見る。「書いたから動くはず」は、確かめていないのと同じ。

  街頭窃盗統計の余裕の見張りが、**余裕 0 になるまで鳴らない作りだった。**
  docstring 自身が「『あと1件で崩れる』状態は素通りする」と書いていたのに、
  誰も読んでいなかった。25%で鳴るよう直し、人工的に細らせて鳴ることを
  確かめた（2026-09-17）。

  同じ日に足した2つの検査は、**足した直後に本物を1件ずつ見つけた**
  （退役名の見張り → 旧名の混入／伏せる判断の手書き検査 → 公報の表の合計）。
  どちらも偶然そうなっただけで、「鳴らして確かめる」を手順として
  書いてはいなかった。

  **鳴ることを確かめたら、直すと黙ることも確かめる。**
  常に鳴る見張りは、鳴らない見張りと同じくらい役に立たない。
  人が「またこれか」と読み飛ばすようになり、本物が来ても止まらない。
  壊した状態で鳴り、直した状態で黙る。**両方を見て、はじめて動くと分かる。**

- **偶然効いている性質は、意図に格上げして検査で留める。**
  守りになっている性質が、設計の意図ではなく**たまたまそうなっている**
  だけのことがある。そのままにすると、**次の変更で黙って消える。**
  気づいたら、意図として文書に書き、検査で留める。

  街頭窃盗統計では、町丁目が8年の合計だけ・市の升が年ごとで、
  そのため**年別には引けない。** 意図して作ったものではなかったが、
  実際に守っていた。気づいた時点で決定ログに書き、粒度がずれていることを
  検査で留めた（2026-09-17）。

- **URL に連動するものを、固定文字列で書かない。** `config` の URL から作る。
  公開先が決まるまでの仮 URL、公開後の本 URL、その差し替え。
  名乗り（User-Agent）・`robots.txt` の `Sitemap:` 行・`sitemap.xml` の中身は
  どれも公開先 URL を含む。別々に書くと、**差し替えのときにどれか1つが残る。**

  街頭窃盗統計は `SITE_URL` から作る形にしたので、公開時の差し替えが
  **1行で済んだ**（名乗りが追従したことを実際に確かめている。2026-09-17）。

  **ただし、config から作っても、人が書き写すところで切れる。**
  大型店日報は名乗りを変数から組み立てていて、コードは正しい。
  それでも国会図書館へ出した手紙に書いた文字列が実物と違っていた
  （訂正を送る予定）。**手紙を書いた側が、実物を出力して確かめなかったため。**
  外に出す文書に名乗りを書くときは、**実物を1回出力して、それを貼る。**
  7節の「手紙で『しない』と書いたことは、あとで守る」と同じ場所で切れる。

- **検査をコマンドで繋ぐとき、パイプを挟まない。** 終了コードが隠れる。
  `検査 | 整形` と書くと `$?` は後ろのコマンドのものになり、
  **検査が落ちても成功に見える。** 繋ぐなら `set -o pipefail` を付けるか、
  一度ファイルに落としてから読む。
  検査そのものが正しくても、**呼び方で黙る。**

- **相手が書き戻したファイルを、作り直しで消さない。**
  Pages に独自ドメインを付けると、GitHub が公開側に `CNAME` を commit する。
  公開用の木を作るスクリプトは `CNAME` を除外している（自分で入れると
  ドメインを取り合う）ので、**作り直した木には無い。**
  そこに `.git` を被せて `git add -A` すると、**CNAME を削除する差分になり、
  push すると独自ドメインが外れる。**

  除外リスト方式は「**作る**」ときは正しい。公開用の木は収集用の写しなので、
  足し忘れより消し忘れのほうが起きやすいから。
  だが「**入れ替える**」ときは、相手が足したものまで消す。
  定期実行は**許可リスト方式**（`git add -A -- <列挙>`）にして、
  手で作り直す経路にだけ注意を書く（街頭窃盗統計・2026-09-17）。

- **除外リストは3回続けて漏れた。個別のパスではなく、種類で捕まえる。**
  街頭窃盗統計で公開側に漏れかけたのは `CNAME`（相手が書き戻すファイル）、
  `_raw` で終わる金庫の写し、`data/reports`（収集の途中の記録）の3つ。
  どれも「そのパスを1行足す」で直したが、**3回とも、次の1つが漏れた。**
  1つずつ足しているかぎり、新しいものが増えるたびに同じ穴が開く。

  漏れたものはパスとしてはばらばらだが、**種類としては3つしかない**——
  相手が書き戻すもの／金庫から来たもの／収集の途中の記録。
  除外はこの**種類で書く**（`*_raw/`、`data/reports/`、Pages が置くもの）。
  そのうえで、**列挙に無いものが公開側に現れたら止める検査**を持つ。
  「3回漏れた」という事実のほうが、漏れた3つのパスより長く効く
  （街頭窃盗統計・2026-09-19）。

- **前身の置き場を見る。** 9節の作り直し手順は「いま書いているリポジトリ」を
  対象にしている。**その前に使っていた置き場は対象外になっている。**

  サイトは、たいてい別のリポジトリの中から始まる。分けて引っ越したあと、
  前身のほうは「転送ページだけにした」で終わりがちだが、
  **git 履歴には引っ越す前の出力がそのまま残る。**

  大型店日報は `ic-log`（別用途のアプリ）の中で始まり、2026-09-13 に
  `ogataten-nippo` へ移した。前身側は全ページを転送ページに置き換えてあったが、
  **`ic-log` は public で、履歴から伏せる前の3,525枚が読めた。**
  設置者の欄を機械で分類したところ、伏せてあったのは**2枚だけ**だった
  （2026-09-17 に発見し、`ic-log` を private にして塞いだ）。

  確かめること。**いまのリポジトリだけを見ても出てこない。**

  - このサイトは、どこから分かれてきたか
  - その置き場は public か
  - そこに、いまの伏せ方が入る前の出力が残っていないか
  - 転送ページに置き換えてあっても、**履歴からは読める**

  **private 化は force-push と違って実際に効く。** 9節が「当てにならない」と
  言っているのは履歴の書き換えのこと。可視性を落とすのは別の手で、
  fork が無ければ外から読めなくなる（先に fork 数を見る）。

- **workflow が作業用に置くディレクトリは、`.gitignore` と検査の両方に登録する。**
  片方だけだと、もう片方で事故る。

  街頭窃盗統計の月次 workflow が、金庫を `_raw/` に checkout していた。
  `.gitignore` に無いので、手で `git add -A` すれば金庫の中身が公開側に入る。
  検査の除外にも無いので、**検査が金庫まで見て毎回落ちていた**（2026-09-18）。
  金庫の記録に親の合計があるのは正当で、**検査が正しく、当て方が違っていた。**

  **除外リストに1語足すのは応急処置。** 次の作業用ディレクトリで同じことが起きる。
  **検査の範囲は許可リストで決める。** ただし「git が追跡している」だけでは
  足りず、「**公開対象か**」も要る（追跡されていても公開しないものがある）。
  追跡情報が無い場所では除外リストに落ちるが、**どちらで決めたかを毎回印字して、
  落ちたことを黙らない。**

- **検査は、最初の1件で止まらない形にする。** 止まると2件目以降が隠れ、
  同じ穴が2か所にあっても、1か所直すまで2か所目が見えない。

  上の穴を1つ直したあと、**別の検査が同じ穴を持っていた**ことが分かった。
  最初に落ちた1つしか見えていなかった（街頭窃盗統計・2026-09-18）。

- **「どこから来たか」だけでなく「どこへ書いたか」も辿る。**
  前身の置き場を見るとき、来た先だけでは足りない。このリポジトリの出力が
  **外のどこかに書き出されていないか**も見る。

  確かめること：push 先は自分だけか、外への HTTP に書き込み（POST/PUT）が
  無いか、workflow が外部の資格情報を持っていないか、Pages を出していないか。
  開発系が、外への HTTP 全3か所とも GET・Secret 0件・Pages 無しを確かめた
  （2026-09-18）。

- **許可リストが掛かるのはパスだけ。本文には 3.2 が掛かる。**
  コミットメッセージ、**PR の題名と本文**、issue、チャットに貼る報告に、
  升の実数・引き算の式・場所の名前を書かない。

  この節は「PR の題名と本文は履歴の外に残る」と書いている。
  **force-push でも消えない側なのに、検査は本文を見ていない。**
  掛かる先を「コミットメッセージ」だけと読むと漏れる（競売統計・2026-09-18）。

### 公告のあとに起きたことは、段階ではない

競売統計から「段階の語彙に `取下げ` と `不明` を足すか」と聞かれた（2026-09-19）。
どちらも足さない。段階は増やさない。3つのまま。

段階を4つにする案は、以前も鍵の決まりに照らして断っている（11節）。今回も同じ。
**段階は値ではなく位置なので、鍵に入れてよい**（上の節）。
取下げは公告に至るまでの位置ではなく、**公告のあとに起きたこと**で、位置ではなく値になる。
段階を鍵に入れてよい理由が、取下げには当てはまらない。

**取下げをどこに足すかは、まだ決めない。** 足し先の候補が2つある。
結果の欄（不調・落札と同じ扱い）と、3.5 の終了の欄。
記録の単位は「1回の入札」なので、入札が行われなかった取下げを結果の欄に入れると、
1つの欄に2つの意味が混ざる。`closed_detected` に公表日を入れない、と同じ形（3.5）。

**足す前に、同じ欄に入るものを先に数える。**
競売には「公告のあとに入札が行われなかった」形が、取下げのほかにもある
（執行停止、期日変更など）。聞かれるたびに1つずつ足すと、欄が育つ。
育った欄は、どのサイトも全部の値を出せない。
横断ハブから見ると「出していない」と「起きていない」の区別がつかなくなる。

数えるのは1件の実例ではなく、**出どころの様式のほう。**
その制度で起こりうる形を様式から数え切ってから、まとめて決める。

`不明` も同じ。段階には足さない。名前の欄に入っている `不明` の扱いは
5節で決まっているので、そちらを見る。段階や結果の語と混ぜない。

### 表の見出しは、1段とはかぎらない

自治体の一覧表は、見出しが2段になっていることがある。大阪府の届出一覧は、上の段の「17. 備考欄」が4列ぶん結合されていて、その下の段に「延床面積」「施設の用途地域」「その他」がぶら下がっていた（2026-09-19 に実物で確かめた）。

上の段しか読まないと、**延床面積を「備考」として拾い、用途地域は丸ごと落とす。** 画面には「備考 10909」という、意味の分からない数だけが33ページに出ていた。

この節の「`rowspan` / `colspan` を展開してから読む」とは、ずれ方が違う。あちらは「隣の列の値が入る」で、値そのものは残る。2段見出しは**列が丸ごと消える**ほうで、見に行かなかった段は `extra` にも `data/parse-unknown.md` にも出ない。知らない列として残せるのは、見た列だけ。落ちたことにも気づけない。

結合された見出しの下に別の見出しがあれば、**下の段まで読んでから欄を決める。** 上の段は欄の名前ではなく、欄のまとまりの名前のことがある。

### 列がずれたことは、値の形に出る

備考のような自由記入の欄に、4桁以上の数字しか入っていないことがある。それは文章ではなく、どこかの列の数がそこに来ている。ほかの収集先の備考は、全部が文章だった（2026-09-19）。**中身を読まなくても、形だけで気づける検査がある。** 欄の意味を知らなくても書けるので、初めて見る様式にも当たる。

しきい値は、件数ではなく割合で置く。理由は2つ。

- 件数は、データが増えると意味が変わる。「10件を超えたら鳴らす」は、1,000件のうちの
  10件と、100件のうちの10件を同じに扱う。この節の「実測値をコメントや説明文に
  書かない」と同じ理由で腐る。検査は「あるか」しか見ないので、腐っても誰も気づかない
- 割合のほうが、現象の出方に合っている。**列がずれると、わずかではなく、
  ほとんど全部がずれる。** 少しだけ読めないのは出どころの言い方のばらつきで、
  そちらは書き方をそろえる側（5節）が吸収する。「読めないものが2割を超えたら
  鳴らす」なら、ばらつきでは鳴らず、列ずれでは鳴る

### 拾いに行く前に、手元のものが数えられる形か確かめる

同じものが、出どころごとに別の書き方で入ってくる。4節が住所でやっていることは、住所だけの話ではない。

大型店日報で、用途地域を外から拾い足そうとした。その前に 2026-09-19 に手元の1,231件を数えたら、**31通りの書き方**で入っていた。同じ用途地域が4つに割れていた。

    第１種住居 112 ／ 第一種住居地域 27 ／ 第一種住居 18 ／ 第1種住居 13

170件が1つとして数えられていない。1節が「住所の正規化と出力スキーマだけは、4サイトで一言一句そろえる」と言っているのは突き合わせのためだが、そろっていない害はその前に出る。**横断ハブの前に、同じサイトの中で集計できていない。**

### 変わった回数は、ひと続きで数える。種類を数えない

「何回変わったか」を、出てきた値の**種類**で数えると、**戻ったことが消える。**

    A → B → A → C     ひと続きで数えると3回
                      種類を数えると3種類 − 1 = 2回

大型店日報が、設置者の変わった回数をこの形で数え違えていた（2026-09-19）。
`A → B → A` は「変わっていない」ことになっていた。

**戻したことが消えると、予兆を見るときに効く。**
営業時間の変更が撤退の予兆になるかを調べるなら、
24時間 → 22時 → 24時間 に戻した店を「1回変更」と数えてはいけない。
**戻した店は、そもそも母集団から外す**（戻したという事実のほうが、
変更したという事実を打ち消している）。

検証を始める前に決めておくこと（3.3「測る前に、外れたときにどうするかを
決めておく」と同じ場所）。数え終わってから気づくと、やり直しになる。

### 書き戻す相手は、GitHub だけではない

自動で書かれたものを、手作業が知らずに消す。これが同じ形で2回起きる。

  CNAME      GitHub が公開側に書き戻す。作り直した木には無いので、消える
  生成物     自分の CI が公開側に書き戻す。金庫から作り直すと、古い版に戻る

CI が定期実行でデータを取り直し、作り直して公開側に commit する作りだと、
**公開側の生成物のほうが、金庫より新しい。**
金庫は生データだけを受け取り、作ったものは受け取らないことがあるためで、
これは設計として自然に起きる。片方の落ち度ではない。

そこから木を作り直して `git add -A` すると、**CI が昨日やった仕事を、
古い日付で上書きする。** 消えるのは設定ではなくデータで、
気づかないと次の定期実行まで古いまま出続ける。

  ・コードだけを直すときは、**コードのパスだけを stage する**
  ・生成物も出すときは、**巻き戻していないかを先に見る**

        git diff --cached -- <生成物> | grep '^-.*generated_at'

**気づく入口は、差分の中身ではなくファイル数。**
コードしか触っていないのに生成物が何百件も `M` になっていたら、
動いているのは中身ではなく日付。1件開けば分かる。

本筋の直し方は、**金庫を CI の出力に追いつかせること。**
ただし書き戻す先を増やすと、出どころが2つから3つになる。
**緑になった直後の CI を、確かめずに触らない。**
定期実行が安定してから触ること。

### 作った一覧を巡回に入れないと、古いまま検査を通る

新しい出力を作ったら、**同じ日に毎朝の巡回へ足す。**
足すまでの間、置いてあるファイルだけがその場に残る。
中身は作った日のもので、データのほうは毎朝増えていく。

大型店日報で退店の一覧を作り、巡回に足すのを忘れた。
検査は毎朝通っていた。形も伏せ方も正しいので、落ちる理由が無い。
走らせ直したら193件が194件になった（2026-09-19）。
**検査は「ファイルが正しいか」を見る。「ファイルが新しいか」は見ない。**

新しい出力は、巡回と公開用の許可リストの両方に足す。
上の「公開用への commit は許可リスト」は足し忘れても「載らない」だけで済むが、
**巡回は済まない。** 載るのは載って、作った日のまま載り続ける。

9節の「実測値をコメントや説明文に書かない」と同じ形。
あちらは説明文に書いた数が腐り、こちらは出力そのものが腐る。
本体はどちらも、腐ったことに誰も気づかないことで、腐ること自体ではない。

巡回に入れた生成物は毎日動く。上の「気づく入口は、差分の中身ではなく
ファイル数」が効くのはコードだけを触って手で作り直すときなので、そこは変わらない。

### 標準ライブラリと同じ名前のファイルを作らない

設置者の一覧を作るスクリプトを `operator.py` と名づけた。
Python には `operator` という標準モジュールがあり、自分の置き場のほうが
先に見つかる。`ImportError` で止まり、`settisha.py` に変えて通った（2026-09-19）。

**出るのは、自分が import した瞬間ではない。**
別の何か（標準ライブラリの中の別のモジュールや、例外で入れた道具）が
`operator` を読んだ瞬間に出る。止まった場所と原因の場所が違うので、
自分のコードを何度読んでも見えない。知らない名前で `ImportError` が出たら、
まず同じ名前のファイルが自分の置き場に無いかを見る。

危ないのは短くて役目を指す名前で、こちらが付けたくなる名前とそのまま重なる。

    operator  types  code  time  random  email  json  csv  io  copy  test  select  signal

**日本語の役目をローマ字にすると当たらない。**
`settisha.py` `taiten.py` `koho_pdf.py` はこの形。
役目は読めて、標準とは重ならない。

### 規則を満たしていても、規則の言葉で書く

共通仕様に規則が足されたとき、自分のコードが**別の書き方で既に
満たしている**ことがある。そのままにしない。規則の言葉に書き換える。

理由は、読む人に**偶然そうなっているように見える**こと。
偶然に見えるものは、次に誰かが別の理由で動かす。整理のつもりで、
短いほうに寄せるつもりで。そのとき規則は黙って成り立たなくなる。
**テストも守ってくれない。** テストのほうも古い書き方で書いてあるため。

  例：「当てる組合せが1通りしかないまとまりは、親を出さない」が
      正本に入ったとき、あるサイトの条件は `k < 2 or m <= 0 or m >= k` だった。
      同じことを指しているが、そうは読めない。
      `math.comb(k, m) == 1` に書き換えた。

**手順は3つ。順番を守る。**

  1. **同値を確かめる。** 確かめずに書き換えるのは、直しではなく
     別の規則に変えること。範囲を決めて総当たりする
  2. 書き換える
  3. **鳴らして確かめる。** 書き換えた条件で、落ちるべきものが
     落ちるか。同値を確かめてあっても、当て方を間違えれば鳴らない

3のあとに、もう1つ。**同値の確認そのものをテストに移す。**
手元で1回確かめただけだと、根拠がどこにも残らない。
古い書き方と新しい書き方を突き合わせるテストを置けば、
どちらを動かしてもずれた時点で落ちる。

### 守りを壊して、鳴ることをテストに残す

「鳴らして確かめる」「直すと黙ることも確かめる」を、**手元で1回ではなく
恒久のテストにする。**

守りのいちばん外側を1つずつ壊し、**壊した状態で落ちること**を並べた表にする。

    住まいの語を1つ落とす          → 居住用の個票が落ちなくなるはず
    当事者の列の判定を常に偽に      → 氏名の例が記録に残るはず
    伏せる関数が伏せなくなる        → 小さい升が実数で出るはず
    落ちた日の収集を捨てる設定に    → その日のぶんが消えるはず
    public でも止まらなくする       → 生データが公開に出るはず

**存在を数えるだけでは分からない。** 「その名前の検査がある」ことと
「壊したときに鳴る」ことは別。実際に壊して確かめる
（開発系が、存在しか見ていない検査が31件あると数えたが、
**数えるだけでは分からず、7つを実際に壊して7つとも鳴ることを確かめた**。
2026-09-18）。

**この表を作る検査自身も、鳴ることを確かめる。**
「壊したあと」を壊れない値にすり替えて、ちゃんと落ちるか。
**検査を足しただけで満足すると、5節に入った穴（あるかしか見ていない）を
自分で踏む。**

全テストを1件ずつ回すので時間はかかる。それでも置く。
**ここが黙ると、ほかの検査が何も守っていないことになる。**

### たまたま合っているほうが、ずれているより見つけにくい

同じバグでも、**毎回ずれるものは気づける。たまたま合うものは気づけない。**

2026-09-19、4サイトのうち2つが同じ形を持っていた。
どちらも走り始めと終わりで日付をまたぐのに、**片方は毎日1日ずれ、
もう片方は合っていた。** 違いは実行にかかる時間だけだった。

    走り始めに打つ  →  始まりの日付。commit の日付とずれる
    終わりに打つ    →  終わりの日付。**速く終わった日だけ、黙って1日戻る**

ずれているほうは、見れば分かるので直せた。合っているほうは、
**いつか速くなった日に、誰にも知られずに1日戻る。**

**「いま合っている」は、正しいことの証拠にならない。**
合っている理由を言えないなら、まだ直っていない。

#### 時計を見る場所は1つ。既にあるなら足さない

走っている途中で日付が変わらないようにするには、**走り始めに1回だけ決めて、
最後まで同じ値を使う。** 時間帯を寄せるだけでは足りない。それは
「たまたままたがない」だけで、走る時刻が動けばまた起きる。

そのとき、**時計を見る関数を新しく作らない。** 既にその役の関数があるなら、
そこに足す。2つあると、次に読む人がどちらが正か迷う（5節）。
大型店日報は無かったので新設し、競売統計は既に持っていたので足した。
**同じ決まりから、違う実装になってよい。**

### 新しく足したファイルは、コミットするまで検査に入らない

検査の対象を `git ls-files` で決めていると、**足したばかりのファイルは
一覧に出ない。** 走らせて通っても、**通ったのではなく、見ていない。**

街頭窃盗統計が踏んだ（2026-09-19）。見出しを数える検査を足した回、
金庫では4本とも通ったのに、公開用の木では落ちた。木は `git archive HEAD`
から作るので**コミット後の姿**で検査され、そこで初めて捕まった。

**足した直後の「通った」は、通った証拠にならない。**
コミットしてから、もう一度走らせる。

**同じ検査を2か所で走らせている意味が、ここにある。** 片方は作業中の姿、
片方はコミット後の姿を見る。1か所だけなら、この穴は残ったままになる。

上の「鳴らせていない見張り」と対になる。あちらは**鳴らない見張り**、
こちらは**見ていない見張り**。どちらも、通ったことが何も保証しない。

### 書いた検査が鳴らないのが、いちばんこわい

検査の中身が緩いと、**壊しても鳴らない。** それでも「検査がある」ので、
誰も疑わない。

競売統計が踏んだ（2026-09-19）。時間帯の設定を見張る検査が
`"TZ" in text` だったので、**設定そのものを消しても通った**。
本文のどこかに `TZ` の3文字があれば通る検査だった。

**鳴らして確かめなければ、気づかない。** 上の「守りを壊して、鳴ることを
テストに残す」は、この形を恒久化したもの。

そして**検査は、書いた人にも掛かる。** 同じ回で、その検査が
**書いた本人の新しいコードを2回捕まえた**（走った日を決める処理で
日付を2回打っていた）。自分のコードを例外にしない。

### 見張る範囲と、公開する木の範囲は、別々に決まってしまう

道具が2つあると、「公開するもの」を2か所で別々に決めることになる。
**片方を直しても、もう片方は付いてこない。**

開発系が踏んだ（2026-09-19）。公開前の語の検査は `docs/` を見ていたが、
公開用の木を作るほうは `docs/` を木に入れていなかった。
**公開しないものを見張り、公開するものを見張っていなかった。**

だから**範囲は1か所で決めて、2つがそろっていることを検査で見張る。**
片方に足したらもう片方にも足す、を人が覚える形にしない。

**そして、見張る範囲に「直せないもの」を入れない。**
同じ回で `docs/letters/`（大阪府と国立国会図書館に**送った手紙の写し**）が
見張りに入っていた。送った文そのものなので、こちらの都合で直せない。
3.3 の語が1つ入っていて、**毎回鳴っていた。**

鳴りつづける見張りは、**鳴らなくなるのではなく、見られなくなる。**
直せないものは、範囲から外すか、外した理由をその場に書く。
（9節「守りを入れる日に、その守りが止めるものが、まだ要ることがある」の
期限つきの例外とは別。あれは**いずれ直す**もの、これは**直せない**もの。）

### 壊して鳴らす前に、`__pycache__` を消す

上の「鳴らして確かめる」は、**手順そのものが嘘をつくことがある。**

Python は `.pyc` が古いかどうかを **(元ファイルの mtime、サイズ)** で決める。
`売却` を `落札` に書き換えると**バイト数が同じ**なので、
**同じ秒のうちに書き換えた場合、両方とも一致してしまい、古いほうが読まれる。**
30回試して30回とも古いままだった（2026-09-19、実測）。

嘘は**両方向に出る。**

    直したのに落ち続ける      → 直し方が悪いのだと思って、余計なものを足す
    壊したのに鳴らない        → 検査が効いていると信じてしまう

こわいのは2つめ。**「壊して鳴った」が、検査の証拠にならなくなる。**

**`python3 -B` では直らない。** `-B` は「新しく `.pyc` を書かない」だけで、
**もうある `.pyc` は読む**（実測。`-B` 付きでも古い値が出た）。消すしかない。

    find . -name __pycache__ -prune -exec rm -rf {} +

検査は、これを先にやる入口（`check.sh` など）から呼ぶ。**手で
`python3 test_xxx.py` と打たない。** 打てるようにしておくと、急いだ日に打つ。

踏みやすいのは**漢字の置き換え**（結果の語・用途地域・見出しの語）。
2文字を2文字に替えるとバイト数が変わらない。競売統計が結果の語を
`売却/不売` から `落札/不調` に寄せた回に踏んだ。

### 出力を見たくて、落ちたことを捨てない

検査は走ったし、落ちてもいた。**それでもコミットと push が通った。**

    python3 test.py | tail -2 && git commit    ← tail の終了コード（0）が返る
    python3 test.py > log 2>&1; echo "$?"      ← $? を読んだ時点で set -e が効かない

どちらも「出力を見たい」から書く形。**見るために、落ちたことを捨てている。**
競売統計が同じ日に2回踏み（2回目は公開用でだけ落ちる1本を公開側に出した）、
**統括もこの文書を直した回に同じ形で書いていた**（2026-09-19）。

落ちたら止まる形で書く。

    python3 test.py > log 2>&1 || { tail -20 log; exit 1; }

パイプの先の終了コードが返るのは `tail` だけではない。`head`・`grep`・`jq`・
`tee` も同じ。**検査の後ろにパイプを置かない。** ログに落として、あとで読む。

### 読んでいるものを、読めているか見ていない

検査がファイルを開いているのに、**そのファイルが壊れていないかは見ていない**、
ということが起きる。開いて、文字として走査して、探している形が無ければ通す。
**壊れていても、探している形は無い。だから通る。**

2026-09-19、大型店日報で踏んだ。マージの衝突を直すときに `git add -A` で
全部拾い、**衝突マーカーが入ったままの `.py` をコミットした。**
`SyntaxError` になっているのに、**47本の検査が全部通った。**
検査は `*.py` を文字として走査していた（伏せる関数を迂回していないかなど）が、
**構文が通るかは一度も見ていなかった。**

同じ形を、この日だけで5回踏んだ。**どれも道具は正しく、当て方が狭かった。**

    浅いクローンで履歴を数えた    持っていないものは数えられない
    枝の上で「無い」と数えた      本流は見ていない
    コミット前のファイル          `git ls-files` の一覧に出ない
    `"TZ" in text`                設定を消しても通る
    `*.py` を文字として読む       **読めない `.py` でも通る**

同じ形は、そのあとも出ている。

    古い `__pycache__`            **書き換えても、古いコードを検査している**
    検査の後ろのパイプ            **落ちても、パイプの 0 が返る**
    `docs/` を見張っていた        **公開する木に `docs/` は入っていない**

**開いたものは、開けているかを最初に見る。** その形式で当たり前の読み方を
1回通す（`.py` なら構文、JSON なら parse、YAML なら load）。
通らなければ、中身を見る前に落とす。

**`git add -A` は衝突マーカーも拾う。** 衝突を直したあとは、
コミットする前に手元で1回走らせる。生成物の衝突は手で直さず、**作り直す。**

### 画面に出すものは、画面で当てる

出来上がった HTML を、**読んで確かめたことにしない。** 実際にブラウザで開いて、
狭い画面を含む複数の幅で見る。

2026-09-19、大型店日報で一覧を2ページ作った。書いたときには気づかず、
ブラウザで当てて初めて3つ出た。**どれもコードを読んでも見えない。**

  ・**画面の外に出た列は、無いのと同じ。** 狭い画面で横に溢れていた
  ・**見出しが折り返さないと、見出しの長さが列の幅を決める。**
    8文字の見出しが105pxを取り、表が画面からはみ出していた
  ・**見えないつもりの文字が、見えることがある。** 場所取りに使った
    空白文字が、font によって□で出た

見る幅は、いちばん狭いところを含める。手元の端末だけで見ると、
**その端末で通っただけになる。**

  ・横に溢れていないこと（`scrollWidth > innerWidth` が偽）
  ・JavaScript がエラーを出していないこと
  ・絞り込み・並べ替えが、実際に行を変えていること

**数が合っていることまで見る。** 「絞り込んだら37件」を、データの側の数と
突き合わせる。画面が動いているだけでは、正しいことにならない。

### 守りを入れる日に、その守りが止めるものが、まだ要ることがある

守りは、要らなくなったものを止めるために入れる。だが**入れる日と、止める先が
まだ要る日は、重なることがある。**

2026-09-19、競売統計で起きた。9節は「収集用は**置き場**。収集用の Actions は止め、
workflow は持たせない」と決めていて、その守りが同じ括弧にある「名前が `-raw` で
終わるか `-raw-` を含むリポジトリでは workflow が自分で止まる」。競売統計には
まだ入っていなかった。ところがその日、金庫がまだ唯一の集め手だった。金庫の名前は
既に `-raw` で終わっていて、公開用の Actions は鍵が未了で動かせない。素直に入れると、
その晩の巡回がその1行で止まる。裁判所の入札物件は消えるので、**止めた日のぶんは
永久に取れない**（3.5「巡回の頻度が、そのまま記録の完全性になる」）。

守りを入れないのは、入れる日が来ないのと同じ。守りを弱めるのは、元の条件が
どこにも残らず、戻すときに書き直しになる。**守りはそのまま入れ、期限つきの例外を、
消す条件と一緒に置く。**

#### 例外には3つ要る

条件は書き換えない。通す口を1つだけ足す。

    名前が `-raw` で終わる／`-raw-` を含む  かつ  印が無い  → 止まる
    同上                                    かつ  印がある  → 通す。毎回そう出す
    どちらでもない名前                                      → 通す（印のあるなしに関わらず）

  ・(a) 消す条件が書いてある
  ・(b) 効いているあいだ、そう見える（走るたびに出る）
  ・(c) 例外が残ったまま先に進むと止まる

**(c) が無い例外は、消えない。** (a) は読む人がいないと効かず、(b) は読み飛ばせる。
止まるものだけが残り続けない。競売統計では、印が公開用の木に混ざったら、
公開用の木を作るスクリプトが中断する形にした（印が届くと、公開用でも
自己停止が素通りするため）。

**(c) も、置いた日に人工的に鳴らす。** 鳴らせないうちは (c) ではない
（9節「鳴らせていない見張りは、動くと分かっていない見張り」）。
いまは `.github` が公開用の許可リストに無いので、この経路は一度も通らない。
**通らない見張りは、置いた日に1回だけ人工的に通す。**

印は1ファイルにする。条件をあちこちに書くと、消すのが1回の動作にならない。
中身に、作った日・消す条件・消し方・なぜ要るかを書く。

#### 消す条件は、日付ではなく出来事で書く

「あとで消す」とだけ書いた例外は消えない。かといって**日付で書くと、その日に
何も起きていなくても消す。** 待っていたことが済んでいなくても期限が来る。

出来事で書く。走った・引けた・届いた、のように**後から確かめられるもの**にする。
「落ち着いたら」は出来事ではない。競売統計は「公開用が1回通った日」にした。

出来事で書くと、出来事が来ないかぎり例外は残る。だから**出来事は、既にある手順の
段に書き込む。** どこにも書かれていない出来事は、誰も待っていない
（9節「貼り付け用に書いたものは、リポジトリにも1行残す」と同じ形）。
消すときは、守りと印を**同じコミットで**消す。片方だけ残ると守りが黙る。

#### 自己停止が効き始めるのは、rename した瞬間

作り直す順番では、**④の rename で名前が `-raw` になった瞬間に自己停止が効く。**
⑤で workflow を消すより前。そして公開用の Actions が走れるのは、⑥で Deploy key、
⑧で Secret を入れたあと。**④から⑧のあいだ、集め手がいない。**

だから⑤は2つの動作に分ける。**private 化はすぐ。workflow と印を消すのは、
公開用が1回通ってから。** 塞ぐほうは遅らせない。

#### 例外が消えたあとの姿を、置いた日に試す

**例外を消したあとの姿は、消す日まで一度も走らない。** その日に初めて走らせて
落ちると、守りの直しと引っ越しが同じ日に重なる。

**置いた日に、印が無い形を先に通す。** 印あり・印なし・置き場の名前の組合せを、
全部その日に確かめる。**存在を数えるだけでは分からない**ので、workflow から
`run:` の本文を取り出し、名前と印を入れ替えながら実際に走らせる。
`-raw` でない側が印のあるなしで変わらないことも固定する。ここを見ていないと、
印が公開用に届いた日に守りが静かに外れる。

#### 期限つきの例外を置いてよいのは、あとから直せる守りだけ

この形を全部の守りに当てない。**「例外なし」と書いてある守りには、当てない**
（3.2「当てる組合せが1通りしかないまとまりは、親を出さない。例外なし」、
3.5「全レコードに `source_url` と `fetched_on` を必ず付ける。例外なし」）。
3.1 の氏名と地番も同じ。出してしまった氏名も、引き算で戻る升も、印を消しても戻らない。

**比べるのは、守りを破る害と、守りが止める害の、取り返しのつきかた。**
金庫で Actions が走るのは置き場の形の話で、あとから直せる。取れなかった晩は直せない。
取り返しのつく側に倒す。どちらも取り返しがつかないなら、例外は置かずに、
先に進むのをやめる。

### 決めてから当てるまでの間を、書いておく

名前・ドメイン・`site_id`・URL・UA は「**⓪のあとに一度に差し替える**」。
だが**決まってから⓪が済むまでの間**、リポジトリには
「決まった名前」と「まだ当てていない名前」が同時にある。
次に読む人には、どちらが正なのか分からない。

**決定は先に書く。当てるのは⓪のあと。両方を1か所に並べて書く。**

    決めたもの        ドメイン／site_id／id の接頭辞   （2026-09-18 決定）
    まだ当てていない  UA／リポジトリ名                 （⓪のあと）
    まだ当てていない  site_url／Pages                  （配信を確かめてから）

**内部の鍵と、外向きの名乗りは分けてよい。**

  ・`site_id` と `id` の接頭辞は**鍵**。`records` が0件のうちが唯一の窓。
    出し始めてからだと「鍵は変えない」に触れる。先に当ててよい
  ・UA・リポジトリ名は外向きの**名前**。3.4「404 になる URL を入れない」は
    「名乗るな」ではない。3.4 の後ろの形（屋号・サイト名・連絡フォームの URL
    だけ）なら 404 になる URL を持たないので、⓪のあとに当てる
  ・`site_url`・Pages は外向きの **URL**。3.4 が正面から掛かる。
    引けるようになってから当てる（下の「名前は先に当てられる。URL は配信を
    確かめてから」）

「一度に」が守ろうとしているのは「**どこかが古いまま残らないこと**」で、
内部の鍵と外向きの名乗りでは、古く残ったときの害が違う。

### 名前は先に当てられる。URL は配信を確かめてから

作り直す順番の⓪（Verified domains）が保証するのは「**ほかの人にそのドメインを
取られない**」ことだけ。そこに何かがあることは保証しない。
⓪はアカウントの設定、独自ドメインを Pages に付けるのは同じ順番の⑧で、
そちらはリポジトリの設定。公開用リポジトリが無ければ、付ける先も無い。

2026-09-19、競売統計で⓪が済んだあと、UA は
`kujiraya archive bot (keibai-toukei; …)` に当てられたが、`site_url` は
当てられなかった。公開用リポジトリがまだ無く、Pages も設定していないので、
`curl` が `keibai-toukei.com` を引けなかった。

同じ「⓪のあと」でも、当てられる時期が違う。**鍵 → 名前 → URL の順に当たる。**
鍵（`site_id`・`id` の接頭辞）は `records` が0件のうち、
名前（UA・リポジトリ名）は⓪のあと、
URL（`site_url`・`Sitemap:` 行・`sitemap.xml`）は配信を確かめてから。

3.4「404 になる URL を入れない。確認できない名乗りは、名乗らないより
不審に見える」は、名前ではなく URL に掛かる。3.4 の短い形は 404 になる URL を
含まないので⓪の直後に当てられる。`site_url` は URL そのものなので、
引ける前に当てると、名乗った先が 404 になる。
UA も、URL を含む形に差し替えるのは配信を確かめてから
（上の「URL に連動するものを、固定文字列で書かない」）。

**当てる条件は「⓪が済んだ」ではなく「引けた」。** `curl -I` で 200 を見てから
当て、見た日を決定ログに書く。

### 手順を作ったら、既にあるものにも一度当てる

ドメインの検証（作り直す順番の⓪）は、作り直しの手順の中に書いた。
これから公開するサイトの話として書いたので、**既に公開しているサイトは
手順の外**に置かれた。

2026-09-19 に見たところ、4サイトで最初に公開したドメイン
（大型店日報・`ogataten-nippo.com`）が検証されていなかった。
これから作るほうにだけ当てていた。

手順は、たいてい「これから作るもの」を見て書く。書いた時点で既にあるものは
手順のどの段にも現れないので、抜けても何も落ちない。
5節の「「あるか」を見る検査は、「合っているか」を見ていない」が、
手順の側に出た形。

  ・手順を足したら、その場で既にあるサイト全部に1件ずつ当て、当てた日を書く
  ・当て終わるまで「手順を入れた」と報告しない
  ・当たらないサイトがあるなら、当たらない理由を書く
    （1節「どの節が効くかは、サイトによって違う」）

11節の手順3（各サイトの `common/` を更新する）が正本の置き場自身に抜けていた
のと同じ形。11節「上げる前に、ほかのサイトの実物を見る」は見張りの話で、
こちらは手順の話。**見張りは無い穴に足さない。手順は既にあるものにも当てる。**

上の「前身の置き場を見る」は同じ形の別の面。あちらは過去の置き場が手順の外に
残る話、ここは現に動いているものが手順の外に残る話。

## 10. 報告の形（各サイトのチャット共通）

4サイトの進み具合は、共通仕様チャット（大型店日報のチャット）に集約している。
そこへ貼るとき、長い報告のままだと読めない。**報告する側が短い版を用意する。**

各サイトのチャットは、報告のたびに本文の最後にこれを付ける。
**画面の操作を頼むときも同じ。** 運営者は手元の端末（多くはスマートフォン）で
GitHub の画面を触る。**貼る値は1つずつコードブロックに入れる。**
リポジトリ名・Secret の名前・ドメイン・入力欄に入れる語を、地の文に混ぜない。
1つの枠に1つだけ入れる。2つ入れると、どちらもコピーできない。

押す場所は**見出しの文字そのまま**で書く（`Run workflow`・`Allow write access`）。
訳さない。画面が英語なので、訳すと探せなくなる。

**必ずコードブロック（``` で囲む）で出すこと。** 地の文で書くとコピーの範囲を
**必ずコードブロック（``` で囲む）で出すこと。** 地の文で書くとコピーの範囲を
指でなぞることになり、貼るのが面倒になる。コードブロックならコピーボタンが出る。

````
```
━━━ 共通仕様チャット貼り付け用 ━━━
【やったこと】3行まで
【決まったこと】箇条書き3つまで
【数字】検証した件数・実測値だけ
【判断が要ること】無ければ「なし」
【次にやること】1行
━━━━━━━━━━━━━━━━━━━
```
````

- 10行を超えない。理由や経緯は書かない。
- 本文はこれまで通り詳しく書いてよい。最後にこの枠を足すだけ。
- 「【判断が要ること】なし」と書けるなら、それが一番いい報告。

## 11. この文書の直し方

1. `VirgoB77/ogataten-nippo` にブランチを切って、この文書を直す
2. Pull Request を出す
3. マージされたら、各サイトのリポジトリで `common/addr.py` と `common/privacy.py` を更新する

### 見つけたあと、何をするか

公開してしまったものを見つけたとき、**何をどこまでやるか**の線引き。

| 見つけたもの | どうするか |
|---|---|
| **他人の氏名・地番** | **塞ぐ。** 可視性を落とす、公開用を作り直す |
| 運営者自身の連絡先 | 受け入れる。止血（noreply 化）だけする |
| 当事者に結びつかない統計の升 | 受け入れる |

三段目は「**升だから軽い**」ではない。「**当事者に結びつかないから軽い**」。
升でも当事者に結びつくものは重い。

**事後の重さと、事前の基準は別。** この表は「**見つけたあと何をするか**」であって、
「最初からどこまで気をつけるか」ではない。**公開する前なら費用はゼロ**なので、
事前の基準は下げない。

街頭窃盗統計・大型店日報・競売統計の3者が、独立に同じ線に着いた（2026-09-17）。

### 上げる前に、ほかのサイトの実物を見る

この節は「食い違いを見つけたら報告する」と書いているが、**その裏側**を
言っていなかった。

**「4サイトに効きそうだ」と思ったら、送る前にほかのサイトの実物を見る。**
自分の置き場にある穴が、ほかにもあるとはかぎらない。

効きそうだから送ると、**無い穴の見張りを、ほかのサイトに足させることになる。**
足した見張りは鳴らない。鳴らない見張りは、そのうち読み飛ばされる
（9節「常に鳴る見張りは、鳴らない見張りと同じくらい役に立たない」の逆で、
**一度も鳴らない見張り**も同じ）。

    競売統計が「設定が読めない日に、既定値へ黙って落ちる」を上げようとした
      → 街頭窃盗統計を見たら、そもそも設定を読み込んでおらず、落ちようがない
      → その作りは1サイトにしかなかった。**上げるのをやめた**（2026-09-18）

**これは報告をためらう理由にはならない。** 見るのは「**ほかにもあるか**」で
あって、「**報告してよいか**」ではない。1サイトにしか無ければ、
その1サイトで直す。**確かめたことも含めて報告すれば、次に同じ形が出たとき
2サイト目として上がる**（5節の線3）。

### 食い違いを見つけたら、直す前に報告する

**この文書は間違っている可能性がある。** 実装していて、

- 節と節で食い違っている
- どちらにも読めて、どちらが正しいか決められない
- 書いてある通りにすると明らかにおかしくなる

に気づいたら、**自分の解釈で先に進まずに報告すること。** 正本のほうを直す。

仕様を書いた側は自分の矛盾に気づけない。実装する側が「両方要ると読んだけれど
合っているか」と聞いてくるのが、いちばん早く正しくなる。これは手戻りではなく、
いちばん安い直し方。

実際にこれで直った例：

- 3.1（画面は `個人` と表記）と 6（`party` は空文字）が食い違って見えた
  → どちらも正しく、用途が違うと分かった。5節に関数を分けて書いた
- 3.1「入札中物件は扱わない」が、集計の件数まで禁止に読めた
  → 個票だけが禁止で、集計は構わないと書き直した
- 3.4「公報は月2回」が、姉妹サイトの GitHub を読むときにも当てはまるように読めた
